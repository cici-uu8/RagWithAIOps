# MySQL 慢查询告警处理手册

## 文档状态

- 候选编号：C6-SRC-MD-003
- 适用部门：process_digital_dept
- 适用场景：MySQL slow query、DBSlowQuery、接口 P99 升高、数据库 CPU 或连接池压力异常
- Owner 批准：C6-P1b owner-approved runbook source, 2026-06-12
- 安全边界：本文只允许只读诊断、索引/SQL 优化建议和变更申请；生产库写入、删除、DDL 必须遵守数据库操作权限和审批流程

## 告警定义

当 MySQL 出现以下任一信号时，进入慢查询处理流程：

- `mysql_query_latency_seconds` P95 或 P99 连续 5 分钟高于阈值
- 慢查询日志中 `query_time > 1s` 的 SQL 明显增加
- 数据库 CPU、IO wait 或 buffer pool miss 同时升高
- 应用连接池等待、超时或队列堆积
- 核心接口 P99 升高并且 trace 显示耗时集中在数据库访问

慢查询可能由缺失索引、执行计划变化、数据量增长、锁等待、连接池耗尽、批处理任务或缓存失效引起。处理时必须先确认影响范围和 SQL 指纹，不能直接在线修改表结构。

## 立即分级

### P1

满足任一条件时按 P1 处理：

- 核心交易、登录、下单、查询链路大量超时
- 数据库 CPU 持续高于 85% 且业务错误率上升
- 连接池耗尽导致请求排队
- 慢 SQL 引发主从延迟或锁等待扩散

### P2

满足以下条件时按 P2 处理：

- 慢查询数量增加，但核心链路尚可用
- 只影响后台报表、离线任务或非核心接口
- 单个 SQL 指纹变慢，尚未形成全局资源压力

## 排查步骤

### 步骤 1：确认时间窗口和影响面

需要记录：

- 告警开始时间和持续时间
- 受影响服务、接口和租户范围
- 数据库实例、schema 和表名
- 是否有发布、数据导入、定时任务或大促流量
- 是否同时出现 Redis miss、API 5xx 或 SlowResponse

### 步骤 2：获取慢查询样本

优先使用只读平台能力或慢查询日志。

需要聚合：

- SQL fingerprint
- count
- avg latency
- p95 latency
- rows examined
- rows sent
- lock time
- first seen / last seen

不要把带参数的完整 SQL、用户隐私字段或生产数据贴到公共群里。对外沟通时使用 SQL 指纹和脱敏样例。

### 步骤 3：查看执行计划

对候选 SQL 使用只读 `EXPLAIN` 或平台执行计划功能。

重点检查：

- 是否走到预期索引
- `type` 是否退化为 `ALL`
- `rows` 是否异常放大
- 是否出现 filesort 或 temporary
- join 顺序是否异常
- where 条件是否被函数包裹导致索引失效

### 步骤 4：检查锁等待和连接池

慢查询不一定是 SQL 本身慢，也可能是等待资源。

需要确认：

- 是否有长事务
- 是否有行锁或 metadata lock
- 应用连接池 active / idle / wait 指标
- 数据库连接数是否接近上限
- 是否有批处理任务占用连接

### 步骤 5：关联缓存和上游流量

如果慢查询突然增加，需要检查：

- Redis 命中率是否下降
- 是否有缓存穿透或缓存雪崩
- 上游接口 QPS 是否突增
- 是否有新版本改变查询条件
- 是否有新增报表或导出任务

## 常见原因和处理

### 原因 1：缺失或不合适的索引

特征：

- `EXPLAIN` 显示全表扫描
- `rows examined` 很高
- SQL 过滤条件稳定但数据量增长后变慢

处理：

- 评估组合索引顺序是否匹配 where/order by
- 使用影子环境或从库验证索引收益
- 生产加索引必须走变更审批，避开高峰
- 加索引后复查执行计划和写入延迟

### 原因 2：SQL 写法导致索引失效

特征：

- where 条件对列使用函数或隐式类型转换
- like 前缀为通配符
- order by 和 limit 未命中索引
- 大 offset 分页

处理：

- 移除列上的函数包装
- 修正字段类型和参数类型
- 改成基于游标的分页
- 拆分复杂查询或预聚合

### 原因 3：锁等待或长事务

特征：

- SQL 本身扫描行数不高，但 lock time 高
- 更新或 DDL 操作正在运行
- 多个请求等待同一资源

处理：

- 找到阻塞事务和 owner
- 暂停相关批处理任务
- 按审批流程处理异常长事务
- 复盘事务范围和提交策略

### 原因 4：连接池耗尽

特征：

- 应用日志出现 connection timeout
- 数据库连接数接近上限
- 慢查询和请求排队同时出现

处理：

- 临时扩容应用实例或连接池，但不能超过数据库承载能力
- 限流低优先级接口
- 优先修复最慢 SQL，减少连接占用时间
- 检查连接泄漏

### 原因 5：缓存失效导致回源放大

特征：

- Redis miss 上升
- 数据库 QPS 突然增加
- 热点查询集中在少数接口

处理：

- 恢复或预热热点缓存
- 对穿透参数做校验和空值缓存
- 对热点接口限流
- 与 Redis high memory 或 cache miss storm 一起复盘

## 应急措施

5 分钟内可执行：

- 通知数据库 owner、服务 owner 和 on-call commander
- 限流或降级触发慢查询的非核心接口
- 暂停报表、导出、批处理等低优先级任务
- 将读流量切到健康只读实例，前提是权限和一致性要求允许

30 分钟内完成：

- 固定 top SQL fingerprint
- 给出执行计划和锁等待判断
- 明确是索引、SQL、锁、连接池、缓存还是流量问题
- 形成临时止血和长期修复 owner

## 验证标准

处理完成后必须同时满足：

- 慢查询 count 回落到正常水平
- 目标 SQL P95 / P99 恢复到阈值以下
- 应用连接池等待恢复正常
- 错误率和接口 P99 恢复
- 没有新增主从延迟、锁等待或数据库 CPU 异常
- 已记录 SQL fingerprint、根因、处置动作和后续变更计划

## 禁止动作

- 禁止在生产库直接执行未审批 DDL
- 禁止在群里发送含用户数据的完整 SQL
- 禁止用 `KILL` 长事务替代 owner 确认和影响评估
- 禁止把连接池无限调大来掩盖慢 SQL
- 禁止只看应用日志，不查执行计划、锁等待和数据库指标
