日期：2026-06-02

状态：方案决策稿；当前代码已支持受控只读 `safe_select`（C2 commit `201252e`）。DB-MySQL-1 已完成 MySQL 只读 provider、独立 `MySqlSafeSqlKernel`、PyMySQL 只读连接器、配置启用、自动化验证和本地 Docker MySQL live smoke。DB-Ops-2 tool schema、DB-Ops-3 SQL 操作分类器、DB-Ops-4 operation permission resources、DB-Ops-6 prepare operation 后端、DB-Ops-7/8 用户确认 + sandbox 执行管线、DB-Ops-9 审计回归门禁和 DB-Ops-10 真服务 smoke 已完成；DB-RAG-1 已把 `list_database_tables`、`describe_database_table`、`safe_select_database` 作为只读 LangChain tools 接入 RAG Agent。现在能表达严格 function tool schema、识别 L1/L2/L3/L4/L5/M1，并能用 `database_operation/<database_id>.update|delete|ddl/execute` + table/column scope 控制数据库操作。产品规则已更正：非删除写操作和非删除 DDL 有权限后直接执行并审计；删除类操作才生成 SQLite 持久化 confirmation，并由用户后台确认后执行。DB-MySQL-3 已新增并 live-smoke 验证非生产 MySQL `INSERT` / `UPDATE` 直接执行路径，并保留 `DELETE` 确认流；DB-MySQL-4 已实现并 live-smoke 验证非生产 MySQL L5 非删除 DDL direct execute，同时保留 `DROP TABLE` 等删除类 DDL confirmation。生产库接入仍未开放。

## 1. 目标

本文件定义数据库操作在企业助手里的能力分级、确认方式和后台边界。核心原则是：

- 只读能力可以直接执行，但必须继续经过权限、表列 allowlist、SQL AST 校验和审计。
- 写入、修改、删除和表结构变更是数据库操作能力，不等同于后台权限管理。
- 数据库操作按“是否拥有对应 `database_operation` 权限”决定能否执行；没有权限时直接拒绝。
- 非删除写操作和非删除 DDL 有权限后直接执行，不生成确认项。
- 删除类操作必须到用户后台做确认后才能执行。
- 授权、撤权、角色、部门 scope 等权限管理属于管理员专职后台，不归普通数据库操作确认流。

- `POST /api/database/safe-select`（C2 commit `201252e`）
- RAG Agent 只读工具：`list_database_tables`、`describe_database_table`、`safe_select_database`

这些能力已经走：

### 2.0.1 DB-MySQL-3 非生产 MySQL 非删除写操作直接执行

真实场景不等于直接拿生产库开刀。DB-MySQL-3 的第一版目标是在一个“真实 MySQL 协议、真实事务、真实表结构、可写账号、非生产数据”的 MySQL 上，把非删除写操作改为有权限后直接执行，把删除类操作继续留在用户确认流。

执行边界：

- `INSERT`：有 `database_operation/<database_id>.update/execute` + table/column 权限后直接执行，不生成 confirmation。
- `UPDATE`：有 `database_operation/<database_id>.update/execute` + table/column 权限后直接执行，不生成 confirmation。
- `DELETE`：有 `database_operation/<database_id>.delete/execute` + table/column 权限后只能 prepare，必须由用户后台 confirm 后执行。
- `DROP TABLE` / `TRUNCATE` / `ALTER TABLE DROP COLUMN`：删除类，必须走用户后台确认；DB-MySQL-4 已把 `DROP TABLE` 接入非生产 MySQL confirmation 执行链路。
- `CREATE TABLE` / `ALTER TABLE ADD COLUMN` / `ALTER TABLE MODIFY COLUMN` / `RENAME TABLE` / `RENAME COLUMN` / `CREATE INDEX` / `DROP INDEX`：非删除 DDL，有 `database_operation/<database_id>.ddl/execute` 权限和 scope 权限后直接执行；DB-MySQL-4 已完成非生产 MySQL runtime 和 live smoke。
- 无对应 `database_operation` 权限：直接 403；非删除操作不生成 confirmation，删除类也不生成 confirmation。
- 删除类 confirm 前仍复核 SQL hash、参数 hash、operation/table/column 权限、目标表列和 preview 摘要。
- 审计必须继续记录 `sql_hash`、`resource_ids` 和执行结果；删除类审计继续串 `confirmation_id`，不能绕过管理员 grant/revoke，也不能绕过用户确认流。

阶段切片：

- DB-MySQL-2：历史切片；曾把 UPDATE/DELETE 都放入确认流，已发现与产品规则不一致。
- DB-MySQL-3a：已完成设计更新；废除“所有 L3-L5 都确认”的口径，改为“只有删除类确认”。
- DB-MySQL-3b：已新增非删除写操作直接执行 API，第一切片覆盖 MySQL `INSERT` / `UPDATE`。
- DB-MySQL-3c：MySQL `DELETE` 继续走 prepare -> confirm，确认流保留。
- DB-MySQL-3d：已完成真 MySQL live smoke，验证 INSERT、UPDATE 直接执行，DELETE 仍需确认，无权限 403，audit 不缺字段。

### 2.0.2 DB-MySQL-4 非生产 MySQL L5 DDL 已实现

DB-MySQL-4 已把 L5 表结构变更从“方案规则”推进到非生产 MySQL 运行时验证。规则延续 DB-MySQL-3：只把删除类操作放进用户后台确认流；可恢复或可重建的非删除 DDL 在有权限后直接执行并审计。

直接执行范围：

- `CREATE TABLE`
- `ALTER TABLE ADD COLUMN`
- `ALTER TABLE MODIFY COLUMN`
- `RENAME TABLE`
- `RENAME COLUMN`
- `CREATE INDEX`
- `DROP INDEX`

仍需确认或默认关闭的范围：

- `DROP TABLE`
- `ALTER TABLE DROP COLUMN`
- `TRUNCATE`
- `DROP DATABASE`，如果未来支持，必须默认关闭或至少进入删除类确认流

执行边界：

- 非删除 DDL 必须拥有 `database_operation/<database_id>.ddl/execute` 权限。
- 对已有表、列或索引的 DDL，仍必须满足当前 table/column scope。
- 对新建表、重命名目标和新增列，必须经过 DDL allowlist / registry 规则验证，不能因为对象尚不存在就绕过 scope。
- 成功执行写 `database_operation_direct_executed`，记录 `operation_type=ddl`、`sql_hash`、`parameters_hash`、`resource_ids`、schema impact 和 `rows_affected`。
- 执行失败写 `database_operation_direct_execution_failed`，不暴露底层数据库敏感错误。
- 删除类 DDL 继续走 prepare -> 用户后台 confirm -> confirm-time 复核 -> transaction execute。
- 生产库 DDL 接入仍需要独立生产策略，不从 Docker MySQL smoke 自动外推。

阶段切片：

- DB-MySQL-4a：已完成规则和计划更新，冻结“非删除 DDL 直接执行，删除类 DDL 确认”的口径。
- DB-MySQL-4b：已扩展 MySQL classifier / permission checker / direct executor，支持非删除 DDL direct execute。
- DB-MySQL-4c：已保留删除类 DDL confirmation executor，覆盖 `DROP TABLE`；`TRUNCATE` / `ALTER TABLE DROP COLUMN` 仍按删除类分类和权限模型处理。
- DB-MySQL-4d：已完成本地 Docker MySQL live smoke，trace 为 `mysql-ddl-smoke-202606022317`，覆盖真实 `CREATE`、`ALTER`、`RENAME`、`CREATE INDEX`、`DROP INDEX`、`DROP TABLE` 确认流、撤权失败、重放失败和 audit。

### 2.1 SQL 操作分类器

当前 DB-Ops-3 已新增 standalone 分类模块：

- `app/enterprise/database/operation_classifier.py`
- `tests/test_enterprise_database_operation_classifier.py`

分类器基于 `sqlglot` AST，不靠字符串包含。它能把 SQL 归类为：

- L1：`SELECT`
- L2：`EXPLAIN` / `SHOW` / `DESCRIBE` 等 metadata 操作
- L3：`INSERT` / `UPDATE`
- L4：`DELETE` / `TRUNCATE` / `DROP TABLE` / `ALTER TABLE DROP COLUMN`
- L5：`CREATE TABLE` / 非删除类 `ALTER TABLE` / `CREATE INDEX` / `DROP INDEX` / rename / modify
- M1：`GRANT` / `REVOKE`，不进入普通数据库操作确认流

边界：

- 分类器只负责后续路由决策，不替代 `SafeSqlKernel` / `MySqlSafeSqlKernel` 的执行前安全校验。
- 分类器当前未接入 `safe_select`、audit、prepare 或 confirm；现有只读执行路径行为不变。
- 如果分类器判定为 L1，但只读 kernel 因 JOIN、函数、未授权表列、锁定 SELECT 等原因阻断，必须以 kernel 阻断为准。

### 2.2 Operation 权限资源

当前 DB-Ops-4 已新增 operation 权限资源和 prepare 前置权限 checker：

- `app/enterprise/database/permissions.py`
- `app/enterprise/database/operation_permissions.py`
- `tests/test_enterprise_database_operation_permissions.py`

资源模型：

```text
database_operation / <database_id>.update / execute
database_operation / <database_id>.delete / execute
database_operation / <database_id>.ddl / execute
```

映射规则：

- L3 `INSERT` / `UPDATE` -> `update`
- L4 `DELETE` / `TRUNCATE` / `DROP TABLE` / `ALTER TABLE DROP COLUMN` -> `delete`
- L5 DDL -> `ddl`

`DatabaseOperationPermissionChecker` 判断某条 SQL 是否拥有进入后续执行路径的资格；DB-MySQL-3 中它既服务删除类 prepare，也服务非删除写操作 direct execute：

- 先检查 `database_operation/<database_id>.<operation>/execute`
- 再检查涉及表的 `database_table/<database_id>.<table>/read`
- 再检查涉及列的 `database_column/<database_id>.<table>.<column>/read`
- 支持 `INSERT` column list 和子查询表/列 owner 解析
- 保持 PermissionService 的默认 deny 和 deny 优先

边界：

- DB-Ops-4 本身只定义权限判定，不直接执行 SQL。
- DB-Ops-7/8 已新增 confirm/cancel API，并先在 `sandbox_sales` SQLite sandbox 内开放确认后执行。
- 当前没有把 L3-L5 接入 `safe_select` route、`ToolGateway` function calling 或 `MySqlSafeSqlKernel`。
- DB-MySQL-2 曾把非生产 MySQL UPDATE/DELETE 接入 confirmation executor；DB-MySQL-3 已更正为 MySQL `INSERT` / `UPDATE` 直接执行、`DELETE` 保留 confirmation。DB-MySQL-4 已把非删除 DDL direct execute 和删除类 DDL confirmation 接入非生产 MySQL。

### 2.4 Prepare operation 后端

当前 DB-Ops-6 已新增 HTTP prepare 后端：

- `app/enterprise/database/confirmations.py`
- `app/enterprise/database/routes.py`
- `tests/test_enterprise_database_operation_prepare.py`

当前 prepare 链路：

```text
CurrentUser
  -> RequestContext
  -> POST /api/database/operations/prepare
  -> DatabaseOperationPermissionChecker
  -> read-only preview
  -> SQLiteDatabaseOperationConfirmationRepository
  -> database_operation_prepare_created / rejected audit
```

已实现能力：

- 历史 sandbox 路径中，有 operation/table/column 权限的 `UPDATE` 会生成 `pending` confirmation。
- 当前产品规则中，有 operation/table/column 权限的 `DELETE` 会生成 `pending` confirmation。
- 删除类 DDL 如 `DROP TABLE` 在支持的 sandbox 和非生产 MySQL 路径中会生成 `pending` confirmation；DB-MySQL-4 已规划并实现非删除 DDL direct execute、删除类 DDL confirmation。
- 无 operation 或 table/column 权限时直接 403，不生成 confirmation。
- `UPDATE` / `DELETE` 的第一版 sandbox preview 只执行只读 `SELECT COUNT(*)` 估算影响行数。
- `DROP TABLE` 等无法可靠估算的操作显式返回 `estimate_reliable=false` 和 `estimated_affected_rows=null`。
- confirmation 记录包含 SQL hash、参数 hash、SQL hash version、normalization version、risk summary、TTL 和 `expires_at`。

边界：

- DB-Ops-6 完成时没有用户后台列表、确认或取消页面；这些已在 DB-Ops-7/8 通过普通用户“我的权限”弹层和 confirmation API 补齐。
- 当前没有把 `database_demo.prepare_operation` 注册成 function calling tool。
- Prepare 入口仍不运行任何写入、删除或 DDL SQL；执行只发生在确认后的删除类链路，或 DB-MySQL-3 的独立 direct execute 路径。
- DB-MySQL-3 已开放非生产 MySQL `INSERT` / `UPDATE` direct execute；`DELETE` 仍走确认；DB-MySQL-4 已开放非生产 MySQL 非删除 DDL direct execute 和删除类 DDL confirmation，生产接入仍需后续独立切片。

### 2.5 用户确认和 sandbox 执行

当前 DB-Ops-7/8 已新增用户确认和 sandbox 执行管线：

- `GET /api/database/confirmations`
- `GET /api/database/confirmations/{confirmation_id}`
- `POST /api/database/confirmations/{confirmation_id}/cancel`
- `POST /api/database/confirmations/{confirmation_id}/confirm`

执行链路：

```text
pending confirmation
  -> owner / pending / TTL / SQL hash / parameter hash recheck
  -> operation/table/column permission recheck
  -> target table/column recheck
  -> reliable preview row-count recheck
  -> atomic pending -> executing
  -> SQLite sandbox transaction
  -> executed / failed audit
```

已实现能力：

- 用户只能列出、查看、取消、确认自己的 confirmation。
- `cancelled`、`expired`、`executed`、`failed` 不能再次 confirm。
- confirm 时权限被撤销、SQL hash 被篡改、参数 hash 不匹配、TTL 过期或可靠 preview 变化，都会拒绝执行。
- `UPDATE`、`DELETE`、`DROP TABLE` 可在历史 `sandbox_sales` SQLite sandbox 中通过确认执行；DB-MySQL-3 已将非生产 MySQL `INSERT` / `UPDATE` 改为 direct execute，MySQL `DELETE` 继续通过确认执行。
- 普通用户“我的权限”弹层展示数据库操作确认项、风险、SQL、目标表列、预估影响行数、状态、confirm/cancel 按钮。
- DB-Ops-9 已补齐 prepare / cancel / confirm / execute / expired / failed 审计中的 `parameters_hash` 和 `resource_ids` 稳定字段，便于按同一个 `confirmation_id` 串起全链路。
- DB-Ops-10 真服务 smoke 已通过真实 uvicorn HTTP 端口验证：无删除权限 403、不生成确认；授权后 prepare 不改数据；撤权后 confirm 复核失败；重新授权后 confirm 真执行；重放失败；audit 能区分普通用户数据库确认链路和管理员 grant/revoke 链路。

边界：

- 管理员后台仍只负责授权、撤权、角色和部门 scope，不承载普通用户数据库操作确认。
- 没有把 confirm 暴露为 function calling tool；模型最多只能走 prepare，confirm 只能由用户 HTTP/UI 触发。
- 非生产 MySQL `INSERT` / `UPDATE` 已在 DB-MySQL-3 通过 direct execute 开放；MySQL `DELETE` 保留确认；DB-MySQL-4 已开放非生产 MySQL 非删除 DDL direct execute，生产接入尚未开放。
- 没有实现执行超时 cleanup job、历史状态筛选 UI、更新/删除前样例、trace_id/request_id 展示、最大影响行数阈值和 DDL allowlist 细化。

### 2.6 DB-MySQL-1 MySQL 真实只读验证（历史阶段）

DB-MySQL-1 当时的真实数据库验证限定为 MySQL 只读链路，不顺手打开写入、删除或 DDL。这个边界是 DB-MySQL-1 的历史阶段边界，不是当前 DB-MySQL-3 的永久产品边界。

MySQL 验证目标：

- 使用真实 MySQL 数据源验证 L1/L2 能力，而不是继续只在 SQLite sandbox 上证明。
- 保持 `ToolGateway -> PermissionService -> DatabaseProvider -> SQL Kernel -> audit` 的治理链路。
- 使用只读 MySQL 账号或只读连接策略。
- 只允许 `list_tables`、`describe_table`、`safe_select` 等只读工具。
- 表、列、数据库资源必须进入 allowlist 和权限模型。
- DML / DDL / 权限管理 SQL 仍然直接阻断。

MySQL 接入方式：

- MySQL provider 与现有 `DatabaseDemoToolProvider` 共存，不替代 sandbox provider。
- sandbox 继续使用 `database_id=sandbox_sales` 和 `database_demo.*` resource_id。
- MySQL 第一版使用独立 `database_id`，例如 `mysql_sales_readonly`，tool resource_id 也必须带来源前缀，例如 `database_mysql.sales.safe_select`，不能复用 `database_demo.safe_select`。
- `database_id` 是权限、审计、allowlist 和 operation resource 的边界；两个 provider 不得共享同一个 `database_id`。
- 真实 MySQL 工具仍通过 `ToolGateway.execute()` 调用，不进入默认 MCP 工具池。
- `POST /api/database/safe-select` 使用可选 `database_id` 分发；不传时默认保持 C2 的 `sandbox_sales` 行为。
- MySQL 第一版采用独立 `MySqlSafeSqlKernel`，不在 DB-MySQL-1 阶段重构 SQLite `SafeSqlKernel`。
- MySQL 连接必须有小型连接池或可注入 connector，避免每个请求无界创建连接。

当前 DB-MySQL-1 代码落点：

- `app/enterprise/database/mysql.py` 新增 `DatabaseMySqlToolProvider`，暴露 `database_mysql.<database_id>.list_tables`、`describe_table`、`safe_select` 三个只读工具。
- `MySqlSafeSqlKernel` 使用 MySQL dialect 解析，只允许单条非锁定 SELECT，继续阻断 DML、DDL、超限 `LIMIT`、`SELECT *`、JOIN、子查询和函数。
- `MySqlSafeSqlKernel` 在返回前把 MySQL `DECIMAL` 等非 JSON 原生值转成 JSON-safe 值；金额类 `Decimal` 以字符串返回，避免精度丢失和 HTTP 序列化失败。
- `PooledMySqlReadonlyConnector` 使用 PyMySQL 懒连接和固定小池，每次执行包在 `START TRANSACTION READ ONLY` / `COMMIT` 中，异常时 rollback。
- `app/config.py` 增加 `enterprise_mysql_*` 配置；只有 `enterprise_mysql_enabled=true` 且 host/database/username/allowlist 完整时，`app/enterprise/database/routes.py` 的默认 database gateway 才附加 MySQL provider。
- `POST /api/database/safe-select` 已支持可选 `database_id` 分发；不传仍走 `sandbox_sales`，传未知 id 不回落到 sandbox。
- `app/enterprise/admin/resources.py` 已把启用的 MySQL allowlist 纳入 admin resource catalog，使 `/api/admin/resources` 和 `/api/admin/grants` 能看到 `database_mysql.<database_id>.*`、`database_table`、`database_column` 资源；grant validator 仍保持 `resource_exists` 校验。

本地 Docker MySQL live smoke 已验证：

- 使用本地 MySQL 8.0 容器、`sales.orders` allowlist 和只读账号。
- admin 可通过 `/api/admin/grants` 授权 `demo_user_dept1` 的 MySQL tool/table/column 只读资源。
- 未授 DB tool 的账号调用 MySQL `safe_select` 返回 403 `default_deny`。
- 授权用户查询 `order_id,total_amount` 返回 200，`DECIMAL` 值以字符串返回。
- 未授权列返回 403 `database_column_denied`，未知表返回 403 `unauthorized_table`。
- `UPDATE`、`DROP TABLE` 和 `SELECT ... FOR UPDATE` 返回 403，并写入 MySQL `database_query` audit。

DB-MySQL-1 只读验证不做：

- 不接生产写库。
- 不开放 `INSERT`、`UPDATE`、`DELETE`、`DROP TABLE`；这不是永久边界，后续 DB-MySQL-2/3 已在非生产 MySQL 上推进 writable 切片。
- 不把 MySQL tool 放入默认 MCP 工具池。
- 不把 SQLite 的 dry-run / 事务行为直接搬到 MySQL。
- 不承诺生产 MySQL L3-L5 已经可用。

## 3. 操作分级

| 分级 | 操作 | 示例 | 是否需要确认 | 无权限时 |
|---|---|---|---|---|
| L1 只读查询 | 查询数据 | `SELECT`、条件查询、排序、分页、聚合、JOIN、业务明细查询 | 不需要 | 直接拒绝 |
| L2 元数据查看 | 查看结构和执行信息 | 库/表列表、表结构、字段类型、索引、表大小、行数、`EXPLAIN`、慢查询、连接数、锁等待 | 不需要 | 直接拒绝 |
| L3 写入/修改 | 改变数据但不删除 | `INSERT`、`UPDATE`、批量导入、数据修复、状态回填 | 不需要；有权限后直接执行并审计 | 直接拒绝 |
| L4 删除类操作 | 删除数据或删除结构 | `DELETE`、`TRUNCATE`、`DROP TABLE`、`ALTER TABLE DROP COLUMN` | 需要用户后台确认 | 直接拒绝 |
| L5 表结构变更 | 非删除类 DDL | `CREATE TABLE`、`ALTER TABLE ADD COLUMN`、修改字段类型、新增/删除索引、重命名表/字段 | 不需要；有 ddl 权限后直接执行并审计 | 直接拒绝 |
| M1 权限管理 | 管理用户和资源权限 | 授权、撤权、角色、部门 scope、资源 scope | 管理员后台处理 | 直接拒绝 |

## 4. 权限和确认规则

数据库操作只看一类操作权限：

```text
database_operation / <database_id>.<operation_type> / execute
```

其中 `database_update`、`database_delete`、`database_ddl` 只是语义标签或计划阶段简称，不是当前权限系统里的独立平行模型。真正落地时，仍应回到 `database_operation` 这一类资源。

例如：

- `database_operation/sandbox_sales.update/execute`
- `database_operation/sandbox_sales.delete/execute`
- `database_operation/sandbox_sales.ddl/execute`

规则如下：

- 没有对应 `database_operation` 权限时，直接返回无权限。
- 有对应 `database_operation` 权限时，非删除写操作和非删除 DDL 可直接执行并审计。
- 有对应 `database_operation` 权限时，删除类操作才允许进入用户后台确认流。
- 用户后台确认只负责“确认执行”，不负责授予权限。
- 如果某个操作需要先走 Stage 5 的权限申请，那么申请和批准仍属于权限管理后台，用户后台确认不替代 grant/revoke，也不替代 F6 HITL 审批边界。
- MySQL DB-MySQL-3 第一切片把非生产 MySQL `INSERT` / `UPDATE` 改为直接执行；`DELETE` 继续确认。DB-MySQL-4 已把非生产 MySQL 非删除 DDL 改为直接执行，删除类 DDL 继续确认；生产库写入、删除和 DDL 仍未开放。

多表 SQL 按最小授权面判断：

- 写入、删除或 DDL 的目标表，必须同时拥有对应 `database_operation` 权限。
- `SELECT`、`JOIN`、子查询、`WHERE`、`RETURNING` 中引用到的表和列，仍必须满足只读表 / 列权限。
- 触及未授权列时直接拒绝，不因为主表有权限就放行。

不要再额外设计一套“审批权限”。确认动作是该操作权限的一部分：

```text
有对应 database_operation 权限 + 非删除操作
  -> 后端复核表列范围
  -> 直接执行并审计

有对应 database_operation 权限 + 删除类操作
  -> 可以进入确认流
  -> 在后台确认
  -> 后端复核
  -> 执行并审计

没有对应 database_operation 权限
  -> 直接拒绝
  -> 不进入确认流
```

## 5. 用户后台和管理员后台边界

### 5.1 用户后台

用户后台用于处理自己有权限执行但需要显式确认的删除类数据库操作。

适用范围：

- `DELETE`
- `TRUNCATE`
- `DROP TABLE`
- `ALTER TABLE DROP COLUMN`

不适用范围：

- `INSERT`
- `UPDATE`
- `CREATE TABLE`
- 非删除类 `ALTER TABLE`
- `CREATE INDEX`
- `DROP INDEX`
- `RENAME TABLE`
- `RENAME COLUMN`
- 批量导入
- 数据修复和回填

用户后台只展示需要显式确认的删除类操作，至少应包含：

- SQL 摘要。
- 操作类型。
- 数据源、schema、表、列。
- 预估影响行数。
- dry-run 结果。
- 删除前的样例行或对象摘要。
- 风险等级。
- 请求人、trace_id、request_id。
- SQL hash 和参数 hash。

确认后执行前必须重新校验：

- 当前用户仍拥有该操作权限。
- SQL hash 和参数 hash 没有变化。
- 目标数据源、表、列仍在授权范围内。
- dry-run 结果没有超过后端阈值。
- 操作没有过期或被重复使用。

确认项生命周期必须显式管理：

- `pending -> confirmed -> executing -> executed / failed`
- `cancelled` 和 `expired` 是侧支状态，不得混成“已确认但未处理”
- 过期项应由定时清理任务标记为 `expired`，默认列表里隐藏，但审计和保留期仍需保留
- 执行失败必须落到 `failed`，不能长期卡在 `executing`
- 如果执行失败时结果不确定，应重新复核后再发起新的确认项，而不是复用旧的 `confirmation_id`

### 5.2 管理员后台

管理员后台用于权限管理和系统治理，不处理普通用户自确认的数据库操作。

适用范围：

- 授权。
- 撤权。
- 用户角色。
- 部门 scope。
- 资源 scope。
- 数据库操作权限本身的分配和回收。

管理员后台的动作仍然必须审计，但它是管理动作，不是数据库操作确认动作。

### 5.3 dry-run 方案

dry-run 不是统一真理，不同数据库方言要分别说明边界：

- 第一版 L3-L5 用户可见 dry-run 不把“执行后 rollback”作为默认方案；rollback 型预演只允许留在隔离测试或 sandbox 实验里，不能作为真实 MySQL 或用户可见影响评估。
- SQLite sandbox 如果为了测试使用 `BEGIN ... ROLLBACK`，必须标记为 sandbox-only，并说明可能触发 trigger、锁、自增 ID 消耗或其他副作用，不能描述成“无副作用 dry-run”。
- DB-MySQL-1 真实验证阶段只做 L1/L2 只读验证；DB-MySQL-2 非生产可写阶段已用 read-only preview 支持 UPDATE/DELETE 的 prepare 摘要。
- 当前 `SafeSqlKernel` 是 SQLite sandbox kernel，`_parse_one` 固定使用 SQLite 方言；MySQL 不能直接复用这个方言设置。
- MySQL 只读阶段应抽出 dialect-aware read-only kernel，或新增 `MySqlSafeSqlKernel`，但两者都必须保留同一条 ToolGateway / PermissionService / audit 链路。
- MySQL L3-L5 preview 只允许 read-only 路径：AST 分析、allowlist 检查、`SELECT COUNT(*)` 估算、schema metadata 摘要、`EXPLAIN FORMAT=JSON` 计划信息。
- `EXPLAIN` 只能作为计划预览，不能冒充实际影响行数。
- `UPDATE` / `DELETE` 的 `COUNT(*)` preview 只能估算直接命中的目标行，不能覆盖 trigger、cascade、外键连带影响、索引维护或锁等待。
- `INSERT ... VALUES` 的估算以 values 行数为准；`INSERT ... SELECT` 只有在 source SELECT 可被只读 kernel 安全验证时才给 count preview。
- DDL 的 dry-run 只能给 schema diff / 风险摘要，不能伪装成 affected_rows。
- 如果无法可靠估算，就明确标记“无法可靠估算”，不要展示伪精确值。
- DB-Ops-6 首个实现切片应优先在 sandbox / 非生产 writable fixture 上验证 L3-L5；真实 MySQL 写入、删除和 DDL 需要非生产 writable MySQL、备份/恢复说明、数据 owner、operation resource 和 smoke 计划齐备后才能打开。

dry-run 摘要至少包含：

```text
estimated_affected_rows
estimate_reliable
estimate_method
estimate_reason
estimate_notes
plan_summary
schema_impact
sample_before_rows
max_allowed_affected_rows
```

### 5.4 confirmation 生命周期方案

用户后台确认项第一版必须持久化，不允许只靠内存或前端状态维持。确认项默认状态机：

```text
pending
confirmed
cancelled
expired
executing
executed
failed
```

锁定规则：

- `pending` 默认 15 分钟过期，记录 `expires_at`；过期后不能 confirm。
- cleanup job 把超时 `pending` 标记为 `expired`，不是静默删除。
- confirm 必须用原子条件更新抢占 `pending`，防止重复点击、并发请求或重放造成二次执行。
- `executing` 必须有 `execution_deadline_at`，默认 2 分钟；超时仍未完成时标记为 `failed`。
- `cancelled`、`expired`、`executed`、`failed` 都是终态，不能再次 confirm。
- failed confirmation 默认不能复用；重试必须重新 prepare。
- confirmation 记录必须包含 SQL hash、参数 hash、`sql_hash_version`、`normalization_version`、dry-run 摘要、权限快照、trace_id 和 request_id。
- confirm 前必须重新校验 owner、operation 权限、table/column 权限、allowlist、SQL hash、参数 hash、dry-run 摘要和过期状态。
- confirmation cleanup 不能删除 audit；audit retention 和 confirmation retention 分开配置。

## 6. 删除类操作

删除类操作单独列为 L4，因为它的恢复成本高，即使用户有权限，也不能在聊天或普通 API 中直接执行。

删除类操作包括：

- `DELETE`
- `TRUNCATE`
- `DROP TABLE`
- `ALTER TABLE DROP COLUMN`

处理规则：

1. 后端识别为删除类操作。
2. 检查用户是否有对应 `database_operation/<database_id>.delete/execute` 权限。
3. 没有权限时直接拒绝。
4. 有权限时生成用户后台确认项，但不执行。
5. 用户进入后台确认。
6. 后端复核 SQL hash、权限、目标和 dry-run 摘要。
7. 执行操作。
8. 写入完整审计。

`DROP TABLE` 不走管理员审批。用户有对应 `database_operation/<database_id>.delete/execute` 权限时，走用户后台确认；没有该权限时直接拒绝，不生成确认项。

## 7. 执行流

### 7.1 只读查询

```text
用户请求
  -> 识别为 L1 / L2
  -> 检查 tool/table/column 权限
  -> SQL AST / allowlist / LIMIT / timeout 校验
  -> 执行
  -> 审计
  -> 返回结果
```

### 7.2 非删除写入 / 非删除 DDL

```text
用户请求
  -> 识别为 L3 或非删除类 L5
  -> 检查对应 database_operation 权限
  -> 无权限：直接拒绝
  -> 有权限：后端复核表列范围、allowlist 和 SQL hash
  -> 直接执行
  -> 审计
  -> 返回结果
```

### 7.3 删除类操作

```text
用户请求
  -> 识别为 L4 删除类
  -> 检查 database_operation/<db>.delete/execute 权限
  -> 无权限：直接拒绝，不生成确认项
  -> 有权限：生成确认项
  -> 用户后台展示确认项
  -> 用户确认
  -> 后端复核权限、SQL hash、参数 hash、目标范围、dry-run 摘要
  -> 执行
  -> 审计
  -> 返回结果
```

### 7.4 权限管理

```text
管理员进入管理员后台
  -> 执行授权 / 撤权 / 角色 / 部门 scope / 资源 scope 管理
  -> 后端校验管理员身份和管理权限
  -> 执行
  -> 审计
```

## 8. 审计要求

所有数据库操作都必须审计。

只读审计至少记录：

- user_id
- trace_id
- request_id
- operation_type
- database_id
- table_ids
- column_ids
- SQL hash
- row_count
- elapsed_ms
- decision
- denied_reason

非删除写入和非删除 DDL 额外记录：

- operation resource id
- actual_affected_rows
- SQL hash
- SQL hash version
- hash normalization version
- parameter hash

删除类操作额外记录：

- confirmation_id
- confirmed_at
- dry_run_summary
- estimated_affected_rows
- actual_affected_rows
- before_sample_hash
- after_sample_hash
- rollback_reference，如果存在
- SQL hash
- SQL hash version
- hash normalization version
- parameter hash

确认项清理和审计保留要分开：

- confirmation 记录可以按 TTL 清理，但 audit 不能跟着一起删
- audit retention 应单独配置，至少覆盖 confirmation 生命周期和排障窗口
- cleanup 任务本身也要写审计，避免“为什么消失了”无法追踪

权限管理审计单独记录为管理动作，不混入普通数据库操作确认流。

## 9. 非目标

本方案不做：

- 不把数据库工具加入默认 MCP 工具池。
- 不让无权限用户通过审批绕过权限。
- 不把权限管理开放给普通用户后台。
- 不把删除操作做成聊天里一句“确认”就执行。
- 不用前端 `confirm=true` 作为安全依据。
- 不把写操作接入当前 `safe_select` route。
- 不在 DB-MySQL-1 只读验证阶段开放写入、删除或 DDL。
- 不接真实生产写库，除非后续另有数据库连接、回滚、备份和 owner 方案。

## 10. 验证用例

后续实现时至少覆盖：

1. 有只读权限的用户执行 `SELECT` 成功。
2. 无表权限用户执行 `SELECT` 返回无权限。
3. 无列权限用户执行 `SELECT` 返回无权限。
4. 有 `database_operation/<db>.update/execute` 权限的用户执行 MySQL `UPDATE` / `INSERT` 时直接执行并审计，不生成确认项。
5. 无 `database_operation/<db>.update/execute` 权限的用户执行 MySQL `UPDATE` / `INSERT` 直接无权限，不生成确认项。
6. 有 `database_operation/<db>.delete/execute` 权限的用户执行 `DELETE` 时生成后台确认项，不立即执行。
7. 无 `database_operation/<db>.delete/execute` 权限的用户执行 `DELETE` 直接无权限，不生成确认项。
8. 有 `database_operation/<db>.delete/execute` 权限的用户执行 `DROP TABLE` 时生成后台确认项，不立即执行。
9. 有 `database_operation/<db>.ddl/execute` 权限的用户执行 MySQL `CREATE TABLE` / `ALTER TABLE ADD COLUMN` / `CREATE INDEX` / `DROP INDEX` 时直接执行并审计，不生成确认项。
10. 无 `database_operation/<db>.ddl/execute` 权限的用户执行 MySQL 非删除 DDL 直接无权限，不生成确认项。
11. 多表 `SELECT ... JOIN ... WHERE ...` 触及未授权列时直接拒绝。
12. 用户确认时 SQL hash 被改，后端拒绝执行。
13. 用户确认时权限已被撤销，后端拒绝执行。
14. confirmation 过期后不能确认，并且会被清理任务标记为 `expired`。
15. 执行失败会落到 `failed`，不会长期卡在 `executing`。
16. 管理员在管理员后台授权 / 撤权成功并写审计。
17. 普通用户不能访问管理员后台权限管理 API。

## 11. 一句话结论

数据库操作能力按 `database_operation/<database_id>.<operation_type>/execute` 权限控制：只读直接执行；非删除写操作和非删除 DDL 有权限后直接执行并审计；删除类操作由拥有对应 delete operation resource 的用户在自己的后台确认后执行；没有对应权限直接拒绝。授权、撤权、角色和部门 scope 是管理员后台的专职管理能力，不进入普通用户的数据库操作确认流。
