# 企业助手开发计划 2.0 - 详细设计

日期: 2026-05-30

状态: 可执行详细设计。适用于 E0-E11 全部验收完成之后的 2.0 改进阶段。

本文是 `docs/企业开发计划2.0.md` 的执行版。2.0 阶段的核心不是多智能体，而是把企业助手补成“可约束、可评估、可恢复、可审批、可度量”的系统。

## 1. 设计原则

1. **先不做多智能体**
   F1-F8 都在单 Agent / 单流程治理框架内完成，不引入 Coordinator、专业 Agent 群、A2A、CrewAI 或 AutoGen 主线依赖。

2. **详细设计必须自包含**
   本文档不依赖短期生成目录、外部草稿或生成中间文件。后续实现以本文和 `docs/企业开发计划2.0.md` 为准。

3. **先评估和边界，再做智能化**
   先落 F2a 轨迹评估骨架、F1 任务合同、F2b 合同感知评估，再落 F4/F5/F6。F3/F7/F8 不进入默认热路径，除非满足触发条件。

4. **沿用现有企业边界**
   新代码优先放在 `app/enterprise/*`，旧 RAG/AIOps/DB 逻辑通过 adapter 接入。不要为了 2.0 大规模搬迁 `app/services/*` 或旧 agent 节点。

5. **审计和权限接口按当前项目形态设计**
   审计事件通过 `AuditService.record(AuditEvent(...))` 写入。权限检查通过 `PermissionService.check(context, resource_type=..., resource_id=..., action=...)`。详细设计中的伪代码不能绕过这两个边界。

6. **每个能力先做 MVP 切片**
   每个 F 项都必须有可单独验收的最小闭环。大而全能力只能作为后续扩展，不作为第一版完成标准。

7. **每次改动都要有验证命令**
   实现阶段至少跑目标测试、`compileall`、相关 `ruff check`、`git diff --check`。计划阶段至少检查文档无短期路径、无未完成标记、命名一致。

8. **每个小阶段都要 Git 收口**
   F2a、F1、F2b、F4、F5、F6、F3、F7、F8 每个阶段完成后，都必须在当前 2.0 分支上完成 git 收口: 实现提交记录源码/测试变更，收口提交记录验收结果和状态文档，最终 `git status --short` 为空。

## 2. 推荐执行顺序

| 顺序 | 阶段 | 优先级 | 目标 | 推荐工期 | 是否进入默认路径 |
|---|---|---|---|---:|---|
| 1 | F2a 轨迹评估骨架 | P0 | 建立 trace 提取、matcher、基础 eval runner | 3-4 天 | 否 |
| 2 | F1 任务合同化 MVP | P0 | 为复杂任务建立 scope、成功标准、风险等级 | 4-6 天 | 仅复杂任务 |
| 3 | F2b 合同感知评估 | P0 | 用 eval 验证合同、权限、工具路径是否合规 | 3-4 天 | 否 |
| 4 | F4 结构化自检 MVP | P1 | 先做 Plan/Citation/SQL 三类 verifier | 5-7 天 | 受控接入 |
| 5 | F5 统一失败处理 | P1 | 统一 error_class、恢复决策、SSE 错误事件 | 6-8 天 | 是 |
| 6 | F6 Human-in-the-loop MVP | P1 | 高风险任务进入人工审批和审计 | 4-6 天 | 高风险路径 |
| 7 | F3 策略路由 Shadow | P2 | 路由器只旁路评分，不改变主路径 | 3-5 天 | 否 |
| 8 | F7 高级 Guardrail | P2 gated | 有合规触发后做 PII/output shadow | 6-10 天 | 默认否 |
| 9 | F8 资源感知优化 | P2 gated | 有成本/延迟数据后做预算驱动策略 | 6-10 天 | 默认否 |

关键调整:

- F2 不再一次性做 5 个 evalset。先做 F2a，再做 F1，再补 F2b。
- F3 虽然实现量不大，但必须等 F2/F1/F5 有基础数据后再 shadow。
- F7/F8 是触发式 backlog，不是固定排期任务。

## 3. 通用验收出口

每个 F 项完成时必须同时满足:

- 功能有目标测试，失败场景有负例。
- 关键事件写入 audit，能通过 `trace_id` / `request_id` 关联。
- SSE 事件不破坏 `docs/enterprise_sse_event_contract.md` 的既有约定。
- 新增配置有默认值，且本地开发不依赖云服务。
- 变更记录写入 `docs/enterprise_capability_development_record.md`；涉及计划顺序或路线调整时，同步更新 `PROJECT_STATE.md` 和开发记录。
- 不修改无关主线，不把 DB tools 放回默认 AIOps/RAG 工具池。
- Git 收口完成: 至少有实现提交和阶段收口提交；收口提交必须包含验收结果、验证命令、已知缺口或明确无缺口；完成后 `git status --short` 为空。

### 目标

### 数据模型

`ExpectedTrajectory` 第一版只描述稳定的执行事实，预留合同字段但不依赖 F1:

```json
{
  "eval_id": "chat_auth_doc_blocked_001",
  "input": {
    "route": "chat_stream",
    "question": "查询未授权文档"
  },
  "expected": {
    "final_status": "blocked",
    "required_stages": ["gateway", "guardrail", "permission"],
    "forbidden_tools": ["database-demo"],
    "required_audit_events": ["permission_check", "request_blocked"],
    "sse": {
      "must_include_trace_id": true,
      "allowed_event_types": ["stage", "content", "error", "done"]
    }
  }
}
```

### 执行步骤

1. 定义 `ExpectedTrajectory`、`ActualTrajectory`、`TrajectoryMismatch`、`TraceEvalResult`。
2. 实现 `AuditTraceExtractor`，优先从现有 SQLite/JSONL audit 中按 `trace_id` 提取事件。
3. 实现 `TrajectoryMatcher`，只做确定性比较: stage 是否出现、顺序是否合理、工具是否越权、阻断是否发生在预期层。
4. 实现统一 runner: 输入 evalset，提取实际 trace，输出 JSON 报告和 markdown 摘要。
5. 建立 3 个最小 evalset: chat/RAG、AIOps、SSE 协议。
6. 加目标测试，覆盖模型校验、matcher、extractor、报告输出。

### 验收标准

- 能离线运行，不依赖外部模型。
- 能输出 pass/fail/mismatch 分类统计。
- 至少能识别三类错误: 缺 audit 事件、错误工具调用、SSE 缺 trace_id。
- 不改变任何用户请求路径。
- 报告中能定位到 `trace_id`、`request_id`、失败类别和 mismatch 原因。
- Git 收口完成: `enterprise2` 分支包含 F2a 实现提交和 F2a 收口提交，收口提交记录目标测试、eval runner、`git diff --check` 结果，完成后工作树干净。

## 5. F1: 任务合同化 MVP

### 目标

把复杂任务从一句 prompt 升级成可验证的任务合同，明确任务范围、允许资源、成功标准、风险等级、预算约束和人工审批需求。

F1 第一版只覆盖复杂任务，不覆盖普通聊天。

### 依赖

- 依赖 E0-E11 的 Gateway、PermissionService、AuditService、SSE 合同。
- 依赖 F2a 提供基础 trace 评估，但不依赖 F2b。

### 范围

新增:

- `app/enterprise/tasks/models.py`
- `app/enterprise/tasks/repository.py`
- `app/enterprise/tasks/validator.py`
- `app/enterprise/tasks/service.py`
- `tests/test_enterprise_task_contract.py`

可选新增:

- `app/api/tasks.py`，只提供查询合同状态和审计定位的只读接口。审批接口留给 F6。

修改:

- `app/config.py`: 新增 `enterprise_task_contract_sqlite_path`，默认 `logs/enterprise_task_contracts.sqlite`。
- `app/enterprise/adapters/aiops_adapter.py`: 复杂 AIOps 任务创建合同并把 `task_contract_id` 写入执行上下文。
- `docs/enterprise_capability_development_record.md`

不修改:

- 不直接重写 planner/executor/replanner。
- 不把普通 `/api/chat` 强制合同化。
- 不在合同层绕过 PermissionService 或 ToolGateway。

### 合同字段

```json
{
  "task_id": "task-xxx",
  "trace_id": "trace-xxx",
  "request_id": "request-xxx",
  "user_goal": "诊断某服务告警并生成报告",
  "scope": {
    "allowed_data_sources": ["kb-prod-runbook"],
    "allowed_tools": ["retrieve_knowledge", "get_current_time"],
    "forbidden_actions": ["write_db", "delete_file", "restart_service"]
  },
  "success_criteria": [
    "说明告警现象",
    "列出证据来源",
    "给出不超过 3 条低风险建议"
  ],
  "risk_level": "medium",
  "requires_human_approval": false,
  "latency_budget_ms": 30000,
  "cost_budget": null,
  "expected_outputs": ["diagnostic_report"],
  "status": "pending|approved|running|completed|failed|rejected"
}
```

### 执行步骤

1. 定义 `TaskContract`、`TaskScope`、`TaskStatus`、`RiskLevel`。
2. 实现 SQLite repository，支持 create/get/update_status/list_by_trace。
3. 实现 `ContractValidator`:
   - 调用 `PermissionService.check(context, resource_type=..., resource_id=..., action=...)` 校验资源。
   - 校验高风险任务必须进入审批。
   - 校验 `forbidden_actions` 与允许工具不冲突。
4. 实现 `TaskContractService`:
   - 创建合同。
   - 记录 `task_contract_created` / `task_contract_rejected` audit。
   - 返回结构化失败原因。
5. 在 AIOps adapter 的复杂任务入口接入合同:
   - 简单 AIOps 请求保持原路径。
   - 复杂任务写入 `task_contract_id`。
   - 合同不通过时返回 SSE `error`，不进入 planner。
6. 目标测试覆盖合同创建、权限拒绝、高风险审批、audit 记录、普通聊天不受影响。

### 验收标准

- 复杂任务能生成合同并持久化。
- 未授权数据源会被合同验证阻断。
- 高风险任务不会在未审批状态下进入执行。
- audit 中能通过 `trace_id` 找到合同创建/拒绝事件。
- 现有普通聊天、普通 RAG、普通 AIOps smoke 不受影响。
- Git 收口完成: `enterprise2` 分支包含 F1 实现提交和 F1 收口提交，收口提交记录合同化验收、回归测试和普通聊天/AIOps 不受影响证据，完成后工作树干净。

## 7. F4: 结构化自检器 MVP

### 目标

在关键输出前加入可控自检，提高 plan、citation、SQL 结果、报告可靠性。自检结果写入 trace，但不记录长链式思维。

### 第一版范围

先做 3 个 verifier:

- `PlanVerifier`: 检查 plan 是否覆盖合同目标、步骤是否过多、是否超 scope。
- `CitationVerifier`: 检查 citation 是否来自授权 source_ref。
- `SqlResultVerifier`: 检查 SQL 是否经过 SafeSqlKernel，结果列是否授权。

后置 verifier:

- `ReportVerifier`: 等 F2b 的 success criteria 评估稳定后接入。
- `GuardrailVerifier`: 等 F7 provider shadow 数据稳定后接入。

### 新增模块

- `app/enterprise/verifiers/models.py`
- `app/enterprise/verifiers/base.py`
- `app/enterprise/verifiers/plan.py`
- `app/enterprise/verifiers/citation.py`
- `app/enterprise/verifiers/sql.py`
- `app/enterprise/verifiers/service.py`
- `tests/test_enterprise_verifiers.py`

### 输出模型

```json
{
  "verifier": "CitationVerifier",
  "status": "passed|failed|needs_revision",
  "findings": [
    {
      "code": "citation_source_not_authorized",
      "message": "引用来源不在授权文档集合内"
    }
  ],
  "revision_required": false,
  "max_revision_attempts": 1
}
```

### 执行步骤

1. 定义 `VerificationResult`、`VerificationFinding`、`VerificationStatus`。
2. 实现 `BaseVerifier` 和 `VerificationService`。
3. 实现 `PlanVerifier`，第一版只做确定性规则，不调用 LLM。
4. 实现 `CitationVerifier`，复用现有 `source_ref` 作为结构化合同。
5. 实现 `SqlResultVerifier`，只接入 DB sandbox 路径。
6. 在 adapter 层写入 verifier audit 事件，不直接改旧 planner 内部。
7. 限制修订次数为 1，失败后返回结构化错误或进入 F6 审批。

### 验收标准

- verifier 失败不会吞掉原始错误。
- verifier 结果能按 `trace_id` 查询。
- `CitationVerifier` 只信结构化 `source_ref`，不信展示文本。
- `SqlResultVerifier` 能识别未通过 SafeSqlKernel 的结果。
- 自检不会形成无限循环。
- Git 收口完成: `enterprise2` 分支包含 F4 实现提交和 F4 收口提交，收口提交记录 verifier 目标测试、RAG/DB 回归和自检边界，完成后工作树干净。

## 8. F5: 统一失败处理与恢复机制

### 目标

把失败从“抛异常或返回 generic error”升级为“可解释、可恢复、可审计、UI 可展示”。

### 范围

新增:

- `app/enterprise/errors/models.py`
- `app/enterprise/errors/exceptions.py`
- `app/enterprise/errors/recovery.py`

修改:

- `app/enterprise/gateway/request_gateway.py`

- `app/enterprise/tools/gateway.py`

### ErrorClass

| error_class | 默认决策 | 说明 |
|---|---|---|
| `auth_failed` | abort | 身份无效，不能自动恢复 |
| `permission_denied` | abort | 权限阻断，不能重试绕过 |
| `guardrail_blocked` | abort | 安全阻断，不能自动绕过 |
| `model_unavailable` | retry/fallback | 模型超时或不可用 |
| `tool_failed` | retry/partial/abort | 工具失败，按工具风险决定 |
| `retrieval_low_confidence` | partial/request_more_info | 检索不足 |
| `sql_blocked` | abort | 危险 SQL 阻断 |
| `stream_interrupted` | recoverable_error | SSE 中断，支持按 trace 查历史 |

### SSE 错误事件

```json
{
  "type": "error",
  "trace_id": "trace-xxx",
```

## 9. F6: Human-in-the-loop MVP

### 目标

高风险、低置信度、需要审批的任务进入人工审批，不让 Agent 自主完成。

### 依赖

- 依赖 F1 的 `TaskContract.risk_level` 和 `requires_human_approval`。
- 依赖 F5 的结构化错误与恢复决策。

### MVP 边界

第一版只做“阻断、登记、审批、审计”。不做透明恢复复杂运行时状态。

审批通过后的执行方式:

- 第一版: 用户或后台用 `review_id` / `task_id` 重新提交同一任务，系统识别已审批合同。
- 后续扩展: 引入 checkpointer resume，实现原 trace 内恢复。

### 新增模块

- `app/enterprise/reviews/models.py`
- `app/enterprise/reviews/repository.py`
- `app/enterprise/reviews/risk_detector.py`
- `app/enterprise/reviews/service.py`
- `app/api/admin_reviews.py`
- `tests/test_enterprise_human_review.py`

### 触发条件

- DB 写操作请求。
- 高敏文档访问。
- 大范围授权变更。
- 输出包含疑似 PII。
- AIOps 低置信度且建议影响生产操作。
- task contract 超出用户权限或风险等级为 high/critical。

### 执行步骤

1. 定义 `HumanReviewRequest`、`HumanReviewDecision`、`ReviewStatus`。
2. 实现 `RiskDetector`，只用确定性规则和 F1/F5 上下文。
3. 实现 repository，支持 pending/list/get/approve/reject。
4. 实现 Admin API:
   - `GET /api/admin/reviews/pending`
   - `POST /api/admin/reviews/{review_id}/approve`
   - `POST /api/admin/reviews/{review_id}/reject`
5. 在高风险路径返回 SSE `pending_approval`，不执行工具。
6. 审批动作写 audit，包含审批人、原因、task_id、trace_id。

### 验收标准

- 高风险任务在审批前不会调用工具。
- pending review 能被 Admin 查询。
- approve/reject 都写 audit。
- 非 Admin 不能审批。
- 拒绝后同一 task 不会被继续执行。
- Git 收口完成: `enterprise2` 分支包含 F6 实现提交和 F6 收口提交，收口提交记录审批 API、Admin 权限保护、audit 和拒绝后不继续执行证据，完成后工作树干净。

2026-05-31：F6 已完成实现并收口。实现提交 `814d9cc enterprise2(f6): add human review mvp`。F6 目标测试覆盖 `tests/test_enterprise_human_review.py` 6/6，受影响 admin/task/gateway 回归 26/26，`tests/test_enterprise_*.py` 全部通过，targeted `ruff check`、`compileall -q app tests`、`make deps-check` 和 `git diff --check` 均通过。F6 只做阻断、登记、审批、审计；审批通过后的恢复采用 `review_id` / `task_id` 重新提交同一任务，不引入 checkpointer resume，也不把审批做成聊天里的临时确认句。

## 10. F3: 策略路由 Shadow

### 目标

为 RAG、AIOps、DB、Admin、普通聊天、人工审批建立可解释的路由决策，但第一版只 shadow，不改变当前主路径。

### 触发条件

### 路由输出

```json
  "risk_level": "low|medium|high",
```

```text
F2a 轨迹评估骨架
```
