# 企业助手开发计划 2.0

日期: 2026-05-30

状态: 后续改进计划。适用前提是当前企业助手待办主线已经全部完成。

> 适用前提: 本文不是 E6-E11 的执行计划。本文假设 E0-E11 已全部完成，也就是身份、RequestGateway、权限、ToolGateway、ModelGateway、RAG/Upload 治理、sandbox DB、DB Gateway、Admin/API、Observability/Eval、Vue3 执行过程可视化都已经验收完成。本文回答的问题是: 对照《智能体设计模式》这本书，项目完成当前全部待办后，还需要怎么继续改进。

## 1. 总结结论

当前全部待办完成以后，项目已经具备企业助手的基础闭环:

```text
身份认证
  -> 请求网关
  -> 权限/资源注册
  -> 工具/模型网关
  -> RAG / AIOps / DB 能力
  -> 审计/Trace/Eval
  -> Vue3 执行过程可视化
```

对照《智能体设计模式》，完成上述闭环后，下一阶段最值得补的不是“多智能体”，而是以下能力:

1. **任务合同化**: 把复杂任务从一句 prompt 升级为可验证的任务合同。
2. **轨迹评估**: 不只看最终答案，要评估执行路径、工具选择、阻断原因和阶段顺序。
3. **策略路由**: 用受控路由决定走 RAG、DB、AIOps、普通回答还是人工确认。
4. **反思与自检**: 加入有边界的 plan/report/citation/sql 自检，不暴露或依赖长链式思维。
5. **异常恢复**: 为模型、工具、检索、DB、SSE 中断建立统一恢复策略。
6. **Human-in-the-loop**: 高风险操作和低置信度结果进入人工确认。
7. **资源感知优化**: 模型、工具、检索、DB 查询都有成本、延迟和优先级预算。
8. **高级 Guardrail**: 在已有规则 provider 之上，按真实合规需求渐进加入 PII、输出检查或 LLM Judge shadow。

明确暂缓:

- **先不做多智能体。**
- 不做 Coordinator + 多个专业 Agent。
- 不拆 LogAnalyzer / MetricAnalyzer / RootCauseAgent / ReportAgent。
- 不引入 A2A / CrewAI / AutoGen 作为主线依赖。

多智能体不是 2.0 的默认方向，只作为未来单独研究项。

## 2. PDF 对照后的能力差距

| 书中模式 | 当前全部待办完成后的状态 | 仍需改进 |
|---|---|---|
| 提示链 / 规划 | AIOps 已有 planner/executor/replanner，RAG/DB/Admin 有固定流程 | 复杂任务还缺“合同化输入/输出”和任务验收条件 |
| 路由 | 已有 Gateway 和权限路由，可能已有业务入口分流 | 还缺统一策略路由: 根据任务类型、风险、数据源、置信度选择路径 |
| 并行化 | 工具/模型/RAG/DB 都可观测，但不一定并行优化 | 可对低风险独立检索、指标收集、trace 查询做受控并行 |
| 反思 | Replanner 是雏形 | 需要显式的 plan verifier、report verifier、citation verifier、sql verifier |
| 工具使用 | ToolGateway 已治理工具可见性和调用 | 需要工具选择质量评估和错误恢复策略 |
| 记忆管理 | Memory/P7 已冻结，Runtime checkpointer 按部署触发 | 需要把 session state、durable memory、audit trace 三者边界写清 |
| 护栏与安全 | E2 rule guardrail + E9 负例 + audit | 需要 PII/output/provider shadow，不直接上重模型 |
| 评估与监控 | E9 有 smoke、负例、trace completeness | 需要 trajectory evalset、理想路径对比、协作/工具选择指标 |
| 优先级排序 | 阶段计划有优先级 | 运行时还缺任务成本/风险/紧急度的动态优先级 |
| 人类参与环节 | Admin/API 和审计可支持人工治理 | 需要把人工确认做成可恢复、可审计流程 |
| 异常处理与恢复 | ModelGateway 有 fallback，DB/RAG/SSE 未必统一 | 需要跨模块恢复策略和用户可见状态 |
| 资源感知优化 | 依赖、模型、工具已有边界 | 需要成本/延迟预算驱动模型、检索和工具策略 |

## 3. 2.0 改进路线

### F1: 任务合同化

对应书中: 规划、评估与监控、“高级承包商”模型。

目标:

复杂任务不能只靠一句自然语言 prompt 驱动，而要先形成可验证的任务合同。

适用场景:

- AIOps 诊断报告。
- DB 分析请求。
- 跨知识库 RAG 报告。
- 管理员批量授权或审计查询。
- 需要长流程执行的企业任务。

合同字段建议:

```json
{
  "task_id": "task-xxx",
  "trace_id": "trace-xxx",
  "user_goal": "用户原始目标",
  "scope": {
    "allowed_data_sources": [],
    "allowed_tools": [],
    "forbidden_actions": []
  },
  "success_criteria": [],
  "risk_level": "low|medium|high",
  "requires_human_approval": false,
  "latency_budget_ms": 30000,
  "cost_budget": null,
  "expected_outputs": []
}
```

验收:

- 每个高复杂任务都有 task contract。
- trace 可以关联 task contract、plan、tool calls、final report。
- final report 能对照 `success_criteria` 做自检。
- 合同范围外的工具或数据源不能被调用。
- Git 收口: 该阶段必须有实现提交和收口提交，收口提交记录合同字段、测试结果和已知缺口，完成后工作树保持干净。

不做:

- 不把所有普通聊天都合同化。
- 不让 LLM 自己无限扩展 scope。

### F2: 轨迹评估 Evalset

对应书中: 评估与监控、智能体轨迹评估。

目标:

从“最终回答对不对”升级到“执行路径是否合理”。

新增评估维度:

- stage 顺序是否正确。
- 工具选择是否正确。
- 未授权资源是否被跳过。
- blocked 事件是否发生在正确层。
- RAG citation 是否来自授权 source。
- SQL 是否经过 SafeSqlKernel。
- fallback 是否有明确原因。
- 是否发生无效循环、重复工具调用或过度检索。

建议 evalset:

| evalset | 覆盖 |
|---|---|
| `enterprise_chat_trace_evalset.jsonl` | chat/RAG 正常回答、未授权文档阻断 |
| `enterprise_aiops_trace_evalset.jsonl` | AIOps planner/executor/replanner 路径 |
| `enterprise_db_trace_evalset.jsonl` | safe_select、未授权表列、危险 SQL |
| `enterprise_admin_trace_evalset.jsonl` | 授权变更、撤权缓存、admin 403 |
| `enterprise_sse_contract_evalset.jsonl` | SSE type/stage/status/data 一致性 |

验收:

- 每条 eval 不只存 final answer，还存 expected trajectory。
- 能比较实际 trace 和 expected trajectory。
- E9 smoke 之后，2.0 eval 能发现“最终答案对但路径不合规”的问题。
- Git 收口: 该阶段必须有实现提交和收口提交，收口提交记录 evalset、matcher、runner 和验证结果，完成后工作树保持干净。

不做:

- 不用 LLM Judge 替代所有确定性检查。
- 不只凭人工看 UI 判断执行路径。

### F3: 策略路由

对应书中: 路由、优先级排序、资源感知优化。

目标:

完成当前主线后，系统会有多种能力: RAG、AIOps、DB、Admin、普通对话。需要一个轻量策略路由层，决定请求进入哪条路径。

路由输入:

- 用户角色和权限。
- query 类型。
- 是否需要实时数据。
- 是否需要数据库。
- 是否涉及高风险资源。
- 是否需要人工确认。
- latency/cost budget。

路由输出:

```json
{
  "route": "chat|rag|aiops|database|admin|human_review",
  "reason": "why this route is selected",
  "risk_level": "low|medium|high",
  "required_capabilities": [],
  "fallback_route": null
}
```

优先级:

1. 先做规则 + 小模型/LLM 分类 shadow。
2. 只在 shadow 准确率稳定后进入默认链路。
3. 路由必须可解释，并写入 trace。

验收:

- 简单知识问答不会误进 DB。
- DB 问题不会绕过 SafeSqlKernel。
- AIOps 故障诊断不会走普通 RAG。
- 高风险操作能进入 human review。
- Git 收口: 该阶段必须有实现提交和收口提交，收口提交记录路由规则、shadow 结果和回归检查，完成后工作树保持干净。

不做:

- 不做多 Agent 协调器。
- 不让路由器直接执行工具。
- 不把路由器变成第二个大 Agent。

2026-05-31 状态：F3 已完成。实现提交 `17a99bd enterprise2(f3): add strategy routing shadow`，新增 `app/enterprise/routing/*`、接入 `ChatAdapter` / `AIOpsAdapter` 的 shadow audit，并提供 route comparison report helper。验证覆盖 F3 targeted 4/4、受影响 gateway/request/human-review/task-contract 回归 20/20、企业侧累计回归、ruff、compileall、deps-check 和 diff-check。F3 只写 `routing_decision` audit，不改变用户响应、实际 route、工具池、SafeSqlKernel 或 human-review 执行门；promote 条件尚未满足。

### F4: 反思与自检

对应书中: 反思、推理技术、ReAct。

目标:

在关键输出前加入结构化自检，提升可靠性，但不暴露内部长链式思维。

建议自检器:

| 自检器 | 检查内容 |
|---|---|
| `PlanVerifier` | plan 是否覆盖 task contract，是否超出 scope |
| `CitationVerifier` | citation 是否来自授权文档，source_ref 是否完整 |
| `SqlResultVerifier` | SQL 是否经过 safe_select，结果列是否授权 |
| `ReportVerifier` | final report 是否覆盖 success_criteria |
| `GuardrailVerifier` | 输出是否含敏感信息或越权内容 |

输出格式:

```json
{
  "verifier": "ReportVerifier",
  "status": "passed|failed|needs_revision",
  "findings": [],
  "revision_required": false
}
```

验收:

- 自检结果进入 trace。
- 自检失败时能触发修订、拒绝或人工确认。
- 自检不改变权限边界。
- Git 收口: 该阶段必须有实现提交和收口提交，收口提交记录 verifier 行为、测试结果和已知边界，完成后工作树保持干净。

不做:

- 不把完整 chain-of-thought 写进 audit。
- 不让反思循环无限重试。
- 不因反思失败直接吞掉原始错误。

### F5: 异常恢复与降级策略

对应书中: 异常处理与恢复。

目标:

把失败从“报错结束”升级为“可解释、可恢复、可降级”。

需要统一的失败类别:

| 类别 | 示例 | 处理 |
|---|---|---|
| `auth_failed` | token 无效 | 401，提示重新登录 |
| `permission_denied` | 未授权文档/工具/表 | 403，写 audit |
| `model_unavailable` | 主模型超时 | fallback 或结构化失败 |
| `tool_failed` | MCP tool 超时 | retry/fallback/partial report |
| `retrieval_low_confidence` | 检索结果不足 | 提示补充信息或降级回答 |
| `sql_blocked` | 危险 SQL | 阻断并解释安全原因 |
| `stream_interrupted` | SSE 中断 | 客户端可按 trace 恢复或查看历史 |

验收:

- 每类失败都有 `error_class`、`stage`、`decision`、`user_message`。
- UI 能显示 blocked、failed、degraded、retrying、completed。
- audit 能区分系统失败和安全阻断。
- Git 收口: 该阶段必须有实现提交和收口提交，收口提交记录失败分类、恢复策略和回归验证，完成后工作树保持干净。

不做:

- 不对安全阻断做自动绕过重试。
- 不把所有错误都归为 generic error。

2026-05-31 状态：F5 已完成。实现提交 `c9646ef enterprise2(f5): add structured error recovery`，验证覆盖 F5 targeted、企业侧累计回归、ruff、compileall、deps-check 和 diff-check；收口提交记录 error_class / SSE / audit 验收与安全阻断不自动重试证据。

### F6: Human-in-the-loop

对应书中: 人类参与环节、护栏与安全。

目标:

高风险、低置信度、需要审批的任务进入人工确认，而不是让 Agent 自主完成。

触发条件:

- DB 写操作请求。
- 高敏文档访问。
- 大范围授权变更。
- 输出包含疑似 PII。
- AIOps 诊断置信度低但建议影响生产操作。
- task contract 超出用户权限。

流程:

```text
request
  -> risk detection
  -> pending_human_review
  -> approve / reject / request_changes
  -> resume or stop
```

验收:

- pending 状态可追踪。
- 人工审批写 audit。
- 审批后可以恢复同一 trace。
- 拒绝后不会继续调用高风险工具。
- Git 收口: 该阶段必须有实现提交和收口提交，收口提交记录审批流、审计事件和高风险路径回归，完成后工作树保持干净。

不做:

- 不把 human review 做成聊天里的临时确认句。
- 不绕过 PermissionService。

2026-05-31 状态：F6 已完成。实现提交 `814d9cc enterprise2(f6): add human review mvp`，验证覆盖 human review targeted、admin/task/gateway 受影响回归、企业侧累计回归、ruff、compileall、deps-check 和 diff-check；收口提交记录审批 API、Admin 权限保护、audit、审批后重提执行和拒绝后不继续执行证据。

### F7: 高级 Guardrail

对应书中: 护栏与安全模式。

目标:

在规则 guardrail 之上，渐进加入输入和输出侧安全检查。

推荐顺序:

```text
PII regex/provider shadow
  -> output rolling check
  -> 企业 DLP/content safety API adapter
  -> LLM-as-Judge shadow
  -> 根据误报率/漏报率/延迟决定是否默认启用
```

验收:

- 每个 provider 都有 `provider_name`、`policy_id`、`category`、`severity`、`decision`。
- shadow 阶段不阻断用户路径，只写 audit。
- 默认阻断前必须有误报/漏报样本复核。
- Git 收口: 该阶段必须有实现提交和收口提交，收口提交记录 provider 证据、shadow 指标和复核结论，完成后工作树保持干净。

不做:

- 不训练自定义安全分类模型。
- 不直接把 LLM-as-Judge 放进热路径。
- 不把云安全 API 作为本地开发必需依赖。

2026-05-31 状态：F7 已按 gated 规则完成 evidence-only 收口。证据提交 `d5c6d9e enterprise2(f7): record guardrail trigger audit`，记录见 `docs/enterprise2_f7_guardrail_trigger_audit.md`。本地 audit JSONL/SQLite、2026-05-31 app log 和 F2/F4/F5 记录中未发现 PII / 敏感输出样本，也没有证明现有 rule guardrail 不足；因此不实现 PII regex provider、DLP adapter、云安全依赖或 LLM-as-Judge shadow，不改变默认用户路径。

### F8: 资源感知优化

对应书中: 资源感知优化、优先级排序。

目标:

让系统根据任务价值、风险、成本和延迟选择模型、工具和执行策略。

可优化对象:

- 模型选择: cheap model / strong model / fallback model。
- 检索策略: vector only / hybrid / rerank / no retrieval。
- DB 查询: row limit、timeout、explain-only。
- 工具调用: 并发、重试、timeout。
- SSE 输出: 阶段粒度和历史保留。

指标:

- latency p50/p95。
- token usage。
- tool call count。
- retrieval cost。
- DB query cost。
- failure / retry count。
- user-visible degraded rate。

验收:

- 每次模型/工具/fallback 选择都有原因。
- 高成本路径默认需要明确触发条件。
- 优化前后有 benchmark 或 eval 对照。
- Git 收口: 该阶段必须有实现提交和收口提交，收口提交记录指标基线、对照结果和策略选择边界，完成后工作树保持干净。

不做:

- 不为了省成本牺牲安全边界。
- 不在没有指标前改默认模型或检索策略。

2026-05-31 状态：F8 已按 gated 规则完成 evidence-only 收口。证据提交 `297a45f enterprise2(f8): record resource trigger audit`，记录见 `docs/enterprise2_f8_resource_trigger_audit.md`。当前本地 enterprise audit 没有稳定 token/tool/DB 指标基线，也没有明确成本或延迟瓶颈；因此不新增 resource budget / strategy selector，不改变公开 request schema，也不改变默认模型、检索、DB 或工具策略。

## 4. 优先级

完成全部当前待办后，推荐优先级如下:

| 优先级 | 事项 | 原因 |
|---|---|---|
| P0 | F2 轨迹评估 Evalset | 没有轨迹评估，后续所有智能化改动都难证明收益 |
| P0 | F1 任务合同化 | 复杂任务需要明确范围、交付物、数据源和验收标准 |
| P1 | F4 反思与自检 | 提升报告、citation、SQL、plan 可靠性 |
| P1 | F5 异常恢复 | 生产可用性依赖可解释失败和恢复 |
| P1 | F6 Human-in-the-loop | 高风险企业操作必须有人工审批路径 |
| P2 | F3 策略路由 | 能提升体验，但必须先有 eval 和合同约束 |
| P2 | F7 高级 Guardrail | 有合规触发时优先，不做无证据大而全 |
| P2 | F8 资源感知优化 | 等成本/延迟数据足够后做 |

## 5. 多智能体暂缓规则

虽然 PDF 强调 Level 3 多智能体，但本项目 2.0 阶段仍然不做。

原因:

- 当前企业助手更缺的是可验证性、恢复性、审批和轨迹评估。
- 多智能体会让 trace、成本、失败定位、评估复杂度显著上升。
- 如果没有 trajectory evalset，多智能体收益无法证明。
- 如果没有 task contract，多智能体协作范围容易失控。

重新评估多智能体必须同时满足:

1. F1 任务合同化已完成。
2. F2 轨迹评估已完成。
3. E9/E11 后的企业闭环稳定。
4. 单 Agent 在 AIOps 或复杂研究任务上有稳定、可复现、无法通过 F3-F8 解决的瓶颈。
5. 先做 shadow 模式，不改变默认用户路径。

## 6. 2.0 不改的内容

- 不重开 Memory P7 主线。
- 不默认替换 `MemorySaver`，除非进入 Runtime 部署恢复需求。
- 不默认开启 RAG reranker。
- 不默认加入 query embedding cache。
- 不默认改 Milvus index。
- 不默认改 chunking 策略。
- 不默认引入云内容安全服务。
- 不把 DB 写操作开放给 Agent 自主执行。

## 7. 推荐下一步

如果当前全部待办已经完成，2.0 的第一步应该是:

```text
F2 轨迹评估 Evalset
  -> F1 任务合同化
  -> F4 反思与自检
```

原因:

- 先有轨迹评估，才能判断后续优化是否真的变好。
- 再有任务合同，才能给复杂任务定义边界和成功标准。
- 最后加反思自检，才能在不引入多智能体的情况下提高可靠性。

不建议第一步就做:

- 多智能体。
- RAG 路由大改。
- 高级 LLM Judge 热路径。
- 持久 checkpointer 替换。
- 复杂 Vue3 二次改版。

## 8. 一句话版本

当前全部待办完成后，企业助手下一阶段的关键不是“更多 Agent”，而是:

```text
任务合同化 + 轨迹评估 + 策略路由 + 反思自检 + 异常恢复 + 人工审批 + 资源预算
```

多智能体先不做，等上述可靠性和评估底座成熟后，再用 shadow 方式单独验证。
