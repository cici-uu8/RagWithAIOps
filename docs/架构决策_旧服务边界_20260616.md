# 架构决策：旧服务边界与 RequestContext 传递

日期: 2026-06-16

状态: 已采用，作为 `docs/架构违反检查报告_20260616.md` 的 P0 修复决策记录。

## 背景

架构检查发现两个 P0 偏差:

1. `/api/chat/clear` 直接调用 `rag_agent_service.clear_session()`，绕过 `ChatAdapter` 和 `RequestGateway`。
2. RAG / AIOps 旧服务关键路径直接读取 `get_current_request_context()`，导致调用契约隐式、测试困难。

同时，`app/services/rag_agent_service.py`、`app/services/aiops_service.py` 和 `app/services/knowledge_search_service.py` 已经承载大量历史调用、eval、测试和产品路径。立即移动文件会带来大范围导入路径变更，不适合和 P0 安全审计修复混在同一轮。

## 决策

本轮不移动以下旧服务文件:

- `app/services/rag_agent_service.py`
- `app/services/aiops_service.py`
- `app/services/knowledge_search_service.py`

先采用保守收敛策略:

```text
HTTP route
  -> CurrentUser / RequestContext
  -> Adapter
  -> RequestGateway
  -> legacy service with explicit context parameter
```

旧服务可以暂时保留 `get_current_request_context()` 作为 legacy direct caller / eval / 单测兼容 fallback，但新 adapter 调用必须显式传入 `RequestContext`。

## 已落地修复

- `ChatAdapter.clear_session(...)` 新增 `route="chat_clear"` 的 `RequestGateway.execute(...)` 包装。
- `/api/chat/clear` 改为调用 `chat_adapter.clear_session(...)`，不再直接调用 `rag_agent_service.clear_session()`。
- `ChatAdapter.chat(...)` / `ChatAdapter.chat_stream(...)` 显式把 `RequestContext` 传给 `RagAgentService.query(...)` / `query_stream(...)`。
- `AIOpsAdapter.diagnose_stream(...)` 显式把 `RequestContext` 传给 `AIOpsService.diagnose(...)`。
- `RagAgentService` / `AIOpsService` 的 contextvar 读取降级为 `_resolve_request_context(context)` fallback，而不是 adapter 主路径依赖。

## 非目标

- 不把 `rag_agent_service.py` / `aiops_service.py` / `knowledge_search_service.py` 提升到 `app/enterprise/*`。
- 不在本轮做构造函数级依赖注入替换所有 singleton import。
- 不把所有历史 direct service caller 一次性迁移。
- 不修改 `docs/项目完整架构.md` 长期基线；该文件仍要求所有新增用户请求走 `RequestGateway`。

## 后续触发条件

只有当满足以下任一条件时，才重新讨论移动旧服务:

- 新功能需要继续在 `app/services/*` 内新增 enterprise 依赖，导致 adapter 失去意义。
- 测试或 eval 已经无法在不加载 enterprise 层的情况下运行，且构造函数注入也不能缓解。
- 用户明确要求做分层重构，而不是 P0 安全/审计修复。
