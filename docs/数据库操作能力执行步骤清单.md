日期：2026-06-02

状态：执行清单草案。当前只读 L1/L2 已有基础；DB-MySQL-1 的 MySQL 只读 provider、独立 kernel、PyMySQL 只读连接器、配置启用、自动化测试和本地 Docker MySQL live smoke 已完成。DB-Ops-2 tool schema、DB-Ops-3 SQL 操作分类器、DB-Ops-4 operation 权限模型、DB-Ops-6 prepare operation 后端、DB-Ops-7/8 用户确认 + sandbox 执行管线、DB-Ops-9 审计回归门禁和 DB-Ops-10 真服务 smoke 已完成。产品规则已更正：只有删除类操作需要用户后台确认；非删除写操作和非删除 DDL 有权限后直接执行。DB-MySQL-3 已新增并 live-smoke 验证非生产 MySQL `INSERT` / `UPDATE` 直接执行路径，并保留 `DELETE` 确认流；DB-MySQL-4 已实现并 live-smoke 验证非生产 MySQL L5 DDL：非删除 DDL direct execute，删除类 DDL confirmation；生产库接入仍是后续独立策略。

## 0. 当前边界

当前已完成：

- `database_demo.list_tables`
- `database_demo.describe_table`
- `database_demo.safe_select`
- `POST /api/database/safe-select`
- ToolGateway / PermissionService / DatabaseDemoToolProvider / SafeSqlKernel / database_query audit 的只读链路
- MySQL 真实只读数据库本地 live smoke（Docker MySQL 8.0、只读账号、allowlist、Admin API grant、HTTP safe_select、audit）
- `ToolDefinition.input_schema` / `strict` 和 OpenAI function tool schema helper
- `app/enterprise/database/operation_classifier.py` SQL 操作分类器（standalone，未接入执行路径）
- `database_operation/<database_id>.update|delete|ddl/execute` operation 权限资源和 prepare 前置权限 checker
- `POST /api/database/operations/prepare` 生成 SQLite 持久化 confirmation，不执行写入、删除或 DDL
- `GET /api/database/confirmations`、详情、confirm、cancel API
- 普通用户“我的权限”弹层中的数据库操作确认区
- `sandbox_sales` SQLite sandbox 的确认后 `UPDATE` / `DELETE` / `DROP TABLE` 执行管线
- 非生产 writable MySQL 的 `INSERT` / `UPDATE` direct execute
- 非生产 writable MySQL 的非删除 DDL direct execute：`CREATE TABLE`、非删除 `ALTER TABLE`、`CREATE INDEX`、`DROP INDEX`、rename / modify
- 非生产 writable MySQL 的删除类 confirmation：`DELETE`、`DROP TABLE`，并保留 `TRUNCATE` / `ALTER TABLE DROP COLUMN` 删除类分类和权限边界

当前未完成：

- 生产库写入、删除、DDL 接入策略
- `prepare_operation` function calling 注册
- confirm function calling 暴露（原则上不开放；confirm 只能走用户 HTTP/UI）
- 执行超时 cleanup job、历史状态筛选 UI、更新/删除前样例、trace_id/request_id 展示、最大影响行数阈值、DDL allowlist 细化

硬边界：

- 不做万能 `execute_sql`。
- 不让模型直接调用 confirm / execute。
- 不把通用数据库 MCP server 放进默认工具池。
- 不让无权限用户通过确认流绕过权限。
- 权限管理只在管理员后台做，普通用户后台只做自己有权限的数据库操作确认。
- DB-MySQL-1 真实验证阶段只做只读 L1/L2；DB-MySQL-3 目标是对非生产 writable MySQL 开放非删除写操作直接执行，同时保留删除类确认流。
- DB-MySQL-4 只面向非生产 writable MySQL 的 DDL 切片：非删除 DDL direct execute，删除类 DDL confirmation。
- 生产库写入、删除、DDL 不是 DB-MySQL-3/4 的默认范围，必须另开生产接入策略。

## 6. DB-Ops-3：SQL 操作分类器

目标：在执行前确定 SQL 属于 L1/L2/L3/L4/L5 哪一类。

状态：已完成 standalone classifier；不改变现有 `safe_select` route、`SafeSqlKernel`、`MySqlSafeSqlKernel` 或 ToolGateway 行为。

职责边界：

- [x] 操作分类器负责路由决策：L1/L2 直接走只读 kernel，L3 非删除写入可进入 direct execute，L4 删除类进入 prepare confirmation，L5 非删除 DDL 可进入 direct execute，M1 权限管理 SQL 直接拒绝或转管理员后台。
- [x] `SafeSqlKernel` / MySQL read-only kernel 继续负责执行前安全校验：单语句、只读、allowlist、LIMIT、timeout、结果大小、敏感字段处理。
- [x] 分类器不能替代 kernel 安全校验；kernel 也不能决定 L3-L5 是否进入确认流。
- [x] 分类器和 kernel 对同一 SQL 的基础结论必须一致；若分类器判定 L1 但 kernel 阻断，以 kernel 阻断为准并写 audit。当前 DB-Ops-3 尚未接入 audit，后续接入时必须保留这条优先级。

  - `INSERT` -> L3。
  - `UPDATE` -> L3。
  - `DELETE` -> L4。
  - `TRUNCATE` -> L4。
  - `DROP TABLE` -> L4。
  - `ALTER TABLE DROP COLUMN` -> L4。
  - `CREATE TABLE` -> L5。
  - `ALTER TABLE ADD COLUMN` -> L5。
  - `CREATE INDEX` / `DROP INDEX` / rename / modify -> L5。
  - `GRANT` / `REVOKE` 不进入普通数据库操作确认流。
  - parse failure / multi-statement 返回 denied classification，不进入确认流。

## 7. DB-Ops-4：L3-L5 操作权限模型

- `resource_type=tool`
- `resource_type=database_table`
- `resource_type=database_column`
- `action=use/read`

已锁定方案：

推荐增加一类资源：

```text
resource_type = database_operation
resource_id = <database_id>.<operation_type>
action = execute
```

示例：

```text
database_operation / sandbox_sales.update / execute
database_operation / sandbox_sales.delete / execute
database_operation / sandbox_sales.ddl / execute
```

```text
database_operation 权限
  + database_table 权限
  + database_column 权限
```

- [x] 变更目标表必须拥有对应 `database_operation` 权限。
- [x] 被 `JOIN`、子查询、`WHERE`、`RETURNING` 引用的表和列，仍必须拥有只读 table / column 权限。

## 8. DB-Ops-5：Dry-run 和影响评估方案

目标：在 L3-L5 生成确认项之前，先确定 dry-run 的真实语义，避免给用户展示不可信的影响行数。

阶段性质：这是 L3-L5 的设计 gate，可以没有代码产出，但必须在 DB-Ops-6 prepare operation 开工前完成并记录决策。

Gate 决策（2026-06-02）：

- [x] DB-Ops-5 只冻结设计，不实现任何写入、删除、DDL 或 confirmation 代码。
- [x] 第一版 L3-L5 prepare 的用户可见 dry-run 不使用“执行后 rollback”作为默认方案；rollback 型预演只允许留在隔离测试或 sandbox 实验里，不能作为真实 MySQL 或用户可见影响评估。
- [x] SQLite sandbox 如果后续为了测试使用 `BEGIN ... ROLLBACK`，必须标记为 sandbox-only，并在摘要里说明可能触发 trigger、锁、自增 ID 消耗或其他副作用；不能把它描述成“无副作用 dry-run”。
- [x] MySQL L3-L5 不沿用 SQLite rollback 方案。MySQL 第一版只允许 read-only preview：AST 分析、allowlist 检查、`SELECT COUNT(*)` 估算、schema metadata 摘要、`EXPLAIN FORMAT=JSON` 计划信息。
- [x] `EXPLAIN` / `EXPLAIN FORMAT=JSON` 只能写入 `plan_summary`，不能写入 `estimated_affected_rows`，也不能被当成真实影响行数。
- [x] `UPDATE` / `DELETE` 的影响行数估算优先由 AST 重写出等价 `SELECT COUNT(*)`，且只统计直接命中的目标行；trigger、cascade、外键连带影响、二级索引维护和锁等待不在 COUNT 内，必须写进 `estimate_notes`。
- [x] `INSERT ... VALUES` 的估算以 values 行数为准；`INSERT ... SELECT` 只能在 source SELECT 可被只读 kernel 安全验证时给 count preview，否则 `estimated_affected_rows=null`。
- [x] DDL 的 dry-run 只做 schema impact summary，不做真实执行：`CREATE TABLE` 展示新对象摘要，`ALTER TABLE` 展示新增/修改/删除字段或索引摘要，`DROP TABLE` 展示将删除对象和已有 schema metadata；不返回伪 affected_rows。
- [x] 无法可靠估算时，确认项必须显示 `estimated_affected_rows=null`、`estimate_reliable=false` 和具体 `estimate_reason`，不能展示伪精确数字。
- [x] 删除类操作默认高风险。`DELETE` 无 `WHERE`、`TRUNCATE`、`DROP TABLE`、`ALTER TABLE DROP COLUMN` 必须进入 L4 确认；真实数据源是否允许 full-object operation 必须在数据源接入配置里显式声明。这是数据源安全边界，不是新增一类用户审批权限；用户侧仍只看 `database_operation/<database_id>.delete/execute`。
- [x] DB-Ops-6 首个实现切片应优先在 sandbox / 非生产 writable fixture 上验证 L3-L5；真实 MySQL 写入、删除和 DDL 需要非生产 writable MySQL、备份/恢复说明、数据 owner、operation resource 和 smoke 计划齐备后才能打开。

确认项风险摘要字段：

```text

dialect
operation_level
operation_type
risk_level
tables
columns
estimated_affected_rows
estimate_reliable
estimate_method
estimate_reason
estimate_notes
plan_summary
schema_impact
sample_before_rows
max_allowed_affected_rows
```

MySQL 真实只读验证阶段：

- [x] 不实现 L3-L5 dry-run。
- [x] 不实现写入、删除或 DDL。
- [x] 只验证 L1/L2 的 SQL 安全、权限、allowlist、audit。

建议测试：

- [ ] `EXPLAIN` 结果不会被当成 affected_rows。
- [ ] `UPDATE ... WHERE ...` 可生成等价 count preview。
- [ ] `DELETE ... WHERE ...` 可生成等价 count preview。
- [ ] 无 WHERE 的删除类操作被标为高风险，或按策略直接拒绝。
- [ ] DDL 返回 schema impact summary，不返回伪 affected_rows。
- [ ] 无法估算时 summary 明确 `estimated_affected_rows=null` 和 `estimate_reliable=false`。

## 9. DB-Ops-5.5：确认项生命周期和失败恢复

目标：在实现 prepare / confirm 之前，先锁定确认项的持久化、清理、失败和重试语义，避免做出只能靠内存或前端状态维持的确认流。

阶段性质：这是 L3-L5 的设计 gate，可以没有代码产出，但必须在 DB-Ops-6 prepare operation 和 DB-Ops-7 用户后台开工前完成并记录决策。

Gate 决策（2026-06-02）：

- [x] confirmation 第一版使用 SQLite 持久化；不使用内存仓库作为正式方案。后续若迁移到正式 durable store，需另开迁移任务。
- [x] confirmation 记录必须保存 `confirmation_id`、owner user、`database_id`、dialect、operation level/type、SQL 原文、SQL hash、参数 hash、normalization version、dry-run 摘要、权限快照摘要、trace/request metadata、状态和状态时间戳。
- [x] confirmation 状态机：

```text
pending
confirmed
cancelled
expired
executing
executed
failed
```

- [x] 允许状态迁移：

```text
pending -> cancelled
pending -> expired
pending -> confirmed -> executing -> executed
pending -> confirmed -> executing -> failed
executing -> failed
```

- [x] 不允许状态迁移：`cancelled` / `expired` / `executed` / `failed` 不能再次 confirm；`confirmed` 不能回到 `pending`。
- [x] `pending` 默认 TTL 为 15 分钟，记录 `expires_at`；超时后 confirm 返回 409 或 403，不能执行。
- [x] cleanup job 负责把超时 `pending` 标记为 `expired`，不是静默删除；cleanup 本身必须写 audit 或可观察日志。
- [x] 默认列表只突出 `pending`；历史列表可过滤 `executed` / `failed` / `cancelled` / `expired`。
- [x] `executing` 必须有 `execution_deadline_at`，默认 2 分钟；超过期限仍未落到 `executed` / `failed` 时，cleanup 标为 `failed`，reason 为 `execution_timeout`。
- [x] confirm 必须用原子条件更新从 `pending` 抢占到 `confirmed` 或 `executing`，防止重复点击、双请求或重放导致二次执行。
- [x] 执行失败进入 `failed` 并写 audit；底层数据库错误要结构化脱敏，不能原样暴露给用户。
- [x] 默认不复用失败 confirmation；重试必须重新 prepare。即使后续增加 `retryable=true`，也必须重新复核 SQL hash、参数 hash、权限、目标范围和 dry-run 摘要。
- [x] SQL hash 必须携带版本字段，例如 `sql_hash_version` 和 `normalization_version`，避免解析器或标准化规则升级后误判。
- [x] confirm 前必须重新校验：当前用户仍是 owner、仍有 operation 权限、仍有 table / column 权限、database/provider 仍存在、allowlist 未越界、SQL hash 和参数 hash 未变、dry-run 摘要仍在阈值内、confirmation 未过期且未被使用。
- [x] audit retention 和 confirmation cleanup 分开配置；清理 confirmation 不能删除 audit。第一版 confirmation closed-state 保留期默认 30 天，audit 保留期不得短于排障和合规窗口。
- [x] 与 Stage 5 permission request 的边界：Stage 5 是申请权限，confirmation 是已有权限后的执行确认，二者不能互相替代。
- [x] 与 F6 HITL 的边界：F6 是人工复核/任务治理流，不替代数据库操作权限，也不替代用户后台 execution confirmation。
- [x] 与管理员后台边界：管理员后台只负责授予/撤销 `database_operation`、table、column 等权限；普通用户后台只确认自己已有权限的数据库操作。

## 15. 长期风险清单

| 风险 | owner | 触发条件 | 应对策略 |
|---|---|---|---|
| SQL hash / normalization 版本漂移 | DB-Ops owner | SQL parser、normalizer 或 dialect 规则升级 | confirmation 记录保存 `sql_hash_version` / `normalization_version`；版本不匹配时拒绝旧 confirmation 或走显式迁移 |
| audit retention 短于 confirmation 生命周期 | 平台 / 审计 owner | cleanup 或 retention 规则调整 | audit retention 单独配置，必须覆盖 confirmation 生命周期和排障窗口 |
| confirmation 堆积 | DB-Ops owner | `pending` / `expired` 记录持续增长 | cleanup job 标记过期并按保留期清理；cleanup 写 audit 或可观察日志 |
| SQLite dry-run 被误用于 MySQL | DB-Ops owner | 开始 MySQL L3-L5 设计 | MySQL 必须另写 dry-run 方案；DB-MySQL-1 阶段明确只做 L1/L2 |
| MySQL 只读验证被误读为 L3-L5 可用 | 项目 owner | MySQL safe_select smoke 通过后 | 文档和 release note 明确只读范围；写入、删除、DDL 另开阶段 |
| 非删除 DDL 被误归为删除类确认 | DB-Ops owner | 开始 DB-MySQL-4 代码切片 | 以 L4/L5 分类为准：`DROP TABLE` / `ALTER DROP COLUMN` / `TRUNCATE` 确认；`CREATE` / 非删除 `ALTER` / index / rename / modify direct execute |
| MCP database server 绕过治理链路 | 工具平台 owner | 引入外部 MCP database server | 只能作为受管 provider 或独立实验；默认工具池不暴露，必须经过 ToolGateway / PermissionService / audit |
| provider `database_id` 冲突 | DB-Ops owner | 新增真实数据源 provider | 每个 provider 独立 `database_id` 和 resource_id 前缀；测试覆盖 sandbox/MySQL 共存不串库 |

## 17. 暂停点

完成任一阶段后，如果出现以下情况，应暂停继续实现：

- 权限模型无法表达 per-database / per-operation / per-table 组合。
- dry-run 无法可靠估算影响行数，尤其在真实 MySQL 上无法给出可信结果。
- 真实数据库没有回滚、备份或 owner。
- 用户后台无法展示足够明确的风险摘要。
- audit 无法追踪 prepare -> confirm -> execute 的同一 `confirmation_id`。
- LLM tool schema 会让模型直接执行 confirm 或 execute。

## 18. 一句话执行路线

先按 DB-MySQL-1 把 L1/L2 只读链路接到真实 MySQL 并验证 provider / `database_id` / dialect / audit 边界；再用 DB-Ops-2~10 打通删除类操作的权限、prepare、confirmation、复核、执行和审计链路；DB-MySQL-3 已把非生产 MySQL `INSERT` / `UPDATE` 改为 direct execute，并保留 `DELETE` 确认流；DB-MySQL-4 已把非生产 MySQL 的非删除 DDL direct execute 和删除类 DDL confirmation 打通并 live-smoke 验证。生产接入策略仍是独立切片，不能把非生产 smoke 直接外推为生产可写上线。
