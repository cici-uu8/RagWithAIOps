# 6 月 4 日项目存在问题和应对办法

日期：2026-06-04

状态：更新版架构问题台账。

适用范围：`SuperBizAgent` 当前企业助手、知识库、RAG、数据库、AIOps、Memory、权限、前端工作台、文档处理、评测与观测主线。

关联基线：`docs/项目完整架构.md`。

## 1. 总判断

当前项目不是“能力没有做”，而是已经形成了多个能力 Module，但一些关键 Seam 还没有完全收口。

已经较成熟的 Module 包括：

| Module | 当前价值 |
|---|---|
| `RequestGateway` | 用户请求、trace、audit、guardrail、失败恢复的统一入口 |
| `PermissionService` | 默认拒绝、显式授权、deny override、权限审计 |
| `DocumentAccessService` | 文档与知识库可见性判断 |
| `RagAdapter` | 企业权限和旧检索链路之间的 Adapter |
| `RetrievalService` | dense / sparse / hybrid 检索与上下文组织 |
| `ToolGateway` | 工具可见性、工具权限、执行审计的目标 Seam |
| `SafeSqlKernel` | 数据库 SQL 安全执行核心 |
| `AuditService` / trace eval | 观测和评测证据入口 |
| `StrategyRouter` | 已有 rules / keyword / LLM shadow 路由框架，当前只记录 shadow 决策 |

但从用户当天看到的问题倒推，项目仍存在十一类主要问题：

| 优先级 | 问题 | 架构根因 | 应对方向 |
|---|---|---|---|
| P0 | RAG scoped / auto 无命中不可解释 | 数据、权限、检索、Agent 工具调用缺少统一 diagnostics | 补 RAG diagnostics 和分层 smoke |
| P0 | PDF / 文档处理状态仍可能卡住 | 文档生命周期散在 ingestion、queue、worker、index、route | 加深 `DocumentProcessingWorkflow` |
| P0 | ToolGateway 还没全线接管 RAG / AIOps 工具 | Agent 仍有直接拼 local tools / MCP tools 的路径 | 建 `ToolExecutionFacade` / bindable Adapter |
| P1 | 知识问答内部缺少 Query Intent Router | 聊天层把问题直接交给 LLM Agent 自行决定 list / retrieve / read / chat，缺少可验证的知识查询意图路由 | 建 `QueryIntentRouter` + `KnowledgeRetrievalOrchestrator`；v1 先 rules-only，v2 再把小 LLM 作为 LangChain / ModelGateway 结构化分类器 |
| P1 | 普通用户权限申请过窄 | 后端资源模型通用，前端只产品化了 KB 快捷申请 | 拆 KB 快捷申请和高级资源申请 |
| P1 | admin / 普通用户知识库入口表现不一致 | 前端契约、profile、路由健康检查分散 | 统一前端 API client 和 capability health |
| P1 | 会话历史不可靠 | localStorage、LangGraph checkpointer、进程内 owner guard 不是统一持久会话 Module | 建 `SessionAccess` + 持久会话库 |
| P1 | 数据库页、数据库 tool、数据库评测不是一个闭环 | catalog、profile、ToolGateway、live Agent eval 分散 | 做 DB capability health 和 live DB Agent eval |
| P2 | SourceRef / ChunkEvidence 分散 | evidence 字段在索引、检索、工具、eval 多处拼装 | 建 `ChunkEvidenceMapper` |
| P2 | 原始资料导入和 RAG 评分还没闭环 | reviewed import 只做了小样本，RAG eval 仍未完成 | 小样本 smoke -> RAG eval -> 扩大导入 |
| P2 | AIOps 工具池和失败语义仍需加深 | planner / executor / replanner 的工具发现、timeout、fallback 分散 | 建 `AIOpsToolCatalog` / `AIOpsFailureSemantics` |

结论：后续整改不要先追页面样式，也不要直接改 prompt。正确路线是先让每个 Module 有清晰 Interface、diagnostics 和验证点，再逐步把绕行路径收口到架构基线。

## 2. 重新审视方法

以后分析任何用户可见问题，都按这个链路拆开：

```text
用户界面
  -> 前端契约
  -> 身份与会话
  -> RequestGateway
  -> Permission / Resource
  -> 领域 Module
  -> ToolGateway / DB / MCP / 检索
  -> 数据 / 索引 / 队列
  -> Audit / Eval / Smoke
```

四个判断原则：

1. 页面无结果，不等于后端能力不存在。
2. 后端接口通过，不等于权限和数据可见性正确。
3. Agent 回答不对，不等于检索坏了，也可能是工具没被调用。
4. 手工问答看起来对，不等于评测通过。

每个问题必须写清楚：

- 属于哪个 Module。
- 跨了哪个 Seam。
- 现有 Interface 缺了什么。
- 应该用什么 Adapter 接旧代码。
- 怎么验证这个 Module 单独正常。

## 3. P0 问题一：RAG 搜索无命中不可解释

## 3.1 现象

用户观察到：

- scoped 到“流程与数字化部”搜“中车长客数字化转型”没有命中。
- scoped 到“工艺部”搜“线上故障怎么处理”没有命中。
- auto 搜“线上故障怎么处理”没有命中。
- 普通用户不同问法得到的回答不一致。

## 3.2 当前代码事实

当前已经有这些正向基础：

- `DocumentAccessService.visible_kb_ids()` 能按用户权限算可见知识库。
- `DocumentAccessService.visible_document_ids()` 能按 KB 和状态算可见文档。
- `RagAdapter.retrieve()` 会先分出可见文档，再把 `allowed_doc_ids` 传给 `RetrievalService`。
- `KnowledgeSearchService` 已支持 scoped / auto / all_visible 路由。
- 聊天页可通过 `KnowledgeBaseIds` 把用户选择的知识库范围传入后端。
- `retrieve_knowledge` 工具会继承当前请求的知识库 scope。

问题不在于完全没有权限过滤，而在于“无结果原因”没有被产品化展示。

## 3.3 架构原因

RAG 无命中至少可能来自五层：

| 层 | 可能原因 | 当前缺口 |
|---|---|---|
| 数据层 | 文件没有导入、还在 `parse_pending`、索引失败 | 搜索结果没有返回 indexed / pending 统计 |
| 权限层 | 用户没有 KB 或 document read 权限 | 搜索结果没有返回 allowed / filtered 统计 |
| 检索层 | sparse / dense / hybrid 没召回 | 没有返回 sparse_hit_count / dense_hit_count |
| Agent 层 | 模型没有调用 `retrieve_knowledge` | 普通用户看不到 tool trace |
| 前端层 | scoped / auto 选择没有实际传到请求 | 没有统一请求 debug 面板 |

这说明 `RetrievalService` 和 `RagAdapter` 的 Interface 还偏“返回结果”，缺少“返回为什么没有结果”的 diagnostics。

## 3.4 解决办法

新增或补强 `RagDiagnostics`，由 `KnowledgeSearchService` / `RagAdapter` / `RetrievalService` 逐层填充：

```json
{
  "requested_kb_ids": ["craft_dept"],
  "visible_kb_ids": ["process_digital_dept"],
  "selected_kb_ids": [],
  "allowed_doc_count": 0,
  "indexed_doc_count": 0,
  "parse_pending_doc_count": 1,
  "sparse_hit_count": 0,
  "dense_hit_count": 0,
  "hybrid_result_count": 0,
  "permission_filtered_count": 0,
  "fallback_mode": "none",
  "no_result_reason": "selected_kb_not_visible_or_no_indexed_documents"
}
```

这个示例故意表示一种失败场景：用户请求检索“工艺部”知识库，但当前账号只可见“流程与数字化部”，所以 `selected_kb_ids` 为空，系统应该明确返回 `selected_kb_not_visible_or_no_indexed_documents`，而不是只显示“没有命中”。

前端知识库搜索调试区展示：

- 当前用户可见 KB。
- 实际搜索 KB。
- 可检索 indexed 文档数。
- pending / failed 文档数。
- dense / sparse / hybrid 召回数。
- 是否因为权限过滤为空。
- 是否因为 worker 未完成解析。

Agent 对话侧补充：

- SSE 或 audit 中记录 `retrieve_knowledge` 调用参数。
- 最终回答 artifact 带 source_ref。
- 快速模式和流式模式都要能看到同样的检索 scope。

## 4. P0 问题二：文档处理状态仍可能卡住

## 4.1 现象

PDF 上传后出现“等待解析”长期不动。用户认为上传和入向量库应该自动完成，不应该靠人工理解后台任务。

## 4.2 当前代码事实

当前已有基础：

- PDF 上传会进入 `parse_pending`。
- `DocumentProcessingQueue.process_deferred_document_job()` 能处理异步解析和索引。
- Python 异常会写 `parse_failed` / `index_failed`。
- `reconcile_stale_document_processing_jobs()` 能把超时的 `parse_pending/parsing/indexing` 转失败态。
- `/api/document-management`、`/api/documents`、`/api/documents/status-batch` 读取前会触发兜底 reconcile。

## 4.3 架构原因

当前文档生命周期仍散在多个 Module：

```text
upload route
  -> UploadAdapter
  -> DocumentIngestionService
  -> DocumentProcessingQueue
  -> worker
  -> parser
  -> VectorIndexService
  -> KnowledgeMetadataStore
  -> status API
```

这个链路的问题是 Interface 太多，状态机知识泄漏：

- route 知道状态。
- queue 知道状态。
- index service 知道失败状态。
- metadata store 知道状态转换。
- 前端只看到结果，不知道 worker health。

这说明 `DocumentProcessingWorkflow` 还没有成为 deep Module。

## 4.4 解决办法

新增或加深 `DocumentProcessingWorkflow`：

```text
DocumentProcessingWorkflow
  - submit_upload()
  - enqueue_deferred_processing()
  - process_deferred_document()
  - reindex_document()
  - reconcile_stale_processing()
  - status_batch()
  - worker_health()
```

业务规则：

- HTTP route 只调用 workflow。
- RQ / Redis 只是 Adapter，不拥有业务状态机。
- worker 崩溃、parser 异常、embedding 失败、Milvus 失败都必须落明确失败态。
- 前端状态不能只显示“等待解析”，还要显示“后台 worker 未运行 / job 超时 / parser 失败 / index 失败”。

## 4.5 验证方式

自动验证：

```bash
uv run pytest tests/test_document_processing_queue.py tests/test_document_ingestion_service.py tests/test_knowledge_base_api.py -q --no-cov
```

人工 smoke：

1. 上传一个 PDF。
2. 观察 `/api/documents/status-batch` 从 `parse_pending` 变成 `indexed` 或失败态。
3. 停掉 worker 后上传 PDF，前端应提示 worker / queue 不健康，而不是无限等待。
4. 构造超时处理中状态，确认 reconcile 后变成 `parse_failed` 或 `index_failed`。

验收标准：

- 不允许长期无解释停留在 `parse_pending`。
- 失败态必须带 `status_evidence`、`status_source`、`status_confirmed_at`。
- 前端显示状态必须反映后端真实生命周期。

## 5. P0 问题三：ToolGateway 没有全线接管工具执行

## 5.1 现象

项目已经有 `ToolGateway`，但用户看到的 Agent 能力、数据库能力、AIOps 能力仍可能不一致：

- profile 显示有工具，不代表 Agent 真会调用。
- Agent 能调用数据库工具，不代表页面有同样能力说明。
- AIOps planner / executor / replanner 的工具池和失败语义仍可能分散。

## 5.2 当前代码事实

当前已有基础：

- `ToolGateway.list_visible_tools()` 会按 `tool/use` 权限过滤。
- `ToolGateway.execute()` 会做权限校验、执行和审计。
- 数据库 read-only tools 已通过 `get_database_tool_gateway().execute()` 接入 RAG 工具。
- `ProfileService` 会聚合 gateway tools 和 database demo visibility。

## 5.3 架构原因

目标架构要求所有工具执行进入 `ToolGateway`。但当前仍存在三种能力面：

```text
HTTP capability
Agent bindable tools
ToolGateway executable tools
```

如果三者不是从同一个 Tool Catalog / ToolGateway Interface 派生，就会出现：

- 前端显示能用，Agent 不会用。
- Agent prompt 里有工具，权限未通过。
- AIOps 工具错误没有统一审计。
- MCP timeout / fallback 语义不一致。

## 5.4 解决办法

新增 `ToolExecutionFacade` 或加深现有 `ToolGateway` Adapter：

```text
Agent runtime
  -> ToolExecutionFacade
  -> ToolGateway
  -> ToolProvider Adapter
  -> local / MCP / DB / monitor / log tools
```

分阶段：

1. 统一工具目录：HTTP、profile、Agent bindable tools 都从同一个 catalog 派生。
2. RAG Agent 不直接维护工具池，只拿 `ToolGateway.get_bindable_tools(context)` 或专用 Adapter。
3. AIOps planner / executor / replanner 使用 `AIOpsToolCatalog`，底层仍经过 ToolGateway。
4. 工具错误统一进入 `AIOpsFailureSemantics` / `EnterpriseError`。

## 5.5 验证方式

```bash
uv run pytest tests/test_enterprise_tool_gateway.py tests/test_rag_database_tools.py tests/test_enterprise_database_e7.py -q --no-cov
uv run pytest tests/test_aiops_mcp_tool_cache.py tests/test_enterprise_gateway_routes.py -q --no-cov
```

验收标准：

- 未授权工具不出现在 profile、Agent bindable tools、ToolGateway visible tools。
- 已授权数据库工具执行一定经过 `ToolGateway.execute()`。
- AIOps 工具失败能在 audit / SSE / eval 中看到统一错误语义。

## 6. P1 问题四：知识问答内部缺少 Query Intent Router

## 6.1 现象

用户观察到两类相近问题得到完全不同结果：

- 问“中车长客数字化转型”时，Agent 把它当成普通开放问题，没有强制检索，于是模型自己先澄清。
- 问“相关文件有什么”时，命中了 prompt / tool description 中的 `list_knowledge_documents` 意图，于是能列出文档。

这说明当前知识问答链路主要依赖 LLM Agent 自己判断是否调用工具。用户问知识性问题时，系统没有先经过一个独立、可测试、可观测的 Query Intent Router 来判断：

- 是否应该查知识库。
- 应该查哪个知识库或部门。
- 应该列文件、检索片段、读取文件，还是普通聊天。
- 是否应该转到数据库、权限申请或 human review。

左侧“选择知识库 / 部门”的入口很重要，但它只是显式 scope 输入，不能替代 Query Intent Router。用户不选时，系统仍应在权限允许范围内自动判断；用户选了部门时，Router 应把这个选择作为强约束或强特征。

## 6.2 当前代码事实

当前已有基础：

- `app/tools/knowledge_tool.py` 已有 `list_knowledge_documents`、`retrieve_knowledge`、`read_knowledge_document` 三个知识库工具。
- `app/services/rag_agent_service.py` 使用 LangChain / LangGraph Agent，把知识库工具交给模型自行选择。
- `app/services/knowledge_search_service.py::KnowledgeSearchService` 已有 scoped / auto 的 KB 范围路由，但它服务于知识库工作台 search API，主要解决“查哪个 KB”，不是聊天问句的 list / retrieve / read 意图路由。
- `app/enterprise/routing/router.py::StrategyRouter` 已存在，但它是企业助手上层 `chat/rag/aiops/database/admin/human_review` shadow 路由，只记录建议路线，不解决 RAG 内部“列文件还是检索答案”的问题。

也就是说，项目已经有工具、KB scope 路由和上层 shadow 路由，但缺少知识问答内部的 Query Intent Router。

## 6.3 架构原因

当前链路更接近：

```text
用户问题
  -> RAG Agent prompt
  -> LLM 自行决定是否调用 list_knowledge_documents / retrieve_knowledge / read_knowledge_document
  -> 工具结果或直接回答
```

这个形状的问题是：

- 工具是否调用由大模型临场决定，不能稳定复现。
- “知识问答类”和“普通闲聊类”没有前置判定，容易把企业资料问题当成开放聊天。
- “文件清单类”和“知识问答类”没有前置区分，导致“相关文件有什么”能列文件，而“中车长客数字化转型”不一定检索。
- KB scope 选择和问句意图没有统一 Interface，左侧选择部门、auto 路由、权限可见文档、工具调用之间缺少同一份决策记录。
- 数据库类问题可能被 RAG 工具或普通聊天吞掉，也可能绕过 SafeSqlKernel 的预期路径。

## 6.4 解决办法

新增 `QueryIntentRouter` 和 `KnowledgeRetrievalOrchestrator`，把知识问答从“LLM 自行猜工具”改成“先路由、再编排、再生成回答”：

```text
用户问题 + 当前用户 + 左侧 KB/部门选择 + profile/capability
  -> QueryIntentRouter
      - document_list
      - knowledge_qa
      - document_read
      - plain_chat
      - database
      - permission_request
      - human_review
  -> KnowledgeRetrievalOrchestrator
      - list_knowledge_documents
      - retrieve_knowledge
      - read_knowledge_document
      - handoff_to_database / permission / human_review
  -> AnswerGenerator
```

第一版必须保守：

1. deterministic rules 是第一层，先稳定识别文件清单、知识问答、文件阅读、普通闲聊、数据库、权限申请等高频意图。
2. 左侧 KB / 部门选择进入 Router 输入，作为 `scope_source=user_selected`；未选择时使用 `scope_source=auto_visible`，只在用户可见范围内检索。
3. `KnowledgeRetrievalOrchestrator` 负责把 intent 映射到工具动作，不让 prompt 自己决定 list / retrieve / read。
4. 数据库类 intent 只做 handoff，实际执行仍必须经过 `ToolGateway`、`SafeSqlKernel`、数据库权限和 confirmation / human review。
5. v1 不依赖小 LLM，先用 rules-only router 覆盖当前用户可见问题。
6. 小 LLM 作为 v2 第二层意图识别，只在规则低置信度或冲突时触发。
7. 小 LLM 必须通过 LangChain / 现有 `ModelGateway` 封装为 structured output classifier，不能直接在 route 或 prompt 里散写网络调用。
8. 如果后续进入 LangGraph，Router 应作为 RAG 子图或 supervisor/router node，并通过 conditional edges 分发到 `document_list`、`knowledge_qa`、`document_read`、`database`、`permission_request`、`plain_chat`、`human_review` 节点。

小 LLM 是否需要：

- 后续需要，但不进入 v1 最小验收。
- v2 推荐作为 classifier / judge：对 rule intent 做二次判断，产出 `intent`、`knowledge_action`、`confidence`、`reason`。
- 小 LLM 未配置、超时或输出不合法时，必须降级到 deterministic rules，不允许请求失败。
- 小 LLM 不能直接执行数据库写、授权、删除、生产操作；它只能给 Router 提供结构化判断，后续仍走权限、工具和 human review 边界。

上层能力路由 shadow 的后续计划：

- `StrategyRouter` 继续保持 enterprise 级 shadow-only 定位，只记录 `chat/rag/aiops/database/admin/human_review` 的建议路线和审计证据。
- 第一版和当前整改阶段不把 `StrategyRouter` 做成 active execution router，也不新增 `StrategyRouterActiveGate`。
- 这个上层路由不用于解决“中车长客数字化转型是否应该检索”“相关文件有什么是否应该列文件”这类知识库内部问题；这些问题由 `QueryIntentRouter` / `KnowledgeRetrievalOrchestrator` 负责。
- 后期计划明确为暂不排期、默认不开启。只有以后重新明确提出“让企业助手自动判断该进入知识库、数据库、AIOps 还是管理入口”的跨能力自动分流需求时，再单独评估是否从 shadow 进入 gated active。
- 即使未来重新评估 active，上线前也必须先满足这些条件：RAG 内部 Router 稳定、ToolGateway 全线接管工具、数据库写入 / DDL / 授权继续走 confirmation 或 human review、AIOps failure semantics 稳定、shadow audit 的误路由率可接受。

建议的 Query Intent 决策字段：

```json
{
  "intent": "knowledge_qa",
  "knowledge_action": "retrieve",
  "provider": "rules|classifier|llm_classifier",
  "selected_kb_ids": ["process_digital_dept"],
  "selected_doc_ids": [],
  "scope_source": "user_selected|auto_visible",
  "confidence": 0.86,
  "requires_retrieval": true,
  "handoff": null,
  "fallback_intent": "plain_chat",
  "reason": "企业资料知识问答，应检索流程与数字化部可见资料"
}
```

## 7. P1 问题五：权限申请入口过窄

## 7.1 现象

普通用户前端主要只能申请知识库。用户担心 tool、database 等权限怎么办。

## 7.2 当前代码事实

后端 `PermissionRequestService` 支持：

```text
document
tool
database
knowledge_base
```

`ResourceCatalogService` 也能列出知识库、文档、工具、数据库资源。

问题主要在前端产品化入口：为了简化知识库场景，把普通用户入口收窄成 KB 快捷申请。

## 7.3 架构原因

资源模型是通用的，但 UI 把一个快捷场景当成了完整权限系统。

这会造成两个问题：

- 用户以为系统没有 tool / database 权限申请能力。
- 管理员看到的是通用资源，普通用户看到的是 KB 专用表单，认知不一致。

## 7.4 解决办法

前端拆两个入口：

```text
权限申请
  - 知识库快捷申请
      - 知识库
      - 访问级别：部门资料
      - 理由
  - 高级资源申请
      - 资源类型：tool / database / document
      - 资源
      - action
      - 理由
```

后端不需要为此新增资源模型，只需要继续使用 `PermissionRequestService.list_requestable_resources()`。


- admin 审批后 grant 进入同一 `PermissionService`。
- 申请页面不允许绕过 catalog 手写不存在的 resource。

## 8. P1 问题六：admin 和普通用户知识库入口不一致

- `static/knowledge-console.js`
- `static/admin-console.js`
- `static/enterprise-dashboard.js`

同时增加 `/api/capabilities/health` 或等价只读聚合接口：

```json

  "profile": "ok",
  "knowledge_base_api": "ok",
  "document_worker": "degraded",

```

## 9. P1 问题七：会话历史不是企业级可恢复

## 9.1 现象

普通用户对话后没有历史记录，但 admin 有历史对话；或者浏览器切换账号后历史表现不一致。

## 9.2 当前代码事实

当前已有基础：

- `SessionOwnershipService` 防止跨用户访问同一个 session。
- 前端历史已经按 `chatHistories:${user_id}` 存在 localStorage。
- `/api/chat/session/{session_id}` 和 `/api/chat/clear` 有 owner guard。
- LangGraph checkpointer / session accessor 能读部分运行时历史。

## 9.3 架构原因

当前会话事实分散在三处：

```text
frontend localStorage
LangGraph checkpointer / MemorySaver
process-local SessionOwnershipService
```

这不是企业级会话 Module。问题包括：

- 换浏览器或清缓存后历史丢失。
- 服务重启后进程内 ownership 丢失。
- RAG chat、AIOps session、Memory ingestion 的历史口径不统一。
- 前端 localStorage 只是缓存，却承担了“历史列表事实来源”。

## 9.4 解决办法

新增 `SessionAccess` 和持久会话库：

```text
ChatSessionRepository
  - create_or_touch()
  - append_message()
  - list_by_user()
  - get_messages()
  - delete_or_archive()

SessionAccess
  - claim_or_assert_owner()
  - assert_read()
  - assert_write()
  - audit_denial()
```

迁移策略：

1. 先保留 localStorage 作为缓存。
2. 服务端成为历史列表事实来源。
3. 前端加载历史先查服务端，失败才降级 localStorage。
4. AIOps session 使用同一 owner / access 规则。

## 9.5 验证方式

```bash
uv run pytest tests/test_enterprise_gateway_routes.py tests/test_assistant_frontend_optimization.py -q --no-cov
node --test tests/js/test_static_app_aiops.mjs
```

新增验收：

- 普通用户刷新页面后历史仍存在。
- 换浏览器登录后能看到自己的历史。
- A 用户不能读取 B 用户 session。
- 服务重启后 owner 关系不丢失。

## 10. P1 问题八：数据库能力没有形成产品、Agent、评测闭环

## 10.1 现象

数据库页可能显示 not found 或没有 sample DB；同时数据库 Agent 评测当前主要证明 reference runner，不证明真实 LLM Agent 工具调用质量。

## 10.2 当前代码事实

当前已有基础：

- `/api/database/catalog` 已存在。
- `ProfileService.database_demo` 能展示数据库可见性。
- read-only database tools 已接入 RAG Agent，并通过 `ToolGateway.execute()` 执行。
- `SafeSqlKernel`、operation permission、confirmation、audit 已有较多测试。
- 数据库 2.0 runner 已有 SQLite reference execution。

## 10.3 架构原因

数据库能力目前有三张脸：

```text
前端 catalog/schema 展示
HTTP safe_select / operation routes
Agent database tools
```

它们共享部分底层安全 Module，但缺少统一 capability health 和 live Agent eval。

因此会出现：

- 页面显示数据库不可用，但 Agent 可能有工具。
- reference runner 能过，但真实模型不一定会正确选择工具。
- tool trace、SQL、DB diff、audit 没有在同一个评测报告里闭环。

## 10.4 解决办法

补齐两件事。

第一，数据库 capability health：

```json
{
  "database_catalog": "ok",
  "visible_databases": ["sandbox_sales"],
  "visible_tools": ["database_demo.safe_select"],
  "safe_sql_kernel": "ok",
  "write_operations_enabled": true,
  "confirmation_required_for": ["delete", "drop_table"]
}
```

第二，live DB Agent eval：

```text
question
  -> Agent
  -> tool_call trace
  -> generated SQL
  -> ToolGateway
  -> SafeSqlKernel / operation checker
  -> DB diff
  -> audit event
  -> rubric score
```

## 11. P2 问题九：SourceRef / ChunkEvidence 分散

## 11.1 现象

RAG citation 是否可靠，目前依赖多个地方都正确拼出 `kb_id/doc_id/chunk_id/source_ref`。

## 11.2 架构原因

这些字段在多个地方被创建或消费：

- parser / artifact。
- vector index。
- sparse search。
- hybrid merge。
- rerank。
- knowledge tool artifact。
- citation verifier。
- RAG eval。

只要一个环节丢字段，最终就会表现为引用不可靠、跨部门证据难查、eval 无法定位。

## 11.3 解决办法

新增 `ChunkEvidenceMapper`：

```text
ChunkEvidenceMapper
  - from_index_metadata()
  - from_sparse_hit()
  - from_vector_hit()
  - from_retrieval_result()
  - to_source_ref()
  - validate_required_fields()
```

原则：

- citation、retrieval result、knowledge tool artifact、eval evidence 使用同一 shape。
- 缺必填字段时早失败，不在前端或评测阶段才发现。
- rerank 后必须保留 evidence，不允许只剩 text。

## 11.4 验证方式

```bash

```

新增验收：

- 每个 retrieval result 都有 `source_ref.kb_id/doc_id/chunk_id`。
- sparse-only、dense-only、hybrid、rerank 路径字段一致。
- RAG eval 能按 source_ref 回查原始文档。

## 13. P2 问题十一：AIOps 工具池和失败语义仍需加深

## 13.1 现象

## 13.2 架构原因

```text
AIOpsToolCatalog

  - bindable_tools(context)
  - required_tools_for_scenario(scenario)

AIOpsFailureSemantics
  - classify_exception()
  - to_degradation_event()
  - to_sse_error()
  - to_audit_metadata()
```

## 14. 推荐整改路线

## 14.1 P0：先让问题可定位

1. RAG diagnostics。
2. DocumentProcessingWorkflow / worker health。
3. Tool Execution Seam。
4. admin / 普通用户 capability health smoke。

这一步目标不是立刻提升回答质量，而是把“哪里坏了”变成系统能回答的问题。

## 14.2 P1：修产品入口和持久状态

1. QueryIntentRouter + KnowledgeRetrievalOrchestrator：把知识库问答从 LLM 自行判断工具调用，改为可验证的 list / retrieve / read / chat / database 路由。
2. 权限申请拆成 KB 快捷申请和高级资源申请。
3. 前端 EnterpriseApiClient。
4. SessionAccess + 持久 ChatSessionRepository。
5. 数据库 capability health。

这一步目标是让用户入口和后端真实能力一致。

## 14.3 P2：补证据和评测闭环

1. ChunkEvidenceMapper。
2. RAG 20 题评分闭环。
3. live DB Agent eval。
4. AIOps failure semantics。

这一步目标是让 RAG、DB、AIOps 的质量可量化、可复现、可回归。

## 15. 每个问题的最小验收矩阵

| 问题 | 最小验收 |
|---|---|
| RAG 无命中 | API 返回 no_result_reason 和分层 diagnostics |
| PDF 卡状态 | 最终进入 indexed / parse_failed / index_failed，并展示 worker health |
| ToolGateway 绕行 | Agent bindable tools 和 ToolGateway visible tools 一致 |
| 知识问答意图路由缺失 | query intent decision 能稳定区分 document_list / knowledge_qa / document_read / plain_chat / database；v1 rules-only 可验收，小 LLM 作为 v2 classifier 未配置也不影响主链路；决策进入 diagnostics / audit |
| 权限申请过窄 | 普通用户可申请 KB / tool / database |
| admin 工作台不可用 | capability health 能区分旧端口、未登录、无权限、接口缺失 |
| 会话历史不可靠 | 服务端持久历史，跨浏览器可恢复，跨用户不可读 |
| 数据库能力不闭环 | catalog / profile / tool / audit / eval 一致 |
| SourceRef 分散 | 所有 retrieval result 都有统一 evidence shape |
| 原始资料未闭环 | reviewed import 后 RAG eval 有真实得分 |
| AIOps 失败语义分散 | SSE / audit / eval 对同一失败语义一致 |

## 16. 不建议现在做的事

- 不建议为了一个页面问题绕过 `PermissionService` 或 `DocumentAccessService`。
- 不建议在 Agent prompt 里硬写权限和工具规则来替代 `ToolGateway`。
- 不建议继续只靠 Agent prompt 让大模型自行决定是否调用知识工具；v1 应先用 deterministic rules 覆盖当前核心问法，小 LLM 作为 v2 classifier 时也不能直接执行高风险路线，必须通过 LangChain / ModelGateway 的结构化输出进入 QueryIntentRouter，再经过权限、工具和 human_review 边界。
- 不建议跳过小样本 smoke 直接全量导入资料。
- 不建议把 localStorage 历史当作企业会话事实来源。
- 不建议在 RAG 无命中原因不清楚前调整 embedding / rerank。
- 不建议把数据库 reference runner 结果说成 live LLM Agent 能力已通过。
- 不建议为了消除 `parse_pending` 直接把状态伪装成成功。

## 17. 最终结论

项目现在最重要的问题不是“少几个页面按钮”，而是多个能力已经存在，但还没有全部收敛到长期架构基线：

```text
RequestGateway
  -> Permission / Resource
  -> Domain Module
  -> ToolGateway / SafeSqlKernel / Retrieval
  -> Data / Queue / Index
  -> Audit / Eval
```

下一步最应该先做的是 P0：

1. RAG diagnostics。
2. DocumentProcessingWorkflow / worker health。
3. Tool Execution Seam。
4. capability health smoke。

这四项完成后，用户看到的“无命中”“等待解析”“not found”“工具不能用”“历史不一致”才会变成可定位、可验证、可回归的问题，而不是每次靠人工猜是哪一层出了问题。

P0 完成后，P1 中最先做 `QueryIntentRouter` 和 `KnowledgeRetrievalOrchestrator`。原因是用户当前最直接看到的问题发生在知识问答内部：同类问题有时检索、有时普通聊天、有时列文件。只有先把 list / retrieve / read / chat / database 的决策从 prompt 中抽出来，后续权限申请、数据库 live Agent eval、AIOps 工具目录和上层 `StrategyRouter` 才不会继续依赖用户手动选入口或模型临场猜测。

上层 `StrategyRouter` 的 active 化不进入当前后续计划。它只保留 shadow 观测价值：记录系统“本可以”把请求分到哪个大能力入口，供审计、评测和未来对照使用。后续如果重新想起并明确需要“跨能力自动分流”，再单独开方案评估；在此之前不默认开启、不做 active gate、不把它作为解决知识库问答不稳定的主路径。
