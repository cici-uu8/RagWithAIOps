# 助手优化 1

## 0. 结论

这轮真实对话暴露的问题不是单一 bug，而是“后端能力、Agent 工具、前端体验、权限可见性”之间没有打通。

当前系统已经有不少底层能力，例如认证、权限、知识库 metadata、RAG 检索、数据库 sandbox、Admin API。但前端聊天页仍像一个普通匿名聊天框，用户不知道自己是谁、能看哪些知识库、能用哪些工具；Agent 也不知道如何回答“知识库里有什么文件”这类元数据问题。

优化目标应该从“能对话”升级为“可解释、可发现、可验证的企业助手”。

## 1. 从真实对话看到的问题

### 1.1 能力回答不准确

用户问“你能干什么”时，助手回答了日志查询、性能监控、时间查询、知识检索、地区信息查询等能力。

问题在于：

- 回答没有说明这些能力是否对当前用户可用。
- 没有说明哪些能力需要权限。
- 没有说明数据库能力当前是否只在 database-demo / 权限控制下可用。
- 没有给出当前用户可见的知识库、工具、模型或功能列表。

这会造成用户以为“系统说有这个能力，我就应该能直接用”，但实际可能被权限、工具注册、前端入口或 session 类型限制。

### 1.2 知识库检索和知识库清单混在一起

用户问：

```text
帮我检查现在的知识库中都有关于什么的资料
现在知识库中有什么文件呢？
enterprise_guide_runbook 讲了什么？
```

助手都没有给出有效答案。

代码事实：

- Agent 目前有 `retrieve_knowledge`，用于按问题检索知识库内容。
- `retrieve_knowledge` 走 `RetrievalService`，再走 Milvus 向量检索和 BM25 稀疏检索。
- metadata store 已经有 `knowledge_metadata_store.list_documents()`。
- 但是没有公开的 `GET /api/documents` 列表接口。
- 也没有 Agent 工具 `list_knowledge_documents`。

因此当前系统能“搜内容”，但不能“列目录”。

本地 metadata 中实际存在文档记录，例如：

```text
x.md                           kb_id=default  status=indexed
x.md                           kb_id=          status=indexed
x.md                           kb_id=default  status=indexed
enterprise_guide_runbook.md    kb_id=guide    status=indexed
```

用户问文件清单时，正确答案应该来自 metadata，而不是让大模型猜。

### 1.3 文件名检索弱

用户问 `enterprise_guide_runbook 讲了什么？`，系统仍回答没有找到。

可能原因：

- 当前检索主要面向 chunk 内容，不是文件名精确查找。
- 文件名、doc_id、kb_id、title 等 metadata 没有作为独立检索入口暴露给 Agent。
- 用户输入的是文件 stem `enterprise_guide_runbook`，实际文件名是 `enterprise_guide_runbook.md`，系统没有做文件名归一化匹配。

这说明需要区分三类查询：

| 用户问题类型 | 应该走的能力 |
|---|---|
| “知识库里有哪些文件” | 文档清单 / metadata 查询 |
| “某个文件讲了什么” | 文件名匹配 + 按 doc_id 检索或摘要 |
| “某个主题怎么处理” | 内容检索 `retrieve_knowledge` |

### 1.4 数据库能力状态对用户不可见

用户问“有没有操作数据库的能力”，助手回答“没有直接操作数据库的功能”。

代码事实并不是这么简单：

- E6/E7 已有 Sandbox DB、SafeSqlKernel、DatabaseDemoToolProvider、表列级权限过滤。
- 但默认 AIOps/RAG 工具池不应该直接暴露 database tools。
- database-demo 能力需要通过权限和 session/工具可见性控制。

因此更准确的产品表达应该是：

```text
系统底层有受限的只读数据库 demo 能力，但当前聊天会话不一定有权限使用。
如果你需要数据库查询，需要切换到 database-demo 能力或由管理员授权。
```

现在的前端和 Agent 没有展示“当前会话可用工具”，所以用户无法判断数据库能力到底是不存在、未授权，还是当前入口没接。

### 1.5 前端缺少企业用户身份感

当前聊天页左侧只有：

- 应用名
- 新建对话
- 近期对话

缺少：

- 登录入口
- 当前用户
- 是否 admin
- 角色列表
- 部门
- 可见知识库 id
- 可用工具
- 可用模型
- 可用功能开关
- 退出登录

这会让企业权限体系变成“后端存在，但用户感知不到”。

### 1.6 前端请求仍是匿名体验

当前 `static/app.js` 中：

```text
apiBaseUrl = http://localhost:9900/api
```

聊天请求直接调用 `/api/chat`，没有明显的登录 token 注入、用户态展示和权限可见性刷新。

这意味着：

- 用户不知道当前请求是匿名、demo_user 还是 admin。
- RequestContext 可能只能靠默认 header 或后端默认值。
- 前端无法解释为什么某些功能不可见或不可用。

## 2. 根因分析

### 2.1 后端能力是分层完成的，前端还没有产品化

E0-E11 和 F1-F8 更偏后端治理闭环：

- Auth
- RequestGateway
- PermissionService
- ToolGateway
- ModelGateway
- RAG
- DB sandbox
- Admin API
- Observability
- Dashboard
- Verifier / Error Recovery / HITL

这些能力大多已经有服务层或 API 层验证，但聊天前端仍是旧的“OnCall 问答框”。因此用户看到的是一个简单聊天窗口，而不是完整企业助手控制台。

### 2.2 Agent 工具不是能力目录

`retrieve_knowledge` 是内容检索工具，不是知识库管理工具。

它适合回答：

```text
某个告警怎么排查？
某个 runbook 中提到什么步骤？
某段故障信息对应哪些知识？
```

它不适合回答：

```text
知识库中有哪些文件？
每个知识库 id 有多少文档？
我能看哪些知识库？
某个文件是否已经 indexed？
```

这些应该由 metadata / registry / permission API 提供。

### 2.3 权限结果没有被产品化展示

E3 已经有 PermissionService，E8 已经有 Admin API，但普通用户前端没有一个“我的权限”视图。

用户真正关心的是：

```text
我是谁？
我是 admin 还是普通用户？
我属于哪个部门？
我能看哪些知识库？
我能用哪些工具？
我能查数据库吗？
为什么这个功能不能用？
```

当前系统没有把这些答案直接显示出来。

## 3. 优化目标

### 3.1 用户视角目标

用户打开前端后，应该立即知道：

- 当前是否已登录。
- 当前用户是谁。
- 当前角色和部门是什么。
- 当前能访问哪些知识库。
- 当前能使用哪些功能。
- 哪些功能不可用，以及为什么不可用。

用户问“你能干什么”时，助手应该回答“当前用户实际可用的能力”，而不是泛泛描述系统潜在能力。

### 3.2 系统视角目标

系统应该支持：

- 权限感知的能力发现。
- 知识库文档清单查询。
- 文件名 / doc_id / kb_id 精确检索。
- 前端登录态和权限态展示。
- 能力不可用时给出可解释原因。

## 4. 优化方案

## P0：修正能力感知和前端基础状态

### P0.1 左下角用户入口

在页面左下角增加类似 ChatGPT 的用户入口。

这个入口只显示“当前是谁”，不要把角色、部门、权限、知识库等详细信息直接铺在左下角，避免主界面变得拥挤。

展示内容：

```text
头像 / initials
用户名
```

未登录时显示：

```text
未登录
```

交互：

- 点击左下角用户入口后打开用户菜单。
- 菜单包含：
  - 个人资料
  - 我的权限
  - 可用功能
  - 可见知识库
  - 管理后台入口（仅 admin 显示）
  - 退出登录

个人资料弹层再展示完整信息：

```text
用户名
用户 ID
角色：admin / user
部门：dept_1 / Department 1
可见知识库 id
可用工具
不可用功能及原因
```

依赖 API：

```text
POST /api/auth/login
GET  /api/auth/me
GET  /api/auth/protected
POST /api/auth/logout
```

前端需要保存 JWT token，并在后续请求中带：

```text
Authorization: Bearer <token>
```

注意：`Authorization` 只负责把登录 token 传给后端。后端必须验证 token 后生成可信的 `RequestContext`，不能依赖前端自己传 `X-User-Id`、`X-Roles` 这类身份头来判断权限。

验收标准：

- 左下角未登录态只显示“未登录”，不能误导用户为 admin。
- 左下角登录态只显示头像 / initials 和用户名。
- 登录 admin 后，完整角色信息只在“个人资料 / 我的权限”弹层中显示。
- 登录 demo_user 后，部门、角色、可见知识库只在“个人资料 / 我的权限”弹层中显示。
- 退出登录后 token 清理，后续 protected API 返回 401。
- 聊天、上传、AIOps 请求都能基于已验证 token 得到正确 `RequestContext`。

#### 登录流程细节

初始状态：

- 页面加载时检查 `localStorage` 是否有 token。
- 有 token 时调用 `/api/auth/me` 验证。
- 验证成功后，左下角显示当前用户名，并异步拉取 `/api/me/profile`。
- 验证失败后，清除 token，左下角显示“未登录”。
- 无 token 时，左下角显示“未登录”。

未登录体验：

- 可以发送普通聊天请求，作为匿名体验。
- 不能访问“我的权限”“个人资料”“管理后台”等需要身份的功能。
- 点击需要身份的功能时提示登录。

登录入口：

- 点击左下角“未登录”打开登录弹窗。
- 登录成功后保存 token，刷新 `/api/auth/me` 和 `/api/me/profile`。

Token 过期处理：

- 任一 API 返回 401 时，前端清除 token。
- 显示“登录已过期，请重新登录”。
- MVP 不做自动刷新 token，过期后要求用户重新登录。

多标签页同步：

- 使用 `window.addEventListener('storage', ...)` 监听 token 变化。
- A 标签页登出后，B 标签页自动清除本地用户态并显示“未登录”。

### P0.2 当前用户 Profile 和可用能力面板

在用户菜单里增加“可用功能”。

显示：

```text
知识库问答：可用
文件上传：可用 / 不可用
AIOps：可用 / 不可用
数据库查询：未授权 / database-demo 可用
管理后台：仅 admin 可用
执行看板：可用
```

这个面板不能硬编码，应该来自后端能力发现 API。

建议新增聚合接口：

```text
GET /api/me/profile
```

返回示例：

```json
{
  "user": {
    "user_id": "user_demo_dept1",
    "username": "demo_user_dept1",
    "roles": ["user"],
    "department_id": "dept_1",
    "department_name": "Department 1"
  },
  "visible_tools": [
    "retrieve_knowledge",
    "list_knowledge_documents"
  ],
  "visible_kb_ids": ["default", "guide"],
  "feature_flags": {
    "rag_chat": true,
    "file_upload": true,
    "aiops": true,
    "admin": false,
    "database_demo": false
  },
  "unavailable_reasons": {
    "admin": "requires_admin_role",
    "database_demo": "permission_denied"
  }
}
```

接口边界：

- `user` 来自已验证的 E1 auth token。
- `visible_tools` 需要合并 RAG 本地工具、MCP / ToolGateway 可见工具、database-demo 工具状态；不能假设 `ToolGateway` 是所有工具的唯一来源。
- `visible_kb_ids` 来自当前用户可见文档的 `kb_id` 聚合。
- `feature_flags` 是产品展示字段，不替代 E3 `PermissionService` 的最终权限检查。
- 数据库能力要区分“系统底层支持”和“当前用户已授权”。

#### `visible_tools` 聚合逻辑

`visible_tools` 是 Agent 可用工具的细粒度列表，需要合并多类来源：

1. 本地 RAG 工具，不经过 `ToolGateway`：
   - `retrieve_knowledge`
   - `list_knowledge_documents`
2. MCP 工具，经过 `ToolGateway.list_visible_tools(context)` 权限过滤。
3. Database 工具，经过 database-demo provider 和 `PermissionService` 检查：
   - 只有当前用户具备 database-demo 工具权限，并且至少有一个可见表/列权限时，才返回 `database_demo.*` 工具。
4. Admin 能力：
   - 只有 `admin` 角色显示管理入口；如果后续存在 admin tool，也应单独登记，不能和普通工具混在一起猜。

聚合伪代码：

```python
def build_profile_visible_tools(context: RequestContext) -> list[str]:
    tools = ["retrieve_knowledge", "list_knowledge_documents"]

    tools.extend(tool.resource_id for tool in tool_gateway.list_visible_tools(context))

    if has_database_demo_access(context):
        tools.extend([
            "database_demo.list_tables",
            "database_demo.describe_table",
            "database_demo.safe_select",
        ])

    return sorted(set(tools))
```

#### `feature_flags` 和 `visible_tools` 的区别

- `feature_flags` 是前端展示用的粗粒度功能开关。
  - `rag_chat` 控制是否显示知识库问答入口。
  - `file_upload` 控制是否显示上传按钮。
  - `aiops` 控制是否显示 AIOps 诊断入口。
  - `admin` 控制是否显示管理后台入口。
  - `database_demo` 控制是否显示数据库查询入口。
- `visible_tools` 是 Agent / 个人资料中展示的细粒度工具列表。
  - 前端主界面不要直接用它铺 UI。
  - 可用于 Agent system prompt 注入。
  - 可在“我的权限 / 可用工具”详情里展示。
- 二者关系：
  - `feature_flags.rag_chat = true` 通常意味着 `visible_tools` 包含 `retrieve_knowledge`。
  - `feature_flags.database_demo = true` 通常意味着 `visible_tools` 包含 `database_demo.*`。
  - `feature_flags` 是 `visible_tools` 和角色/权限状态的产品化聚合视图。
- 权限判断：
  - 前端只用 `feature_flags` 控制入口显示。
  - 后端仍以 `PermissionService`、`ToolGateway`、database provider 的实时检查为准。
  - `feature_flags` 和 `visible_tools` 都不能替代后端权限检查。

验收标准：

- 普通用户不能看到 admin 能力为可用。
- 未授权数据库能力显示“未授权”，不是“系统没有这个能力”。
- admin 能看到管理入口。
- 前端展示来自 `/api/me/profile`，不维护一份独立的 capability 映射表。
- 后端权限判断仍以 `PermissionService` 和各 gateway/provider 为准。

## P1：补知识库文档清单能力

### P1.1 新增文档列表 API

新增：

```text
GET /api/documents
```

查询参数：

```text
kb_id 可选
status 可选，仅 admin/debug 场景使用；普通用户默认只看 indexed
limit 可选
offset 可选
```

返回字段：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "documents": [
      {
        "doc_id": "doc_854...",
        "kb_id": "guide",
        "file_name": "enterprise_guide_runbook.md",
        "status": "indexed",
        "parser_engine": "plain_text",
        "created_at": "...",
        "updated_at": "..."
      }
    ]
  }
}
```

权限要求：

- 普通用户只能看到有权限的 document。
- admin 可以看到全部。
- 需要复用 E3 PermissionService 的 document resource 权限。
- 普通用户默认只返回已成功索引的文档，避免把 pending/failed 等内部状态暴露给 Agent 作为主要对话入口。

验收标准：

- `GET /api/documents` 能列出 metadata 中已 indexed 的文档。
- 未授权文档不会出现在列表。
- 返回中包含 `kb_id/file_name/status/doc_id`。
- admin/debug 查询可以带 `status` 看处理状态，普通对话工具不暴露该参数。

### P1.2 新增 Agent 工具 `list_knowledge_documents`

新增工具：

```text
list_knowledge_documents(kb_id?: string)
```

作用：

- 回答“知识库里有什么文件”
- 回答“某个 kb_id 里有哪些文档”
- 回答“当前用户可见的 indexed 文档有哪些”

返回不要给全文，只给结构化清单。

工具返回示例：

```json
{
  "documents": [
    {
      "doc_id": "doc_854...",
      "file_name": "enterprise_guide_runbook.md",
      "kb_id": "guide",
      "created_at": "2026-05-31T10:00:00Z"
    }
  ],
  "total": 1,
  "kb_ids": ["guide"]
}
```

工具边界：

- 只返回当前用户有权限查看的文档。
- 只返回已成功索引、可用于问答的文档。
- `status` 仍可在 HTTP 管理/调试接口中存在，但不作为 Agent 工具参数暴露。
- 如果指定 `kb_id` 且当前用户无该知识库权限，返回空列表并附带无权限说明，不要把无权限和空知识库混为一谈。

权限过滤逻辑：

- 不指定 `kb_id`：返回当前用户所有可见文档。
- 指定 `kb_id`：
  - 有该 `kb_id` 权限时，返回该知识库的可见文档。
  - 无该 `kb_id` 权限时，返回空列表 + `message`，例如“你没有权限查看知识库 'default'”。

验收标准：

- 用户问“现在知识库中有什么文件呢？”时，助手调用 `list_knowledge_documents`。
- 回答中列出文件名、kb_id，并说明这些文档均为已索引可问答状态。
- 如果确实没有文档，明确说“当前用户可见文档为空”，而不是泛泛让用户提供关键词。

## P2：补文件名精确检索

### P2.1 文件名归一化匹配

新增文件名查找服务：

```text
find_document_by_name(name: str)
```

匹配规则：

- 精确匹配 `enterprise_guide_runbook.md`
- stem 匹配 `enterprise_guide_runbook`
- 忽略大小写
- 支持下划线、短横线、空格的弱归一化

验收标准：

- 用户问 `enterprise_guide_runbook 讲了什么？` 能找到 `enterprise_guide_runbook.md`。
- 找到文件后，按 doc_id 限定 `retrieve_knowledge` 的检索范围。

### P2.2 增强 `retrieve_knowledge` 的文件限定能力

第一阶段不新增 `summarize_knowledge_document` 工具。原因：

- “某个文件讲了什么”本质上可以先通过“文件名匹配 + 限定范围检索”解决。
- 工具数量越多，Agent 越容易在 `retrieve_knowledge`、`list_knowledge_documents`、`summarize_knowledge_document` 之间混淆。
- 长文档摘要质量需要单独 eval，当前真实问题还没有证明必须新增摘要专用工具。

建议先扩展现有工具：

```text
retrieve_knowledge(
  query: string,
  knowledge_base_ids?: string[],
  file_name?: string,
  doc_id?: string,
  top_k?: int
)
```

处理逻辑：

```text
文件名匹配
→ 权限检查
→ 解析出 doc_id / allowed_document_ids
→ 调用 RetrievalService 时限定该文档范围
→ 返回该文档相关 chunk、source_ref、kb_id、doc_id
```

如果用户只问“这个文件讲了什么”，可以把 query 归一化为“总结这份文档的主题、关键步骤和可追问问题”，但仍通过 `retrieve_knowledge` 这一条工具链完成。

验收标准：

- 用户问“某个文件讲了什么”时，不再走全库无约束召回。
- 回答引用对应文件名和 kb_id。
- 无权限时明确说“你没有权限查看该文档”。
- 不新增摘要专用工具，除非后续 eval 证明长文档摘要是独立瓶颈。

## P3：修正“你能干什么”的回答方式

### P3.1 能力回答必须基于当前用户

用户问：

```text
你能干什么？
我有什么权限？
我能查数据库吗？
```

助手应基于当前请求的 profile 信息回答，而不是自由发挥，也不需要新增 `get_current_user_capabilities` 工具。

建议做法：

1. 前端登录后调用 `/api/me/profile` 展示用户信息。
2. 后端处理聊天请求时，基于已验证 token 创建 `RequestContext`。
3. Agent 每次请求注入一段只用于体验解释的 profile 摘要，例如当前用户、角色、部门、可见知识库、可用工具、不可用功能原因。
4. profile 摘要只用于回答“我是谁 / 我能用什么”，不能替代后端权限检查。

示例 system prompt 片段：

```text
当前用户：
- username: demo_user_dept1
- roles: user
- department: Department 1
- visible_kb_ids: guide, default
- visible_tools: retrieve_knowledge, list_knowledge_documents
- unavailable: database_demo(permission_denied), admin(requires_admin_role)

当用户问“你能干什么”或“我有什么权限”时，只根据以上当前用户信息回答。
如果用户请求不可用功能，明确说明当前未授权或当前入口未启用，不要说系统完全没有该能力。
```

验收标准：

- 普通用户问“有没有操作数据库的能力”，回答应区分：
  - 系统是否支持
  - 当前用户是否授权
  - 当前会话是否开启 database-demo
- 不再泛泛说“我没有数据库能力”或“我可以做一切数据库相关任务”。
- 权限变更、登录切换或会话刷新后，profile 需要重新生成，避免长会话使用过期权限说明。

### P3.2 前端欢迎语不展示个人细节

首页欢迎区域可以保留简洁，不直接展示角色、部门、知识库 id 等个人信息。当前用户只通过左下角入口展示用户名，详细信息进入“个人资料 / 我的权限”查看。

如果需要在欢迎区提示能力，只展示粗粒度入口状态，不展示个人资料字段：

```text
可用：知识库问答、AIOps、文件上传
更多权限信息请打开左下角个人资料。
```

如果未登录：

```text
当前未登录。只能使用匿名体验能力。
```

## P4：数据库能力产品化展示

### P4.1 明确数据库能力状态

数据库能力不能只藏在后端测试里。前端应该展示：

```text
Sandbox 数据库：未授权 / 已授权
可见表：orders, incidents...
可见列：按权限过滤
只读模式：开启
禁止：INSERT / UPDATE / DELETE / DDL
```

### P4.2 数据库查询入口

可以先不做完整 SQL 编辑器，但至少应提供：

- 可见数据库工具状态。
- “进入 database-demo”入口。
- 安全说明：只允许 `safe_select`。
- 权限不足时引导找 admin 授权。

验收标准：

- 普通用户不会误以为系统完全没有数据库能力。
- 未授权用户不会看到可执行 SQL 的入口。
- 已授权用户能看到可查询表和列。

## P5：前端体验优化

### P5.1 页面结构

建议左侧栏只保留导航和会话，不再在左侧栏底部堆用户详情：

```text
智能OnCall助手

+ 新建对话

近期对话
- 你能干什么
- 知识库文件
```

建议页面左下角增加一个轻量用户入口：

```text
头像  demo_user_dept1
```

左下角入口只显示头像 / initials 和用户名；角色、部门、知识库、工具等信息不直接显示在主界面。

点击左下角入口弹出菜单：

```text
个人资料
我的权限
可见知识库
可用工具
管理后台（admin only）
退出登录
```

点击“个人资料”后再打开详情弹层：

```text
用户名
用户 ID
角色
部门
可见知识库 id
可用工具
不可用功能及原因
```

### P5.2 错误提示更具体

当前 `Failed to fetch` 对用户不可理解。

应改成：

```text
无法连接后端服务。请确认“启动企业助手.command”窗口仍然打开，或重新双击启动。
```

如果是 401：

```text
登录已过期，请重新登录。
```

如果是 403：

```text
你没有权限使用该功能，请联系管理员授权。
```

如果是 500：

```text
后端处理失败，请复制 trace_id 给开发者排查。
```

### P5.3 前端不要硬编码 API origin

当前前端写死：

```text
http://localhost:9900/api
```

建议改为相对路径：

```text
/api
```

好处：

- 通过 `127.0.0.1`、`localhost`、局域网 IP 或未来域名访问时不容易跨域失败。
- 更接近部署形态。

验收标准：

- `http://localhost:9900/` 可用。
- `http://127.0.0.1:9900/` 可用。
- 前端 fetch 不因 origin 不一致报错。

## 5. 推荐实施顺序

### 第一阶段：身份和基础体验

优先级最高，建议先做：

1. 前端错误提示优化，把 `Failed to fetch` 改成人话。
2. 前端 API base URL 改成相对路径 `/api`。
3. 登录弹窗。
4. 左下角用户入口，只显示头像 / initials 和用户名。
5. `/api/auth/me` 接入前端。
6. JWT token 保存、退出登录、401 过期处理。
7. 后端把 Bearer token 转成可信 `RequestContext`，聊天、上传、AIOps 不再依赖前端伪造身份头。
8. 新增 `GET /api/me/profile`，返回用户信息、可见工具、可见 kb_id、admin/database 状态。

回答必须区分系统支持、当前授权、当前可见表列。

## 7. 风险和边界

### 7.1 不要让 Agent 自己猜权限

权限、功能、知识库清单都应该来自后端结构化接口或工具，不应让模型根据提示词猜。

### 7.2 不要把“系统支持”说成“当前可用”

例如数据库能力：

```text
系统支持 sandbox DB 查询
```

不等于：

```text
当前用户可以查数据库
```

这两句话必须分开表达。

### 7.3 不要把检索失败等同于知识库为空

检索失败可能有多种原因：

- query 太泛。
- 文件名没有进入检索索引。
- 当前用户无权限。
- 文档存在但未 indexed。
- 检索召回失败。
- 工具没有被调用。

回答时应该说明是哪一种，而不是直接说“没有资料”。

## 8. 最小改造建议

如果只做一个最小闭环，我建议先做这 5 个：

1. 前端 API base URL 改成相对 `/api`，并优化 `Failed to fetch` 错误文案。
2. 前端左下角用户入口、登录、登出、token 过期处理。
3. `GET /api/me/profile`，由后端聚合用户、可见工具、可见 kb_id、admin/database 状态。
4. `GET /api/documents` 和 `list_knowledge_documents` Agent 工具。
5. 增强 `retrieve_knowledge`，支持 `file_name` / `doc_id` 限定检索。

做完后，用户最困惑的三类问题就能解决：

```text
我是谁？
我能用什么？
知识库里有什么？
```

这比继续堆更多后端能力更重要，因为当前最明显的短板是“能力不可见、权限不可见、知识库状态不可见”。
