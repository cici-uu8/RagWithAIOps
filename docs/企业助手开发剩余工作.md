# 企业助手开发剩余工作

最后更新：2026-05-31

## 1. 当前状态一句话

企业助手主线不是“还差很多基础功能”，而是“主线已经闭环，剩下的是带触发条件的生产化后续项”。

当前已完成：

- `E0-E11` 企业助手基础闭环已完成：身份、RequestGateway、权限、ToolGateway、ModelGateway、RAG/Upload 治理、sandbox DB、DB Gateway、Admin/API、Observability/Eval、Vue3 执行可视化。
- `F2a-F8` 企业开发 2.0 已完成：其中 `F1/F2a/F2b/F4/F5/F6/F3` 有实现，`F7/F8` 是按 gated 规则做了 evidence-only 收口。
- `DB-P0a/P0b/P1` 已完成：sandbox DB、Safe SQL Kernel、权限级 DB Gateway 已成立。
- Memory、RAG、AIOps 当前都保持冻结，除非有新的真实触发证据。

关系说明：

- `E0-E11` 是底座，解决“企业助手能被治理、审计、授权、展示”。
- `F1-F8` 是 2.0 增强，解决“复杂任务能被合同化、评估、自检、恢复、审批和观察”。
- 后续 backlog 不应该绕过 `E2 RequestGateway`、`E3 PermissionService`、`E9 SSE/Audit contract` 和已完成的 adapter 边界。

## 3. 关键词

- `shadow`：只记录和对比，不改变真实请求路径。
- `evidence-only`：只做证据审计，不写运行时代码。
- `trigger`：满足触发条件才启动，不满足就不做。
- `promote`：从只观察升级到真正接管默认路径。
- `frozen`：当前方向收口冻结，后续必须有新证据才重新打开。

## 6. 主要风险

### 6.1 把“常见成熟做法”误当成“当前需求”

高风险例子：

- 因为成熟项目有 reranker，就默认开启 rerank。
- 因为成熟项目有 embedding cache，就先做 cache。
- 因为成熟项目有 PII 检测，就不看样本直接写 DLP。
- 因为成熟项目有 persistent checkpointer，就替换 `MemorySaver`。

这些都必须先有触发证据。

### 6.2 把 shadow / evidence-only 误当成正式能力

- F3 现在只观察，不接管 route。
- F7/F8 是 evidence-only，不是 runtime 新能力。
- RAG-1/2/3/4 仍是 production readiness backlog，不是默认优化项。
- Memory 已冻结，不是继续扩 L3 / vector / hybrid 的默认队列。

### 6.3 真实企业数据风险

sandbox DB 只证明“可控演示”，不证明“真实库安全上线”。

进入 DB-P2 前，必须先解决：

- 只读账号。
- 表/列 allowlist。
- 数据和权限 owner。
- 脱敏规则。
- 生产审计路径。
- 权限绕过测试。

### 6.4 优化过早带来的复杂度

如果没有 baseline 就优化，后续很难判断收益来自哪里，也很难定位回归。

适用范围：

- RAG 排序优化。
- AIOps prompt/timeout 调整。
- 资源预算策略。
- Runtime checkpointer 替换。
- DB 多数据源扩展。

## 7. 如何判断 backlog 是否该重新打开

| Backlog | 先看什么 | 触发才做什么 | 没触发时 |
|---|---|---|---|
| F3 route promote | `routing_decision` audit、route comparison report、F2b eval | 冻结 match-rate 阈值，做 shadow → canary → default promote | 继续 shadow，不改默认路径 |
| F7 advanced guardrail | `docs/enterprise2_f7_guardrail_trigger_audit.md`、audit JSONL/SQLite、真实输出样本 | 先做 PII/DLP shadow provider，再人工复核误报/漏报 | 保持 E2 rule guardrail |
| F8 resource optimization | `docs/enterprise2_f8_resource_trigger_audit.md`、latency/token/tool/DB audit 指标 | 先做资源基线报告，再做内部 budget / selector | 不改模型、检索、DB、工具策略 |
| RAG-1/2/3/4 | `docs/rag_quality_audit_report_20260529.md`、真实用户反馈、新 eval corpus、规模指标 | 先开 RAG-1 reranker shadow/eval | 不做 broad rewrite |
| Runtime-1 | 部署形态、重启恢复需求、长会话/HITL/多副本要求 | 根据形态评估 SQLite 或 Postgres checkpointer | 保持 `MemorySaver` |
| DB-P2 | `docs/database_operation_capability_plan.md` 中的真实库、账号、owner、allowlist、masking、audit 条件 | 接一个最小只读源并做安全 smoke | sandbox DB 仍是唯一 DB 能力 |
| Memory | `docs/memory_fusion_development_record.md`、`docs/openviking_memory_p0_decision_table.md`、真实 oncall evidence | 补 Gate A.1 证据后再讨论 P7.6+ 或 prompt integration | Memory 保持冻结 |

## 8. 建议后续顺序

1. 先判断有没有新触发证据，不要从 backlog 清单反推开发任务。
2. 有路由样本，就先看 F3 是否能 promote。
3. 有 PII / 合规样本，就开 F7 shadow。
4. 有资源瓶颈，就开 F8 baseline。
5. 有真实企业只读库条件，就开 DB-P2。
6. 有新 RAG 质量或规模压力，就先开 RAG-1。
7. 有部署恢复需求，再开 Runtime-1。
8. 有真实 oncall memory 证据，再重新打开 Memory。

## 9. 一句话版

企业助手当前不是缺基础能力，而是进入“证据驱动的生产化后续阶段”。没有新证据时，正确动作是保持冻结；有新证据时，按对应 backlog 的第一动作小步打开。
