# 助手真实体验问题记录

## 0. 记录说明

本文记录开始真实体验企业助手聊天前端后发现的问题、原因分析和处理过程。

记录范围：

- 双击启动器体验。
- 前端聊天真实对话体验。
- 知识库问答体验。
- 数据库能力询问体验。
- 用户身份和权限可见性体验。

相关文档：

- `docs/助手优化 1.md`：后续优化方案。
- `docs/企业助手功能体验指南.md`：功能体验指南和跑通证据。
- `logs/frontend_verify/`：前端真实对话验证证据。

## 1. 体验时间线

### 1.1 第一轮：双击启动后前端报 `Failed to fetch`

用户在前端输入问题后，页面显示：

```text
抱歉，发送消息时出现错误：Failed to fetch
```

当时看到的现象：

- 浏览器页面仍然打开。
- 用户能输入问题。
- 点击发送后前端提示 `Failed to fetch`。
- 用户无法判断是模型失败、网络失败、权限失败，还是后端没启动。

### 1.2 第二轮：后端重新启动后，对话能返回答案

重新启动后，用 `/api/chat` 直接验证：

```text
POST /api/chat
Question: 你能干什么
```

返回结果：

```text
HTTP/1.1 200 OK
data.success=true
answer=我可以帮助您完成多种任务...
```

随后用前端页面真实输入“你能干什么”，页面也返回了完整回答。

### 1.3 第三轮：真实对话暴露知识库能力不可解释

用户连续询问：

```text
帮我检查现在的知识库中都有关于什么的资料
现在知识库中有什么文件呢？
enterprise_guide_runbook 讲了什么？
```

助手都没有给出有效的知识库清单或文档摘要。

### 1.4 第四轮：真实对话暴露数据库能力不可见

用户问：

```text
有没有操作数据库的能力
```

助手回答大意是：

```text
我目前可以直接使用的工具并不包括直接操作数据库的功能...
```

这和后端真实能力不完全一致，因为 E6/E7 已经实现 sandbox DB、SafeSqlKernel、DB Gateway 权限过滤，但当前聊天入口没有把数据库能力以“当前用户可用/不可用”的方式展示出来。

### 1.5 第五轮：用户提出前端应补个人信息和权限面板

用户指出：

```text
前端界面还要做用户信息入口，像 GPT 一样，可以登录，可以进入个人信息查看是否是管理员还是用户，可以查看自己的部门，能查看的知识库 id，能使用的功能。
```

这是合理的产品化补齐方向，已在 `docs/助手优化 1.md` 中展开为优化方案。

后续 UI 位置修正：用户入口改为放在左下角，只显示头像 / initials 和用户名；角色、部门、可见知识库、可用工具等详细信息进入“个人资料 / 我的权限”查看，主界面不直接铺开。

## 2. 问题 1：启动器验证不完整，导致前端页面打开但后端已停止

### 2.1 现象

前端打开后，用户发送消息显示：

```text
Failed to fetch
```

### 2.2 影响

用户视角：

- 以为系统已经启动成功。
- 浏览器页面仍可操作。
- 但任何真实对话都会失败。
- 错误文案无法解释问题原因。

开发视角：

- 之前只验证了 `/health` 和页面可打开。
- 没有验证“前端发送消息到 `/api/chat` 并返回答案”的完整链路。

### 2.3 根因

第一版 `启动企业助手.command` 里有：

```bash
read -r -p "按回车关闭窗口..."
```

用户关闭启动窗口后，后台启动的 FastAPI 会被系统一起清理。

结果是：

```text
浏览器页面还在
但 localhost:9900 后端已经不存在
前端 fetch /api/chat 失败
```

### 2.4 定位过程

执行健康检查：

```bash
curl -sS -i http://localhost:9900/health
```

失败：

```text
curl: (7) Failed to connect to localhost port 9900
```

检查端口：

```bash
lsof -nP -iTCP:9900 -sTCP:LISTEN
```

结果为空，说明 FastAPI 没有监听。

检查 `server.log`，看到此前启动确实成功过：

```text
Application startup complete.
Uvicorn running on http://127.0.0.1:9900
GET /health HTTP/1.1 200 OK
```

这说明不是启动从未成功，而是启动后被关闭。

### 2.5 处理过程

修改 `启动企业助手.command`：

- 启动成功后不再鼓励用户关闭窗口。
- 明确提示必须保持启动窗口打开。
- 加入健康监控循环，每 15 秒检查一次 `/health`。
- 提示停止服务时使用 `停止企业助手.command`。

修改后的关键逻辑：

```bash
echo "重要：请保持这个启动窗口打开。"
echo "关闭这个窗口会让后端服务停止，前端会出现 Failed to fetch。"
echo "需要停止时，请双击“停止企业助手.command”。"

while true; do
  if curl -fsS "http://localhost:9900/health" >/dev/null 2>&1; then
    sleep 15
  else
    echo "检测到后端服务已停止。"
    break
  fi
done
```

### 2.6 验证结果

重新启动后验证：

```bash
curl -sS -i http://localhost:9900/health
```

结果：

```text
HTTP/1.1 200 OK
milvus.status=connected
```

直接调用聊天接口：

```bash
curl -sS -i -X POST http://localhost:9900/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"Id":"session-launcher-fix-001","Question":"你能干什么"}'
```

结果：

```text
HTTP/1.1 200 OK
data.success=true
```

前端页面真实输入“你能干什么”后，也返回了完整回答。

证据：

```text
logs/frontend_verify/frontend_chat_20260531_1523.txt
logs/frontend_verify/frontend_chat_20260531_1523.png
```

### 2.7 当前状态

已处理。

当前版本是“启动窗口保活版”：

- 双击启动后需要保持窗口打开。
- 关闭窗口会导致后端停止。
- 停止服务应使用 `停止企业助手.command`。

后续如果要做到真正像 App 一样“启动后无需保留 Terminal 窗口”，需要改成 macOS `launchctl` 或其他后台服务管理方式。

### 2.8 2026-05-31 补充冒烟

本轮又做了一次带真实登录态的浏览器冒烟，验证顺序是：

1. 双击 `启动企业助手.command`。
2. 保持启动窗口打开，等待健康检查通过。
3. 打开 `http://127.0.0.1:9900/`。
4. 登录 `demo_user_dept1 / Demo123!`。
5. 打开左下角用户入口，进入“个人资料”。
6. 发送“我是谁”。

结果：

- 左下角入口显示当前用户 `demo_user_dept1`。
- 个人资料弹层显示 `user_demo_dept1`、`user`、`dept_1 / Department 1`。
- 带 Bearer token 的 `/api/chat` 返回当前用户名、部门和角色。

证据文件：

- `docs/assistant_optimization_evidence/frontend_profile_smoke_20260531_1727.png`

## 3. 问题 2：`Failed to fetch` 错误对用户不可理解

### 3.1 现象

前端显示：

```text
抱歉，发送消息时出现错误：Failed to fetch
```

### 3.2 影响

用户无法判断：

- 后端是否没启动。
- 网络是否断了。
- 是否没有登录。
- 是否没有权限。
- 是否模型接口失败。

### 3.3 根因

当前 `static/app.js` 对 fetch 异常直接展示原始错误：

```text
Failed to fetch
```

没有按错误类型做产品化解释。

### 3.4 处理过程

本轮只定位问题，尚未改前端错误处理。

已在 `docs/助手优化 1.md` 中列为 P5.2：

```text
后端断开：无法连接后端服务。请确认“启动企业助手.command”窗口仍然打开，或重新双击启动。
401：登录已过期，请重新登录。
403：你没有权限使用该功能，请联系管理员授权。
500：后端处理失败，请复制 trace_id 给开发者排查。
```

### 3.5 当前状态

待优化。

## 4. 问题 3：助手不能回答“知识库中有哪些文件”

### 4.1 现象

用户问：

```text
现在知识库中有什么文件呢？
```

助手回答：

```text
目前，知识库中没有提供具体的文件列表或概览信息...
```

### 4.2 影响

用户会误以为：

- 知识库为空。
- 文件没有上传成功。
- 系统没有保存文档。
- RAG 能力不可用。

实际情况不是这样。

### 4.3 代码事实

metadata 中实际存在文档记录：

```text
x.md                           kb_id=default  status=indexed
x.md                           kb_id=          status=indexed
x.md                           kb_id=default  status=indexed
enterprise_guide_runbook.md    kb_id=guide    status=indexed
```

`KnowledgeMetadataStore` 已经有：

```python
list_documents()
```

但当前没有：

```text
GET /api/documents
list_knowledge_documents Agent 工具
```

### 4.4 根因

当前 Agent 只有内容检索工具：

```python
retrieve_knowledge(query, knowledge_base_ids=None)
```

它的用途是：

```text
根据用户问题检索相关 chunk 内容
```

不是：

```text
列出知识库文档清单
```

因此用户问“有什么文件”时，Agent 没有结构化工具可调用，只能让模型根据检索结果猜，最后回答不出。

### 4.5 处理过程

本轮完成了定位和方案记录，未实现代码。

解决方案已写入 `docs/助手优化 1.md`：

1. 新增 `GET /api/documents`。
2. 新增 `list_knowledge_documents` Agent 工具。
3. 文档列表必须经过 PermissionService 过滤。
4. 用户问“知识库有什么文件”时，优先调用文档清单工具，而不是语义检索。

### 4.6 当前状态

待实现。

## 5. 问题 4：文件名查询不能命中文档

### 5.1 现象

用户问：

```text
enterprise_guide_runbook 讲了什么？
```

助手回答：

```text
目前，知识库中没有找到关于 enterprise_guide_runbook 的具体信息...
```

但 metadata 中实际有：

```text
enterprise_guide_runbook.md    kb_id=guide    status=indexed
```

### 5.2 影响

用户明确给出了文件名或文件 stem，系统仍然找不到，会直接破坏对知识库能力的信任。

### 5.3 根因

当前检索更偏向“内容语义召回”：

```text
query 文本向量化
→ Milvus 搜相似 chunk
→ BM25 搜 chunk 内容
→ 融合结果
```

但文件名查询需要另一条路径：

```text
文件名归一化匹配
→ 找到 doc_id
→ 按 doc_id 限定 retrieve_knowledge 检索范围
→ 返回该文档相关 chunk 和 source_ref
```

当前缺少：

- 文件名精确匹配。
- 文件 stem 匹配。
- 下划线 / 短横线 / 大小写归一化。
- `retrieve_knowledge` 按 `file_name` / `doc_id` 限定检索的入口。

### 5.4 处理过程

本轮完成原因确认和方案记录，未实现代码。

后续应新增：

```text
find_document_by_name(name)
retrieve_knowledge(file_name 或 doc_id 限定)
```

经后续方案复核，第一阶段不新增 `summarize_knowledge_document`。摘要专用工具容易和现有检索工具重叠，先用文件名匹配加限定检索解决真实问题；只有后续 eval 证明长文档摘要是独立瓶颈时再考虑新增。

### 5.5 当前状态

待实现。

## 6. 问题 5：数据库能力回答不准确

### 6.1 现象

用户问：

```text
有没有操作数据库的能力
```

助手回答：

```text
我目前可以直接使用的工具并不包括直接操作数据库的功能...
```

### 6.2 影响

这个回答容易误导用户，以为系统完全没有数据库能力。

### 6.3 代码事实

后端已经有：

- E6 Sandbox DB。
- SafeSqlKernel。
- Schema Registry。
- E7 DB Gateway 集成。
- 表级 / 列级权限过滤。
- DB audit 查询。

但当前普通聊天入口不应该默认暴露 database tools，数据库能力需要权限和 session/工具可见性控制。

### 6.4 根因

当前前端和 Agent 没有展示“当前用户 / 当前会话可用能力”。

因此 Agent 无法准确区分：

```text
系统底层支持数据库能力
当前用户是否有数据库权限
当前聊天入口是否启用 database-demo
```

### 6.5 正确产品表达

更准确的回答应该是：

```text
系统底层支持受限的 sandbox 只读数据库查询，但当前会话是否可用取决于权限和工具配置。
我可以帮你查看当前账号是否有 database-demo 权限；如果没有，需要管理员授权。
```

### 6.6 当前状态

待实现能力发现和权限可见性后修正。

## 7. 问题 6：前端没有用户身份和权限入口

### 7.1 现象

当前聊天页左侧只有：

```text
智能OnCall助手
新建对话
近期对话
```

没有：

- 登录入口。
- 当前用户。
- 是否管理员。
- 角色。
- 部门。
- 可见知识库 id。
- 可用功能。
- 可用工具。
- 退出登录。

### 7.2 影响

用户无法知道：

```text
我是谁？
我是 admin 还是普通用户？
我属于哪个部门？
我能看哪些知识库？
我能用哪些功能？
我为什么不能查数据库？
```

这会让 E1/E3/E8 已经完成的身份、权限和管理能力在产品上不可见。

### 7.3 根因

后端已有：

```text
POST /api/auth/login
GET  /api/auth/me
GET  /api/auth/protected
POST /api/auth/logout
```

但前端没有接：

- JWT 登录态。
- Authorization header 注入。
- 后端基于 Bearer token 生成可信 `RequestContext`。
- 用户信息展示。
- 权限 / profile 展示。

### 7.4 处理过程

本轮将该问题整理进 `docs/助手优化 1.md`，建议 P0 优先做：

- 左下角用户入口。
- 登录 / 登出。
- 个人资料。
- 我的权限。
- 可用功能。
- admin 管理入口。

### 7.5 当前状态

待实现。

## 11. 后续开发建议

下一步不要继续泛泛优化模型回答，应该先补结构化能力：

1. 先让前端知道“当前用户是谁”。
2. 再让前端知道“当前用户能用什么”。
3. 再让 Agent 能调用“列知识库文档”的确定性工具。
4. 最后再调提示词，让回答基于结构化工具结果。

原因：

```text
身份、权限、文件清单、能力清单都不应该靠模型猜。
这些必须来自后端确定性接口。
```

## 12. 当前经验教训

### 12.1 启动成功不等于可用

必须验证真实用户动作。

### 12.2 能力存在不等于用户可见

后端有数据库、权限、文档 metadata，不代表前端和 Agent 已经产品化。

### 12.3 检索工具不等于管理工具

`retrieve_knowledge` 能搜内容，但不能替代 `list_documents`。

### 12.4 错误信息必须面向用户

`Failed to fetch` 对开发者有意义，对普通用户没有意义。

### 12.5 企业助手必须显示身份和权限

企业系统的核心不是“所有人都能聊”，而是“不同人能清楚知道自己被授权做什么”。

## 13. 方案复核后的修订记录

### 13.1 复核结论

对 `docs/助手优化 1.md` 复核后，确认原方向正确，但存在三处过度设计：

- `/api/me/capabilities` 容易新造一套和 E3 权限体系平行的 capability 概念。
- `get_current_user_capabilities` Agent 工具与 profile API 重复，且会增加不必要的工具调用。
- `summarize_knowledge_document` 和 `retrieve_knowledge` 重叠，第一阶段没有足够证据证明必须新增摘要专用工具。

### 13.2 修订后的方案

修订后的主线是：

1. 前端先完成登录态、左下角用户入口和明确错误提示。
2. 后端新增 `GET /api/me/profile`，聚合用户、角色、部门、可见工具、可见 kb_id、admin/database 状态。
3. 后端必须验证 Bearer token 并生成可信 `RequestContext`，不能依赖前端传来的用户/角色头做权限判断。
4. 新增 `GET /api/documents` 和 `list_knowledge_documents(kb_id?: string)`，只返回当前用户可见的 indexed 文档。
5. 增强 `retrieve_knowledge` 支持 `file_name` / `doc_id` 限定检索，暂不新增摘要专用工具。
6. Agent prompt 注入当前 profile 摘要，用于回答“我是谁 / 我能用什么”，但真正权限仍由后端服务检查。

### 13.3 二次补充

继续复核后，补充四个实施细节：

1. `visible_tools` 必须明确聚合本地 RAG 工具、MCP / ToolGateway 工具、database-demo 工具和 admin 能力，不能假设所有工具都来自 `ToolGateway`。
2. `feature_flags` 是前端粗粒度入口开关，`visible_tools` 是 Agent / 权限详情使用的细粒度工具列表，两者都不能替代后端权限检查。
3. 登录流程需要覆盖初始 token 校验、匿名体验、点击左下角未登录入口登录、401 过期处理和多标签页同步。
4. `list_knowledge_documents(kb_id?: string)` 指定无权限 `kb_id` 时返回空列表并提示无权限，不能让用户误以为知识库为空。

同时修正 UI 约定：左下角只显示当前用户是谁，具体个人资料进入弹层查看。

### 14.2 实施中发现的问题

#### 问题 A：前端上传缺少 `kb_id`

现象：

```text
后端 /api/upload 已要求 kb_id 为必填 Form 字段，但前端 FormData 只提交 file。
```

原因：

```text
之前前端上传入口仍按旧接口实现；后端 C1 已经把知识库边界收紧为显式 kb_id。
```

处理：

```text
前端上传时显式追加 kb_id。
优先使用 profile.visible_kb_ids[0]，没有可见 kb_id 时使用 default 作为前端显式选择值。
```

#### 问题 B：右下角账号入口挡住发送按钮

现象：

```text
Playwright 点击发送按钮时失败，错误为 userAccountBtn intercepts pointer events。
```

原因：

```text
账号入口 fixed 在右下角，而有对话内容时输入框也靠近页面底部右侧。
两者在当前浏览器视口下发生重叠。
```

处理：

```text
后续按用户要求将账号入口改为左下角，放入左侧边栏底部视觉区域。
同时取消聊天输入区为右下角账号入口预留的右侧 / 底部避让空间。
```

#### 问题 C：Codex 中 `make start` 的后台 MCP 进程不能用于验证

现象：

```text
make start 显示 MCP server 启动成功，但随后 make status-mcp 显示未运行。
真实前端对话返回 error，后端日志显示 MCP get_tools ConnectError。
```

原因：

```text
Codex exec 会话结束后会清理该会话拉起的后台子进程。
这不是业务代码错误，也不是双击启动脚本在普通终端里的行为。
```

处理：

```text
验证时改用前台会话分别启动 FastAPI、CLS MCP、Monitor MCP。
重新发送“我是谁”后，前端成功返回当前用户 demo_user_dept1、Department 1、user 角色。
```

## 15. 2026-05-31：优化 1 收口和优化 2 启动

### 15.1 当前状态

优化 1 已收口为“普通用户侧体验闭环”：

- 用户能在左下角看到当前登录身份。
- 个人资料弹层能看到角色、部门、可见知识库和可用工具。
- 聊天、上传、AIOps 统一携带 Bearer token，后端以 token 生成可信 `RequestContext`。
- 知识库文件清单不再靠模型猜测，而是通过 `/api/documents` 和 `list_knowledge_documents` 返回权限过滤后的 indexed 文档。
- 文件名限定检索已接入 `retrieve_knowledge(file_name/doc_id)`。

### 15.2 为什么进入优化 2

真实体验中新的问题是：普通用户已经能知道“我是谁、我能用什么”，但管理员仍没有前端入口处理“创建用户、授权、审批、查审计”。这些能力后端 E8 已经存在，缺的是产品化管理后台。

因此下一步启动优化 2 管理后台 MVP：

- 聊天页只展示 admin 可见的“管理后台”入口。
- 管理后台复用已有 `/api/admin/*` 和 `/api/admin/reviews/*`。
- 后端权限仍由 admin dependency、`PermissionService` 和 audit 兜底，前端不做最终授权判断。

### 15.3 暂不处理的问题

- 部门管理员 scoped admin。
- 用户自助注册和权限申请。
- 资源目录、授权预览、权限模板版本化。
- 前端工程化迁移到 Vite / `.vue` SFC。

这些属于优化 2 后续阶段，不阻塞当前管理后台 MVP。
