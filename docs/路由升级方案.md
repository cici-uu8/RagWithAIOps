# 路由升级方案

更新时间：2026-06-08

## 1. 背景

当前 SuperBizAgent 已经有两类路由能力：

- 企业策略路由：`app/enterprise/routing/` 下的 `StrategyRouter`、`RuleRoutingProvider`、`KeywordRoutingProvider`。当前是 shadow-only，只记录建议路由，不直接调度执行。
- RAG 查询意图路由：`app/enterprise/rag/query_intent.py` 下的 `QueryIntentRouter`。当前已经影响 RAG 查询编排，用于区分文档清单、文档读取、知识问答、普通对话、数据库、权限申请和人工审核。

现有实现的问题不是“没有路由”，而是路由语义还比较扁平：

- `human_review` 被当作和 `rag`、`database`、`aiops` 平级的业务路由。
- 高风险数据库操作会被改写成 `human_review`，容易丢失“这是数据库操作”的业务域信息。
- `RoutingDecision` 主要靠一个 `route` 字段表达去向，缺少 `domain`、`intent`、`approval_required`、`execution_mode` 等结构化字段。
- RAG 入口里承担了部分数据库/权限分流职责，短期能防止 RAG 误答，但长期应上移到统一企业意图层。

本方案的目标是把路由从“猜一个 route”升级为“先判业务域，再判域内意图，再进入治理门槛，最后执行对应工具或回答”。

## 2. 设计原则

### 2.1 业务域优先

高风险不应该直接覆盖业务域。

错误表达：

```text
高风险 -> human_review
```

目标表达：

```text
高风险 -> 对应业务域 -> 操作草案 -> 审批/确认 -> 对应工具执行
```

例如：

```text
把订单金额改成 100
-> domain=database
-> intent=update
-> approval_required=true
-> execution_mode=proposal_then_approval
-> 通过确认后调用数据库写操作工具
```

### 2.2 `human_review` 是治理节点，不是最终业务路由

`human_review` 应表达“需要人审/审批/确认”，不应替代 `database`、`aiops`、`admin` 等业务域。

目标上，路由结果应该同时保留：

- 用户要进入哪个业务域。
- 用户想做什么域内动作。
- 风险等级是什么。
- 是否需要审批。
- 审批通过后由哪个工具或服务执行。

### 2.3 RAG 不吞业务操作

RAG-agent 的职责应收敛到：

- 普通对话。
- 知识库问答。
- 文档清单。
- 文档读取/总结。

数据库操作、AIOps 诊断/修复、权限申请、管理员操作不应被 RAG 当成普通知识问答回答。

### 2.4 LLM 意图识别先 shadow/eval，不直接替代规则

LLM 适合理解自然语言变体，但它也带来成本、延迟、稳定性和模型依赖问题。

推荐路线：

```text
规则 fast-path
-> LLM shadow 意图识别
-> 离线评测/线上审计对比
-> 达标后再考虑进入主路径
```

不要一开始就把企业高风险路由完全交给 LLM。

### 2.5 路由层只产出决策，不直接执行工具

路由结果里的 `target_tool` 只能表示“建议进入哪个工具或服务边界”，不能由路由层直接调用工具。

实际执行必须继续经过项目已有的治理边界：

- RAG、文档、数据库、AIOps 等工具调用应经过 `ToolExecutionFacade` / `ToolGateway` 等现有工具治理入口。
- 数据库写操作应复用现有数据库操作分类、准备、确认、执行链路。
- AIOps 工具池保持现有白名单策略，路由升级不能顺手扩大可执行工具集合。

这条约束的意义是：路由只负责“判断去哪、做什么、风险多高”，执行层继续负责“是否有权限、是否需要审批、是否真正调用工具”。

### 2.6 路由模块纳入共享边界

后续如果同时推进 RAG、PDF、Memory、AIOps 或数据库能力，以下模块必须视为共享边界：

- `app/enterprise/routing/models.py`
- `app/enterprise/routing/providers.py`
- `app/enterprise/routing/router.py`
- `app/enterprise/rag/query_intent.py`
- 未来可能新增的 `EnterpriseIntentRouter`

尤其是 `QueryIntentRouter`：它现在既承担 RAG 内部查询意图，也承担部分数据库/权限兜底分流。P3 迁出这些职责时，必须作为共享边界收口任务处理，不能夹在某条并行开发线里顺手改。

## 3. 目标路由模型

建议将路由决策升级为以下结构。

```text
domain: chat | rag | document | database | aiops | permission | admin | governance
intent: greet | qa | list | read | describe | select | insert | update | delete | diagnose | remediate | request_access | manage
risk_level: low | medium | high
approval_required: true | false
execution_mode: answer | tool_call | proposal_then_approval | handoff
target_tool: optional
entities: optional
reason: string
confidence: 0.0-1.0
```

其中：

- `domain` 表示业务域。
- `intent` 表示域内动作。
- `risk_level` 表示风险等级。
- `approval_required` 表示是否需要审批或二次确认。
- `execution_mode` 表示如何执行。
- `target_tool` 表示最终建议调用的工具或服务。
- `entities` 保存表名、文件名、服务名、知识库 ID 等结构化实体。

为了兼容现有代码，第一阶段不要删除 `route` 字段。可以先在 `RoutingDecision.metadata` 或新模型中增加上述字段，再逐步迁移消费者。

### 3.1 兼容字段一致性规则

在 `route` 与 `domain/intent` 并存期间，需要定义确定性映射和一致性校验，避免两套字段长期漂移。

建议规则：

```text
domain=chat -> route=chat
domain=rag -> route=rag
domain=document -> route=rag
domain=database -> route=database
domain=aiops -> route=aiops
domain=permission -> route=admin 或 chat，按现有入口兼容
domain=admin -> route=admin
approval_required=true -> 不覆盖业务 route，只在 metadata 中表达治理门槛
```

当 `route` 与 `domain/intent` 推导结果不一致时：

- shadow 阶段记录 audit warning。
- 不改变真实执行。
- 纳入 routing eval 的混淆样本。

### 3.2 未定义组合的安全兜底

不要把未定义的 `domain + intent` 组合兜底成普通聊天或问候。那会把潜在危险请求伪装成低风险对话。

推荐兜底：

```text
undefined domain+intent
-> execution_mode=handoff 或 clarify
-> decision=unsupported_intent
-> approval_required=false
-> 不调用工具
-> 返回可解释的澄清、拒绝或人工处理提示
```

例如 `domain=rag, intent=delete`、`domain=document, intent=update_database` 这类组合，应进入 `unsupported_intent`，而不是静默转成 `chat/greet`。

## 5. 分阶段实施计划

### P0：升级路由语义，保持 shadow-only

目标：

- 不改变当前真实执行链路。
- 在现有 shadow routing 中补充结构化语义。

建议改动：

- 在 `RoutingDecision` 兼容新增或通过 `metadata` 输出：
  - `domain`
  - `intent`
  - `approval_required`
  - `execution_mode`
  - `target_tool`
  - `entities`
- 保留现有 `route` 字段，避免破坏审计、adapter 和测试。
- `human_review` 暂时可以保留为兼容 route，但新增字段里应表达真实业务域。

验收：

- 现有 routing 测试继续通过。
- shadow 审计事件中能看到 `domain/intent/approval_required/execution_mode`。
- 高风险数据库操作不再只剩 `route=human_review` 这一种信息。
- `target_tool` 只作为诊断字段出现，不直接触发工具调用。
- `route` 与 `domain/intent` 不一致时能记录 audit warning 或诊断事件。

### P1：修正数据库路由语义

目标：

- 数据库读、元数据查询、写入、删除都保留 `domain=database`。
- 写入/删除通过治理字段表达审批需求。

建议改动：

- 将数据库意图区分为：
  - `describe`
  - `select`
  - `insert`
  - `update`
  - `delete`
  - `ddl`
- 高风险数据库操作输出：

```text
domain=database
intent=update/delete/ddl
approval_required=true
execution_mode=proposal_then_approval
```

而不是：

```text
intent=human_review
handoff=human_review
```

注意：

- 项目已有数据库操作分类、确认、执行能力，应复用现有 `operation_classifier`、`operations/prepare`、`confirmations/{id}/confirm` 等链路。
- 不要另起一套数据库写操作确认系统。

验收：

- “查询订单表字段”进入 `database/describe`。
- “select 订单记录”进入 `database/select`。
- “update/delete/drop” 保留 `database` 域，并标记 `approval_required=true`。

### P2：修正 AIOps 路由语义

目标：

- 区分诊断和修复。
- 诊断可以进入 AIOps 工具链。
- 修复类动作必须先生成方案并审批。

建议语义：

```text
CPU 为什么高
-> domain=aiops
-> intent=diagnose
-> execution_mode=tool_call
```

```text
帮我重启服务
-> domain=aiops
-> intent=remediate
-> approval_required=true
-> execution_mode=proposal_then_approval
```

注意：

- AIOps 当前工具池是有意限制的白名单，不要为了路由升级扩大工具池。
- 修复执行工具是否接入，应单独评估和审批。

验收：

- 诊断类问题不会被 RAG 吞掉。
- 修复类问题不会直接执行。
- 审计中能区分 `diagnose` 和 `remediate`。

### P3：把 RAG 内的非 RAG 分流上移

目标：

- RAG-agent 专注文档和知识问答。
- 数据库、权限、AIOps 分流由统一企业意图层处理。

启动条件：

- RAG baseline 已完成，文档 list/read/retrieve 的当前行为和测试稳定。
- `QueryIntentRouter`、`StrategyRouter`、未来 `EnterpriseIntentRouter` 已被列入共享边界。
- 已有 evalset 覆盖数据库、权限、AIOps、文档和普通聊天的典型混淆样本。

建议改动：

- 新增或演进统一 `EnterpriseIntentRouter`。
- `QueryIntentRouter` 保留知识域内部判断：
  - `plain_chat`
  - `knowledge_qa`
  - `document_list`
  - `document_read`
- 将 `database`、`permission_request`、`human_review` 从 RAG 内部意图逐步迁出。

过渡方式：

- 第一阶段不要直接删除 RAG 内部的 DB/权限判断。
- 先让统一企业意图层输出诊断，RAG 层继续兜底。
- 等 evalset 覆盖足够后再切换主路径。
- P3 不放入第一批并行开发；应作为 RAG baseline 后的共享边界收口任务。

验收：

- RAG 问答不再回答数据库写操作。
- 文档类问题仍可稳定 list/read/retrieve。
- 旧的 RAG 查询测试不回退。
- 数据库/权限/AIOps 迁出后仍保留明确 handoff 诊断，不出现静默吞掉。

### P4：LLM 意图识别 shadow/eval

目标：

- 用 LLM 提升自然语言变体识别能力。
- 先做 shadow，不直接参与执行。
- 控制成本和延迟，不默认对所有请求全量调用 LLM。

建议输出 JSON：

```json
{
  "domain": "database",
  "intent": "select",
  "risk_level": "medium",
  "approval_required": false,
  "execution_mode": "tool_call",
  "entities": {
    "table": "orders"
  },
  "reason": "用户请求查询订单记录，属于数据库只读查询。"
}
```

约束：

- LLM 只输出结构化意图，不直接调用工具。
- 高风险判断仍由规则治理层复核。
- LLM 与规则结果不一致时先记录审计，不直接采用。
- 第一阶段只对高风险关键词、规则低置信度、抽样请求运行 LLM shadow。
- 每次 shadow 记录延迟、token 成本、失败原因和规则/LLM 差异。

验收：

- 增加意图 evalset。
- 输出混淆矩阵：规则 vs LLM vs 期望标签。
- 统计误判类型、成本、延迟、失败率。
- 明确是否达到进入主路径的阈值；未达标时继续 shadow，不改变执行。

### P5：前端展示路由诊断

目标：

- 用户和开发者能看到本次请求为什么进入某个域。
- 方便调试“为什么没有查数据库/为什么走了 RAG/为什么需要审批”。

建议展示字段：

- 业务域：`domain`
- 意图：`intent`
- 风险等级：`risk_level`
- 是否需要审批：`approval_required`
- 执行模式：`execution_mode`
- 实际工具：`target_tool`
- 判断原因：`reason`

验收：

- 前端能显示路由诊断。
- SSE/普通 chat 返回结构保持兼容。
- 没有诊断信息时 UI 不报错。

### P6：执行路由灰度

目标：

- 在 shadow 准确率达标后，再让路由影响真实调度。

前置条件：

- 核心 evalset 覆盖：
  - RAG 问答
  - 文档 list/read
  - 数据库 describe/select/update/delete
  - AIOps diagnose/remediate
  - 权限申请
  - admin 操作
  - 普通聊天
- 高风险误放行率为 0。
- 低风险误拒绝率可接受。
- 有完整审计和回退开关。

灰度方式：

```text
shadow -> selected users -> selected domains -> full route dispatch
```

不建议一开始全量开启执行路由。

## 6. 和并行计划的关系

如果当前已有 RAG、PDF、Memory 等并行优化线，路由升级应作为独立 D 线管理，避免在共享文件上互相覆盖。

建议拆分：

| D 线任务 | 内容 | 是否可近期做 | 依赖 |
|---|---|---|---|
| D0 | shadow routing 补 `domain/intent/approval_required/execution_mode` 诊断 | 可以 | 不改变真实执行 |
| D1 | 数据库路由语义修正，保留 `domain=database` | 可以先做 shadow | 复用数据库确认链路 |
| D2 | AIOps 路由语义修正，区分 `diagnose/remediate` | 可以先做 shadow | 不扩大 AIOps 工具池 |
| D3 | RAG 内非 RAG 分流上移到统一企业意图层 | 后置 | 等 RAG baseline 稳定，作为共享边界收口 |
| D4 | LLM 意图识别 shadow/eval | 可以小范围做 | 高风险、低置信度、抽样优先 |
| D5 | 前端路由诊断展示 | 后置 | 依赖 D0-D4 的稳定诊断字段 |
| D6 | 执行路由灰度 | 最后做 | shadow 准确率、审计、回退开关达标 |

近期最稳妥的是只推进 D0，并把 D1/D2/D4 作为 shadow 诊断能力准备好。D3 不应夹在 RAG 或数据库开发里顺手做，因为它会触碰 `QueryIntentRouter` 的职责边界。

## 7. 不建议做的事

- 不建议删除 Milvus、RAG、Plan-Execute-Replan 或 MCP 工具链。
- 不建议把 `human_review` 当作所有高风险问题的最终终点。
- 不建议让 LLM 路由器直接决定工具执行。
- 不建议为了路由升级扩大 AIOps 工具池。
- 不建议一次性删除现有规则路由；规则在高风险治理中仍然有价值。
- 不建议新增一套平行的数据库确认系统，应复用现有数据库操作确认链路。
- 不建议把未定义 `domain/intent` 组合兜底成普通聊天。
- 不建议在 RAG baseline 未稳定前迁出 `QueryIntentRouter` 的数据库/权限兜底逻辑。

## 8. 推荐的最终故事

路由升级后的 SuperBizAgent 可以这样描述：

```text
SuperBizAgent 不是把所有问题都塞进 RAG 的聊天助手，
而是一个企业任务分流和受控执行系统。

它先识别用户请求属于知识问答、文档读取、数据库、安全运维、权限申请还是管理操作；
再识别域内动作和风险等级；
低风险任务直接调用对应工具或回答；
高风险任务先生成可审查操作方案，经过权限、确认和审计后再执行。
```

这比“有 RAG、有 AIOps、有数据库工具”更像一个完整企业 Agent 的架构故事。

## 9. 下一步建议

最小可落地切片：

1. 在现有 shadow routing 中补 `domain/intent/approval_required/execution_mode`，并增加 `route` 一致性诊断。
2. 明确 `target_tool` 只是建议字段，实际执行必须经过 `ToolExecutionFacade` / `ToolGateway`。
3. 修正数据库高风险语义：保留 `domain=database`，不要直接改成 `human_review`。
4. 新增意图 evalset，覆盖数据库写操作、AIOps 修复、权限申请、文档读取、未定义组合和普通问候。
5. P4 的 LLM shadow 先只覆盖高风险、低置信度和抽样请求。
6. 前端先只展示诊断，不改变真实执行。

这条路线风险最低，也最符合当前项目已有的 shadow routing、数据库确认、RAG 编排和企业治理基础。
