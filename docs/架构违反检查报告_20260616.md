## 1. ❌ P0：API 层绕过适配器直接调用旧服务

### 违反位置

**文件**: `app/api/chat.py:389`

```python
@router.post("/chat/clear", response_model=ApiResponse)
async def clear_session(request: ClearRequest, current_user: CurrentUser):
    _assert_session_owner(...)
    try:
        legacy_success = rag_agent_service.clear_session(request.session_id)  # ❌ 直接调用
        context = _current_context_or_500()
        session_access.audit_service = chat_adapter.gateway.audit_service
        archive_success = session_access.archive(context, request.session_id)
```

### 问题分析

1. **绕过适配器模式**：API 层直接导入并调用 `rag_agent_service`，而不是通过 `ChatAdapter`
2. **绕过网关层**：这个调用路径跳过了 `RequestGateway`，丢失了：
   - trace_id / request_id 生成
   - 速率限制检查
   - Guardrail 安全检查
   - 统一的审计记录（`request_started` / `request_completed`）
3. **不一致的架构**：同文件中的 `/chat` 和 `/chat_stream` 都正确使用了 `chat_adapter`，只有 `/chat/clear` 例外

### 架构原则违反

违反了 `architecture_and_patterns.md` 中的：
- "适配器模式：项目使用适配器模式包装旧的 RAG/AIOps 服务，不改变其内部实现"
- "ChatAdapter 职责: 包装 RAG Agent 服务，注入 trace_id/request_id"

### 修复建议（必须）

**步骤 1**: 在 `ChatAdapter` 中添加 `clear_session` 方法

```python
# app/enterprise/adapters/chat_adapter.py
class ChatAdapter:
    async def clear_session(self, session_id: str, headers) -> bool:
        """Clear session through gateway."""
        gateway_request = GatewayRequest.from_headers(
            route="chat_clear",
            payload={"session_id": session_id},
            headers=headers,
        )
        
        async def handler(context):
            # 审计记录已由 gateway 自动处理
            success = self.rag_service.clear_session(session_id)
            return {"success": success}
        
        result = await self.gateway.execute(gateway_request, handler)
        return result.get("success", False)
```

**步骤 2**: 修改 `app/api/chat.py`

```python
@router.post("/chat/clear", response_model=ApiResponse)
async def clear_session(request: ClearRequest, http_request: Request, current_user: CurrentUser):
    _assert_session_owner(...)
    try:
        # ✅ 通过适配器调用
        legacy_success = await chat_adapter.clear_session(request.session_id, http_request.headers)
        context = _current_context_or_500()
        session_access.audit_service = chat_adapter.gateway.audit_service
        archive_success = session_access.archive(context, request.session_id)
        ...
```

**步骤 3**: 移除 `app/api/chat.py` 中的直接导入

```python
# ❌ 移除这行
from app.services.rag_agent_service import rag_agent_service
```

## 2. ❌ P0：Services 层直接使用全局 RequestContext

### 违反位置

**文件**: `app/services/rag_agent_service.py`（5 处）

```python
from app.enterprise.context import get_current_request_context

# 第 1 处 - _build_runtime_system_prompt
context = get_current_request_context()
if context:
    profile = await profile_service.build_profile(context)

# 第 2 处 - list_knowledge_documents
context = get_current_request_context()
if context:
    visible_kb_ids = document_access_service.list_visible_knowledge_bases(context)

# 第 3 处 - retrieve_knowledge
context = get_current_request_context()

# 第 4 处 - describe_database_table
context = get_current_request_context()

# 第 5 处 - safe_select_database
context = get_current_request_context()
```

**文件**: `app/services/aiops_service.py`（1 处）

```python
context = get_current_request_context()
if context:
    result = aiops_tool_catalog.validate_required_tools(...)
```

### 问题分析

1. **违反依赖注入**：Services 层直接访问全局上下文，而不是通过参数传入
2. **隐式依赖**：调用方无法看到 services 需要 RequestContext，导致调用契约不清晰
3. **测试困难**：全局上下文难以在单元测试中模拟
4. **耦合度高**：Services 层与 enterprise 层的上下文管理机制紧耦合

### 架构原则违反

违反了：
- "分层架构：业务服务层 (app/services/) 应该保持独立"
- "无过度重构：旧服务通过适配器包装，不改变其内部实现"

### 修复建议（必须）

**方案 A（推荐）**: 通过参数显式传递 context

```python
# app/services/rag_agent_service.py
class RagAgentService:
    async def _build_runtime_system_prompt(
        self,
        session_id: str | None = None,
        context: RequestContext | None = None,  # ✅ 显式参数
    ) -> str:
        if context:
            profile = await profile_service.build_profile(context)
        else:
            profile = None
        ...
```

调用方（Adapter）负责传入 context：

```python
# app/enterprise/adapters/chat_adapter.py
async def handler(context):
    answer = await self.rag_service.query(
        request.question,
        session_id=request.id,
        context=context,  # ✅ 适配器传入
    )
```

**方案 B（保守）**: 如果 services 确实需要 enterprise 能力，应该提升为 enterprise 模块

将 `rag_agent_service.py` 移到 `app/enterprise/rag/agent_service.py`，承认它是 enterprise 层的一部分。

## 3. ⚠️ P1：Services 层直接依赖 enterprise 层（违反分层）

### 违反位置 3.1

**文件**: `app/services/rag_agent_service.py`

```python
from app.enterprise.auth.models import UserProfile
from app.enterprise.context import get_current_request_context
from app.enterprise.documents import document_access_service
from app.enterprise.profile import profile_service
from app.enterprise.rag import (
    KnowledgeRetrievalOrchestrator,
    OrchestrationResult,
    QueryIntentRouter,
    QueryScope,
)
from app.enterprise.tools.facade import ToolExecutionFacade
from app.enterprise.tools.local_provider import build_local_agent_tool_execution_facade
```

### 违反位置 3.2

**文件**: `app/services/knowledge_search_service.py`

```python
from app.enterprise.adapters.rag_adapter import RagAdapter, rag_adapter
from app.enterprise.context import RequestContext
from app.enterprise.documents.service import DocumentAccessService, document_access_service
```

### 违反位置 3.3

**文件**: `app/services/aiops_service.py`

```python
from app.enterprise.aiops.failure_semantics import AIOpsFailureLabel, AIOpsFailureSemantics
from app.enterprise.aiops.tool_catalog import aiops_tool_catalog
from app.enterprise.context import get_current_request_context
```

### 问题分析

1. **分层倒置**：`app/services/`（旧业务层）依赖 `app/enterprise/`（新企业层）
2. **架构污染**：原本应该独立的旧服务，现在与新企业能力强耦合
3. **维护困难**：无法单独理解或测试 services 层，必须连同 enterprise 层一起

### 架构原则违反

**预期分层**（根据 `architecture_and_patterns.md`）：
```
API 层 (app/api/)
    ↓
适配器层 (app/enterprise/adapters/)
    ↓
网关层 (app/enterprise/gateway/)
    ↓
业务服务层 (app/services/)  ← 应该独立，只依赖 models
    ↓
数据模型层 (app/models/)
```

**实际分层**（当前代码）：
```
API 层 (app/api/)
    ↓
适配器层 (app/enterprise/adapters/)
    ↓  ↑
业务服务层 (app/services/)  ← ❌ 双向依赖
    ↓  ↑
Enterprise 层 (app/enterprise/*)  ← ❌ 被 services 依赖
```

### 修复建议（强烈建议）

**选项 1（推荐）**: 承认现实，重新划分模块边界

由于 `rag_agent_service` / `aiops_service` / `knowledge_search_service` 已经深度使用 enterprise 能力，应该将它们提升到 enterprise 层：

```bash
# 重构移动
app/services/rag_agent_service.py       → app/enterprise/rag/agent_service.py
app/services/knowledge_search_service.py → app/enterprise/rag/search_service.py
app/services/aiops_service.py            → app/enterprise/aiops/diagnosis_service.py
```

Adapter 调整：
```python
# app/enterprise/adapters/chat_adapter.py
from app.enterprise.rag.agent_service import rag_agent_service  # ✅ 同层导入
```

**选项 2（保守）**: 隔离依赖，创建接口层

在 services 和 enterprise 之间创建抽象接口：

```python
# app/services/interfaces.py
from abc import ABC, abstractmethod

class DocumentAccessInterface(ABC):
    @abstractmethod
    def list_visible_knowledge_bases(self, context) -> list[str]:
        pass

class ProfileInterface(ABC):
    @abstractmethod
    async def build_profile(self, context) -> UserProfile:
        pass
```

Services 依赖接口，enterprise 提供实现，adapter 注入依赖。

**选项 3（激进）**: 回退到纯旧服务

完全移除 services 对 enterprise 的依赖，所有 enterprise 能力在 adapter 层桥接。这需要大规模重构。

## 4. ⚠️ P1：Services 层直接导入 enterprise 单例

### 违反位置

**文件**: `app/services/rag_agent_service.py`

```python
from app.enterprise.documents import document_access_service  # ❌ 单例导入
from app.enterprise.profile import profile_service            # ❌ 单例导入

# 使用
visible_kb_ids = document_access_service.list_visible_knowledge_bases(context)
profile = await profile_service.build_profile(context)
```

**文件**: `app/services/knowledge_search_service.py`

```python
from app.enterprise.documents.service import DocumentAccessService, document_access_service  # ❌
from app.enterprise.adapters.rag_adapter import RagAdapter, rag_adapter  # ❌
```

### 问题分析

1. **隐式依赖**：无法从构造函数看出服务依赖哪些外部服务
2. **测试困难**：无法在测试中替换这些单例为 mock 对象
3. **循环依赖风险**：单例导入容易引发模块间的循环依赖

### 修复建议

使用依赖注入：

```python
# app/services/rag_agent_service.py
class RagAgentService:
    def __init__(
        self,
        document_access: DocumentAccessService | None = None,
        profile_service: ProfileService | None = None,
    ):
        self.document_access = document_access or document_access_service  # 允许默认值
        self.profile_service = profile_service or profile_service_default()
    
    async def _build_runtime_system_prompt(...):
        profile = await self.profile_service.build_profile(context)  # ✅ 使用实例属性
```

## 5. ℹ️ P2：架构边界模糊

### 观察

当前代码中 `app/services/` 和 `app/enterprise/` 的边界已经模糊：

- `knowledge_search_service.py` 是 services 模块，但高度依赖 enterprise 能力
- `rag_agent_service.py` 使用了 QueryIntentRouter、ToolExecutionFacade 等 enterprise 组件
- `aiops_service.py` 使用了 AIOpsToolCatalog、failure_semantics 等 enterprise 业务逻辑

### 根本问题

架构文档声称"无过度重构：新功能在 app/enterprise/*，旧服务通过适配器包装"，但实际实施中：

1. 旧服务**已经被重构**了（添加了 enterprise 依赖）
2. 适配器层**很薄**，大部分 enterprise 集成在 services 内部完成
3. "旧"和"新"的边界**不清晰**

### 建议

**重新定义架构边界**，明确哪些模块属于哪一层：

**方案 A**: Enterprise-first（承认现状）
```
app/
  ├── api/              # HTTP 路由
  ├── enterprise/       # 企业级业务逻辑（包含原 services）
  │   ├── adapters/     # 适配器（薄层）
  │   ├── gateway/      # 网关
  │   ├── rag/          # RAG 业务（含原 rag_agent_service）
  │   ├── aiops/        # AIOps 业务（含原 aiops_service）
  │   └── ...
  ├── models/           # 数据模型
  └── infrastructure/   # 纯技术服务（MCP、存储等，不含业务逻辑）
```

**方案 B**: Clean separation（清晰分离）
```
app/
  ├── api/              # HTTP 路由
  ├── enterprise/       # 企业级横切能力（权限、审计、网关）
  │   ├── adapters/     # 厚适配器（桥接所有 enterprise 能力）
  │   ├── gateway/
  │   ├── permissions/
  │   └── observability/
  ├── services/         # 纯业务逻辑（不依赖 enterprise）
  │   ├── rag/
  │   ├── aiops/
  │   └── ...
  └── models/
```

建议选择 **方案 A**，因为当前代码已经是这个模式，强行拆分成本高且收益低。
