## 系统架构概览

```
用户问题
    ↓
[步骤 1] 向量化查询
    ↓
[步骤 2] 向量检索（Milvus）
    ↓
[步骤 3] 召回 Top-K 文档 chunks
    ↓
[步骤 4] 组装上下文（带 source_ref）
    ↓
[步骤 5] LLM 生成答案（基于上下文）
    ↓
系统回答（带来源标注）
```

## 排查步骤

1. **获取当前时间**
   - 使用 `get_current_time` 工具
   - 确定告警发生的时间范围

**处理**：
1. 立即重启受影响的服务实例
2. 查看日志定位代码问题
3. 回滚到上一个稳定版本
4. 通知开发团队修复 bug

### 原因 2：流量突增
**特征**：
- 多个进程 CPU 均匀升高

- CPU 周期性升高

## 为什么能找对文档？

### 向量检索的原理

1. **语义理解**
   - 用户问："CPU使用率一直高怎么排查"
   - 向量化后，系统理解为："CPU 性能问题 + 故障排查 + 解决方案"
   - 即使用户没说"告警"、"处理方案"这些词，系统也能找到相关文档

2. **余弦相似度**
   - 查询向量：[0.1, -0.5, 0.8, ...]
   - 文档向量：[0.2, -0.4, 0.7, ...]
   - 相似度 = cos(θ) = 0.6085
   - 越接近 1 越相关

3. **Top-K 机制**
   - 从 30 个文档的所有 chunks 中
   - 找出最相关的 3 个
   - 保证召回质量

## 给小白的解释

### 类比：图书馆查资料

**传统方式（关键词搜索）**：
1. 你说"CPU 高"
2. 系统找包含"CPU"和"高"这两个词的书
3. 可能找到很多不相关的

**RAG 方式（语义搜索）**：
1. 你说"CPU使用率一直高怎么排查"
2. 系统理解你要"解决 CPU 性能问题"
3. 找到真正讲"CPU 故障排查"的书
4. 把相关章节摘出来
5. 基于这些章节给你写一份"排查指南"
6. 告诉你每条信息来自哪本书第几页

**为什么更好**：
- ✅ 理解语义，不是死板的关键词匹配
- ✅ 自动组织答案，不是给你一堆原文
- ✅ 标注来源，可以验证
- ✅ 不编造，只用图书馆里的资料
