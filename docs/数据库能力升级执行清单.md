# 数据库能力升级执行清单

**说明：** 本文件保留为历史版清单。当前执行入口请看 [数据库能力升级执行清单 v2（轻量且架构对齐版）](./数据库能力升级执行清单_v2_轻量版.md)，其中示例业务已切换为员工进厂/进楼记录，并按现有 `ToolGateway` / `ResourceCatalogService` / `DatabasePermissionFilter` 对齐。

## 目标

将数据库能力从"安全工具调用"升级为"schema-aware、policy-aware 的数据库问答"，借鉴 Text2SQL 的上下文增强思路，同时坚守现有安全边界。

## 核心原则

- ✅ 增强生成前上下文（schema、描述、示例、策略）
- ✅ 保持执行层安全边界（allowlist、safe SQL kernel、审计、确认流）
- ❌ 不放开 JOIN/子查询/函数/SELECT * 限制
- ❌ 不绕过 SafeSqlKernel 自动重试执行

### S4.2 实现 SQL 修正流程（Agent 层）

**目标：** 允许 Agent 根据错误提示重新生成 SQL，但仍然通过 safe kernel 验证。

**执行步骤：**

1. 设计修正流程：
   ```
   用户问题
     ↓
   [retrieve_database_context] 获取上下文
     ↓
   [LLM 生成 SQL]
     ↓
   [safe_select_database 执行]
     ↓
   成功 ✓ → 返回结果
   失败 ✗ → 返回 SafeSqlBlocked + hint
     ↓
   [LLM 根据 hint 重新生成 SQL（最多 2 次）]
     ↓
   [safe_select_database 再次执行]
   ```

2. **关键约束：**
   - 最多重试 2 次（避免无限循环）
   - 每次重试都必须经过 `SafeSqlKernel` 验证
   - 不绕过任何安全检查
   - 如果 2 次都失败，返回友好错误："抱歉，当前查询超出数据库安全策略限制"

3. 实现位置：
   - **不要** 在 `safe_sql.py` 中实现（执行层应该保持纯粹）
   - **应该** 在 Agent 层或工具层实现重试逻辑

4. 伪代码示例：
   ```python
   def handle_database_query(user_query: str, max_retries: int = 2):
       context = retrieve_database_context(user_query)

       for attempt in range(max_retries + 1):
           sql = llm.generate_sql(user_query, context, previous_errors)

           try:
               result = safe_select_database(sql)
               return result
           except SafeSqlBlocked as e:
               if attempt == max_retries:
                   return f"查询受限：{e.hint['message']}"
               previous_errors.append(e.hint)

       return "无法生成符合安全策略的查询"
   ```

**验收标准：**
- [ ] 修正流程实现完成
- [ ] 最多重试 2 次
- [ ] 每次都经过安全验证
- [ ] 端到端测试：故意提供错误 SQL，验证能自动修正

**产出物：**
- `app/agents/database_query_handler.py`（新增）
- `tests/agents/test_database_query_handler.py`

## 附录：关键设计决策记录

### 决策 1：为什么不放开 JOIN/子查询/函数？

**原因：**
- 当前安全策略是有意设计，不是技术债
- 企业运维场景风险容忍度低
- 复杂查询可通过多次简单查询 + Agent 层聚合实现

**未来可能的例外：**
- 如果业务明确需要 GROUP BY + COUNT，可以考虑白名单允许特定聚合函数
- 必须先建立更严格的查询审计和审批流程

---

### 决策 2：为什么选择"检索上下文"而不是"塞全量 schema"？

**原因：**
- Token 成本：全量 schema 可能数千 tokens
- 精准度：检索能找到最相关的表和示例
- 扩展性：随着表增加，全量方案不可扩展

**Trade-off：**
- 检索不准确会影响生成质量
- 需要持续优化检索策略和示例库

---

### 决策 3：为什么最多重试 2 次？

**原因：**
- 1 次：太少，简单错误（如 SELECT *）无法修正
- 2 次：足够处理常见错误
- 3+ 次：收益递减，且可能进入循环

**实践经验：**
- 绝大多数错误（SELECT *、未授权列）1 次修正可解决
- 如果 2 次都失败，通常是需求超出安全策略，再试也无济于事

---

## 总结

**核心思路：**
- ✅ 借鉴 Text2SQL 的上下文增强（schema、描述、示例、策略）
- ✅ 保持安全边界（allowlist、safe kernel、审计、确认）
- ✅ 错误修正基于策略反馈，不绕过安全检查

**预期收益：**
- SQL 生成准确率提升 30-50%
- 用户体验显著改善（更少的拒绝，更清晰的错误提示）
- 保持零安全事故

**风险和缓解：**
- 风险：检索不准确导致生成质量下降
  - 缓解：持续优化示例库和 schema 描述
- 风险：性能开销增加
  - 缓解：缓存 + 限制检索数量
- 风险：复杂查询仍然无法满足
  - 缓解：明确沟通安全边界，引导用户使用多次简单查询

**成功标准：**
- SQL 生成成功率 > 80%
- 端到端延迟 < 3s
- 用户满意度显著提升
- 零安全事故
