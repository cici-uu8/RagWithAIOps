# 项目与成熟项目做法差距

日期: 2026-05-30

## 1. 文档目的

这份清单记录当前项目和成熟生产项目做法之间的差距，并把差距拆成可执行 backlog。

这里不把所有事情混成一个总优先级表。不同问题的触发条件不同:

- AIOps mainline 看 P6/P7 诊断链路稳定性、超时、trace 和 planner/executor/replanner 质量。
- RAG production readiness 看真实企业知识库里的检索质量、排序质量、成本、延迟和规模。
- Runtime readiness 看部署形态、重启恢复、长会话、human-in-the-loop 和多副本运行。

原则:

1. 方向对不等于立即改默认行为。
2. 成熟项目做法要先落到本项目的失败样本、指标或部署约束上。
3. 默认先 shadow/eval/benchmark，再改生产默认值。
4. 不用外部文章的收益数字直接替代本项目验证。
5. Memory/RAG/AIOps/Runtime 不混排优先级。

## 2. 如何使用这份文档

这份文档不是一次性总结，而是后续成熟化工作的 backlog 入口。

使用规则:

1. 每次只能从一个 backlog 中取一个小切口执行。
2. 执行前必须确认触发条件，不能因为“成熟项目一般会做”就直接改默认行为。
3. 每个小切口完成后，在本文件中更新状态，并同步 `task_plan.md` / `PROJECT_STATE.md` / 对应 development record。
4. 如果代码或默认行为发生变化，必须补验证命令、报告路径和不回归证据。
5. 如果某项只做了调研、benchmark 或 shadow/eval，没有改默认行为，也要明确记录“未改默认”的原因。

状态约定:

| 状态 | 含义 |
|---|---|
| 待执行 | 触发条件已基本成立，但还没进入实现或分析 |
| 待分析 | 需要先读日志/样本/报告，不能直接改代码 |
| 待设计 | 需要先写小设计或实验方案 |
| 暂缓 | 当前触发条件不成立 |
| 完成 | 已执行并有验证证据 |

进度跟踪:

- AIOps 项完成后，更新 `docs/aiops_mainline_development_record.md`。
- RAG 项完成后，更新 `docs/rag_fusion_development_record.md`。
- Runtime / checkpointer 项完成后，更新 `PROJECT_STATE.md`，并按实际归属补对应 record。
- 任何 backlog 状态变化，都同步 `task_plan.md` 和 `findings.md`。

## 4. 如何决定下一步方向

不要默认按文档顺序机械执行。先判断当前触发条件属于哪条线。

### 4.1 继续 AIOps 的条件

满足任一条件，才继续 AIOps mainline:

- P6/P7 或后续诊断 eval 出现新的 infra-stable 质量波动。
- 连续样本或日志显示 planner / executor / replanner 出现 timeout、structured-output failure、工具选择错误或恢复失败。
- 真实 oncall/pilot 反馈显示诊断链路不稳定、步骤遗漏、工具调用失败或最终报告不可用。
- 当前明确要提升诊断主链路，而不是知识库检索或部署可靠性。

当前判断:

- MCP cache 已收口。
- AIOps-1 MCP metrics 已完成并形成可聚合指标。
- AIOps-2 replanner timeout analysis 已完成。结论是 recovered primary structured-output fallback 没有进入 `degradation_events`，下一步如果继续编码，应先补观测链路，不直接调 prompt 或 timeout。
- E10-C 已补上 recovered structured-output fallback observability：fallback 成功仍保持 `has_error=false`，但会进入 `degradation_events`，所以这条已知 gap 不再作为下一轮默认 AIOps 工作。

不继续 AIOps 的条件:

- 只有 P6 分数未超过 7/12，但没有新的样本级失败证据。
- 问题实际来自 RAG 检索质量、知识库覆盖或 runtime 部署形态。

### 4.2 重新打开 RAG 的条件

满足任一条件，才重新打开 RAG production readiness:

- 有真实用户或 pilot 反馈说明检索不准、引用不可信、相似文档干扰严重。
- 有即将接入更大、更杂、更企业化知识库的明确计划。
- 新 eval corpus 扩大后，retrieval / citation / context 指标出现明显问题。
- 成本或延迟数据显示 embedding/search/rerank 已成为瓶颈。

当前判断:

- 现有 RAG audit 不支持 broad rewrite。
- 若 RAG 被重新打开，第一步是 RAG-1 reranker shadow/eval，不是直接默认开启 rerank。

不重新打开 RAG 的条件:

- 只是因为成熟项目常有 reranker、embedding cache 或更复杂 Milvus index。
- 没有新 corpus、新 eval、新反馈或规模压力。

### 4.3 进入 Runtime readiness 的条件

满足任一条件，才启动 Runtime-1 checkpointer 决策:

- 项目准备进入准生产或生产部署。
- 明确要支持服务重启后恢复会话。
- 明确要支持 human-in-the-loop 暂停/恢复。
- 明确要多副本部署并共享 session state。
- 当前 MemorySaver 造成真实 session 丢失或无法审计的问题。

当前判断:

- 部署形态未明确，所以 Runtime-1 保持待定。
- 不在部署约束未明确前强行替换 MemorySaver。

Deadline:

- 一旦确定准生产或生产上线窗口，必须在上线前完成本节决策。
- 如果上线形态要求多副本、重启恢复或 HITL，本项必须在上线前完成实现和 smoke test。

决策表:

| 部署/产品条件 | 决策 |
|---|---|
| 单机、短会话、允许重启丢失当前 session | 继续 `MemorySaver`，记录风险 |
| 单机、需要重启恢复当前 session | 评估 SQLite checkpointer |
| 多副本、需要共享 session | 评估 Postgres checkpointer + connection pool |
| 需要 HITL 暂停/恢复 | 持久 checkpointer 进入上线前必做 |
| 需要跨 session oncall 经验复用 | 不由 checkpointer 解决，仍归 Memory/P7 durable memory |

## 10. 回答: P6 full eval rerun 完成后改干什么

P6 full eval rerun 完成后，已经确认 MCP cache slice 有效，不能继续用“验证缓存是否有效”作为当前问题。

后续应该做的是:

1. 关闭 AIOps MCP cache slice。
2. 把“成熟项目差距”拆成独立 backlog，而不是混成一个 P1/P2 总表。
3. AIOps 如果继续，先补 MCP metrics，再分析 replanner structured-output timeout。
4. RAG 如果重新打开，先做 reranker shadow/eval，不直接默认开启。
5. Runtime 如果进入部署准备，先明确部署形态，再决定是否替换 MemorySaver。

不应该做的是:

- 不继续为了追回 P6 更高分调 prompt。
- 不把 P6 质量波动重新解释成 Memory/P7 未完成。
- 不直接开启 reranker 默认值。
- 不用 10 行 `@lru_cache` 冒充生产级 embedding cache。
- 不直接改 Milvus index 或 chunking 策略。
