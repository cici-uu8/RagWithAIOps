## 0.2 开发顺序

严格按 P0 -> P1 -> P2 推进。

P0 目标不是提升回答质量，而是让问题可定位：

1. 第 1 章：RAG diagnostics。
2. 第 2 章：DocumentProcessingWorkflow / worker health。
3. 第 3 章：Tool Execution Seam。

P1 目标是让产品入口和后端真实能力一致：

1. 第 4 章：QueryIntentRouter 和 KnowledgeRetrievalOrchestrator。
2. 第 5 章：权限申请双入口。
3. 第 6 章：前端 API client 和 capability health。
4. 第 7 章：SessionAccess 和持久会话。
5. 第 8 章：数据库 capability health 和 live Agent eval。

P2 目标是补证据和评测闭环：

1. 第 9 章：ChunkEvidenceMapper。
2. 第 10 章：原始资料导入和 RAG 评分闭环。
3. 第 11 章：AIOps tool catalog 和 failure semantics。

## 0.2.1 章节依赖关系

P0 -> P1 -> P2 是总顺序，但同一优先级内也有依赖。开工前按下表确认前置条件：

| 后续章节 | 前置依赖 | 原因 | 未满足时处理 |
|---|---|---|---|
| 第 4 章 `QueryIntentRouter` | 第 1 章 `RagDiagnostics` | Router decision 要进入 diagnostics / audit，否则无法解释为什么 list / retrieve / read | 只能做 taxonomy / 接口设计，不能验收完整链路 |
| 第 8 章数据库 live Agent eval | 第 3 章 `ToolExecutionFacade` | live DB Agent eval 必须验证真实 tool trace，不能绕过 ToolGateway | 先保留 reference runner，live 模式标 `not_ready_live_agent` |
| 第 10 章原始资料导入扩大 | 第 1、2、9 章 | 扩大导入需要 no_result_reason、worker 最终状态、source_ref / citation 可回查 | 只能继续小样本 smoke，不允许直接全量导入 |
| 第 11 章 AIOps 工具池和失败语义 | 第 3 章 `ToolExecutionFacade` | AIOps 工具目录要和统一工具执行 Seam 对齐 | 先做工具清单审计和 Adapter 技术验证 |

## 0.2.2 动态优先级调整

本清单不是强制把 11 章全部做完的流水线。每章开始前都要用最新 diagnostics、smoke 和用户现象重新判断：

- 如果前一章已经把某个问题解释清楚，并且后续章节收益下降，可以把后续章节标为 `deferred`，但必须在 `PROJECT_STATE.md` 和开发记录中说明原因。
- 如果出现新的 P0 用户可见故障，可以暂停 P1/P2，先回到对应 Module 处理。
- 不允许因为清单存在就机械施工；每次进入新章前都要确认它仍然服务当前问题台账。

## 0.3 每章通用收口规则

每章完成后都必须做四类收口：

1. 接口验证：跑本章列出的目标测试。

3. 文档验证：如改了接口、状态、评测或前端行为，同步更新相关文档。
4. 记录验证：更新 `PROJECT_STATE.md` 和 `docs/rag_fusion_development_record.md`。

每章验收通过后建议独立 commit，commit message 标注章节号，例如：


- 每章的“本章验收标准”就是最小完成边界；标注为 v2、后续迁移、可选增强的步骤不能阻塞 v1 验收。

## 0.4 禁止事项

- 不允许为了快速出效果绕过 `PermissionService` / `DocumentAccessService`。
- 不允许在 prompt 里硬编码权限、知识库范围或工具规则来替代 `ToolGateway`。
- 不允许把前端 localStorage 当成企业会话事实来源。
- 不允许在 PDF 仍未解析时把状态伪装成 `indexed`。
- 不允许在 RAG diagnostics 未完成前调 embedding、rerank 或检索算法默认值。
- 不允许继续只靠 Agent prompt 让大模型自行决定是否调用知识工具；小 LLM 意图识别必须先经过 LangChain / ModelGateway 的结构化输出进入 `QueryIntentRouter`，再经过权限、工具和 human_review 边界。
- 不允许把 SQLite reference runner 的结果说成 live LLM Agent 评测通过。
- 不允许把多个章节混在一个不可回滚的大改动里。

## 1.3 数据结构步骤

### Step 1：定义 `RagDiagnostics`

新增一个稳定结构，至少包含：

```text
requested_kb_ids
visible_kb_ids
selected_kb_ids
allowed_doc_count
indexed_doc_count
parse_pending_doc_count
parse_failed_doc_count
index_failed_doc_count
sparse_hit_count
dense_hit_count
hybrid_result_count
permission_filtered_count
fallback_mode
no_result_reason
tool_called
tool_name
trace_id
```

建议落点：

- 如果已有 response model 文件，放到相邻 model。
- 如果现阶段模型较轻，可先在 `knowledge_search_service.py` 内定义 dataclass，再在后续抽到独立 module。

### Step 2：冻结 `no_result_reason` 枚举

第一版至少支持：

```text
empty_query
selected_kb_not_visible_or_no_indexed_documents
no_visible_documents
documents_not_indexed
retrieval_no_hit
permission_filtered_all_results
worker_pending
tool_not_called
unknown
```

验收重点不是枚举多，而是每个无命中能落到一个稳定原因。

### Step 3：在 `DocumentAccessService` 层填权限统计

搜索前先计算：

- 当前用户可见 KB。
- 当前请求 KB。
- 实际 selected KB。
- selected KB 下可见文档数。
- indexed / pending / failed 文档数。

禁止在前端根据列表自行推断这些字段。

### Step 4：在 `RetrievalService` 层填召回统计

检索链路要暴露：

- sparse 原始命中数。
- dense 原始命中数。
- hybrid merge 后数量。
- rerank 后数量。
- 权限过滤数量。

如果某条路径暂时无法统计，明确返回 `null` 或 `not_available`，不要伪造 0。

### Step 5：让 `KnowledgeSearchService` 统一装配 diagnostics

`GET /api/knowledge-bases/{kb_id}/search` 和 `POST /api/knowledge-search` 都要返回同一 diagnostics shape。

scoped 搜索和 auto 搜索都必须显示：

- 用户请求哪些 KB。
- 系统实际搜索哪些 KB。
- 为什么没有搜索某个 KB。

### Step 6：让 Agent 工具调用带 diagnostics

`retrieve_knowledge` 工具要把：

- 当前 request scope。
- 实际调用参数。
- diagnostics。
- source_ref。

写入 tool artifact 或 audit metadata。

普通对话如果回答没有引用资料，至少能从 audit 或 SSE 里判断工具是否被调用。

### Step 7：前端知识库调试区展示 diagnostics

`static/knowledge-console.js` 的搜索调试区显示：

- 可见 KB。
- 实际搜索 KB。
- 可检索 indexed 文档数。
- pending / failed 文档数。
- dense / sparse / hybrid 召回数。
- `no_result_reason`。

用户界面展示中文 KB 名称，内部 `kb_id` 只作为调试辅助，不作为主要产品文案。

## 1.4 失败点和处理

| 失败点 | 处理 |
|---|---|
| diagnostics 需要遍历大量文档 | 第一版可按请求计算，文档量上来后加 metadata 聚合缓存 |
| sparse / dense 内部暂时不能返回统计 | 先返回 `not_available`，不要阻塞权限和数据状态 diagnostics |
| Agent 普通回答没有工具 trace | 先在 audit 中记录，再决定是否产品化展示 |
| auto 搜索没有选择 KB | 必须返回 selected 为空的原因，而不是只返回空结果 |

## 2. 第 2 章：DocumentProcessingWorkflow 和 Worker Health

对应问题：`docs/6 月 4 日项目存在问题和应对办法.md` 第 4 章。

优先级：P0。

目标：PDF 和异步文档处理不能长期无解释停在 `parse_pending` / `parsing` / `indexing`，所有处理中状态最终进入 `indexed`、`parse_failed` 或 `index_failed`，并给前端提供 worker / queue health。

| Adapter | RQ / Redis 是 Adapter，不拥有业务状态机 |

## 2.3 实现步骤

### Step 1：新增或加深 `DocumentProcessingWorkflow`

第一版 Interface：

```text
submit_upload()
enqueue_deferred_processing()
process_deferred_document()
reindex_document()
reconcile_stale_processing()
status_batch()
worker_health()
```

先把 route、queue、worker 中重复的状态判断收进 workflow。

### Step 2：冻结状态机

状态流转必须单调：

```text
uploaded
  -> parse_pending
  -> parsing
  -> index_pending
  -> indexing
  -> indexed
```

失败分支：

```text
upload_failed
enqueue_failed
parse_failed
index_failed
```

禁止从失败态自动回到处理中态，除非显式 reindex。

### Step 3：统一失败证据字段

失败态必须写：

```text
status_evidence
status_source
status_confirmed_at
error_code
error_message
job_id
```

如果字段当前不存在，先在 metadata JSON / document metadata 中兼容写入，再评估是否需要模型字段。

### Step 4：封装 RQ / Redis enqueue

`DocumentProcessingQueue` 只负责：

- 入队。
- 调用 workflow job handler。
- 暴露 queue adapter 状态。

它不再散落业务状态判断。

### Step 5：补 `worker_health()`

第一版 health 至少包含：

```text
queue_enabled
redis_connected
worker_seen_recently
failed_job_count
stale_processing_count
oldest_processing_age_seconds
```

如果无法准确判断 worker 活跃，返回 `unknown`，不能返回 `ok`。

### Step 6：读取状态前统一 reconcile

这些端点读取前调用 workflow reconcile：

- `GET /api/document-management`
- `GET /api/documents`
- `POST /api/documents/status-batch`
- 文件详情接口
- 知识库文档列表接口

### Step 7：前端状态展示升级

前端不能只显示“等待解析”。至少区分：

- 等待解析。
- 正在解析。
- 正在索引。
- worker 未确认运行。
- 解析失败。
- 索引失败。
- 超时失败。

## 2.4 失败点和处理

| 失败点 | 处理 |
|---|---|
| 本地 macOS worker 崩溃 | 优先用 failure hook + stale reconciliation 兜底，不把生产 worker 模式改成 macOS workaround |
| RQ failed registry 没有记录进程级崩溃 | 依靠 stale reconciliation 扫描处理中超时文档 |
| PDF parser 很慢 | 前端显示处理中年龄和 worker health，不伪造成功 |
| 用户重复点重建索引 | workflow 做幂等判断，已有处理中 job 时返回当前 job/status |

## 3. 第 3 章：ToolExecutionFacade 和 ToolGateway 全线接管

## 3.3 实现步骤

### Step 1：盘点所有工具入口

列出：

- HTTP 暴露能力。
- profile visible tools。
- RAG Agent tools。
- AIOps planner tools。
- AIOps executor tools。
- MCP discovered tools。
- database tools。

输出一个内部对照表，标明是否经过 `ToolGateway.execute()`。

### Step 2：新增 `ToolExecutionFacade`

第一版可以很薄：

```text
ToolExecutionFacade
  - list_visible_tools(context)
  - get_bindable_tools(context, capability)
  - execute(context, tool_name, input)
```

底层仍调用 `ToolGateway`，它的价值是让 Agent runtime 不直接拼 provider。

第一版不能长期退化成单纯 pass-through。它至少要拥有这些责任中的一部分：

- 统一 bindable tool schema。
- 统一 tool execution audit metadata。
- 统一 timeout / degraded / permission denied 的返回形状。
- 阻止 Agent runtime 直接持有 provider 或 MCP client。

如果第一 slice 只能先做到薄封装，必须在开发记录中写明下一步加深路径。

### Step 3：统一 bindable tool schema

把 LangChain bindable tools、OpenAI function schema、本地 callable adapter 收到一个转换层。

要求：

- 未授权工具不生成 bindable schema。
- schema 中保留 tool id / resource id。
- 执行闭包只能调用 facade / gateway，不能直接调用 provider。

### Step 4：RAG 工具接入 facade

`retrieve_knowledge`、database read-only tools 等 RAG 可用工具统一通过 facade 获取。

保留原工具名，避免破坏 prompt 和测试，但执行路径必须可审计。

### Step 5：AIOps 工具接入 catalog

先建立 `AIOpsToolCatalog`：

```text
visible_tools(context)
bindable_tools(context)
required_tools_for_scenario(scenario)
```

planner / executor / replanner 不再各自拼 local + MCP tools。

实现前先做技术验证：确认 LangGraph planner / executor / replanner 节点能否直接消费 `AIOpsToolCatalog.bindable_tools()` 的返回格式。如果返回格式不兼容，先加中间 Adapter，不要一次性重写 LangGraph 图。

### Step 6：统一工具失败审计

所有工具执行结果必须落：

- success audit。
- permission denied audit。
- provider error audit。
- timeout / degradation audit。

### Step 7：profile / UI 使用同一来源

`ProfileService` 的 visible tools 与 Agent bindable tools 必须来自同一 catalog / gateway 结果。

## 3.4 失败点和处理

| 失败点 | 处理 |
|---|---|
| AIOps LangGraph 需要特殊工具对象 | 用 Adapter 包装，不让 LangGraph 直接持有 provider |
| AIOps bindable tool 格式不兼容 | 先做技术验证；必要时保留节点形状，只替换工具来源 Adapter |
| MCP discovery 慢或失败 | Tool catalog 返回 degraded 状态，执行路径仍由 gateway 审计 |
| 老测试依赖固定工具数量 | 更新测试断言为工具名集合和权限语义，不依赖顺序 |
| 数据库工具有独立安全检查 | 保留 `SafeSqlKernel`，但入口仍通过 ToolGateway |

## 4. 第 4 章：QueryIntentRouter 和 KnowledgeRetrievalOrchestrator

对应问题：`docs/6 月 4 日项目存在问题和应对办法.md` 第 6 章。

优先级：P1。

目标：把知识库问答链路从“LLM Agent 自行判断是否调用工具”改成“先做可验证意图路由，再做检索编排，最后生成回答”。用户问 `中车长客数字化转型` 这类企业资料问题时，应稳定进入知识检索；用户问 `相关文件有什么` 时，应稳定进入文件清单；用户要求打开/总结某个文件时，应稳定进入文件读取。

## 4.1 所属架构边界

| 项 | 内容 |
|---|---|
| Module | `QueryIntentRouter`、`KnowledgeRetrievalOrchestrator`、`AnswerGenerator` |
| Seam | chat request -> query intent decision -> knowledge tool orchestration -> answer generation |
| Interface | `classify(query, context, scope)`、`plan(decision)`、`execute(plan)`、`build_answer(...)` |
| Adapter | LangChain / LangGraph Agent、现有 `list_knowledge_documents` / `retrieve_knowledge` / `read_knowledge_document` 工具、前端 KB scope 选择 |

本章不是替换已有 `StrategyRouter`。`StrategyRouter` 是 enterprise 级 shadow 路由，用于观察 `chat/rag/aiops/database/admin/human_review` 建议路线；本章要做的是知识问答内部的 query intent routing，用于区分 `document_list` / `knowledge_qa` / `document_read` / `plain_chat` / `database`。

上层 `StrategyRouter` 后续计划：当前只保留 shadow-only，不做 active execution router，不新增 `StrategyRouterActiveGate`，也不把它纳入本清单施工范围。后续如果重新明确提出“跨能力自动分流”需求，再单独开方案评估；在此之前不要为了第 4 章去改 enterprise 级执行路由。

### 4.1.1 分阶段边界

第 4 章按 v1 / v2 拆开执行，避免一次性把规则路由、小 LLM、LangGraph 迁移和评测全混在一起。

v1 必须完成：

- Step 1 intent taxonomy。
- Step 2 `QueryIntentDecision`。
- Step 3 deterministic rules。
- Step 4 前端 KB / 部门 scope 输入。
- Step 5 `KnowledgeRetrievalOrchestrator`。
- Step 6 `AnswerGenerator`。
- Step 9 diagnostics / audit。
- Step 10 路由评测集。

v2 / 后置增强：

- Step 7 小 LLM classifier。
- Step 8 LangGraph router node / conditional edges 迁移。
- 更多业务问法、低置信度仲裁和线上 drift 分析。

v1 验收不依赖小 LLM。`中车长客数字化转型`、`线上故障怎么处理`、`相关文件有什么` 这类当前问题，必须先由 deterministic rules + evalset 覆盖。

## 4.3 实现步骤

### Step 1：冻结 intent taxonomy

第一版 intent 只定义这些：

```text
document_list      # 相关文件有什么、列出资料、有哪些文档
knowledge_qa       # 企业资料问答、政策/流程/故障处理/数字化转型等需要检索回答
document_read      # 打开/读取/总结某个明确文件
plain_chat         # 不需要企业资料的普通聊天
database           # 查表、字段、SQL、创建表、改字段值等数据库任务
permission_request # 申请知识库/tool/database/document 权限
human_review       # 高风险、不可自动执行或需要人工审批的请求
```

同时定义 knowledge action：

```text
list      -> list_knowledge_documents
retrieve  -> retrieve_knowledge
read      -> read_knowledge_document
none      -> 不调用知识工具
handoff   -> 转数据库/权限申请/human_review
```

### Step 2：定义 QueryIntentDecision

字段必须足够解释“为什么检索 / 为什么没检索”：

```json
{
  "intent": "knowledge_qa",
  "knowledge_action": "retrieve",
  "provider": "rules|llm_classifier",
  "confidence": 0.86,
  "selected_kb_ids": ["process_digital_dept"],
  "selected_doc_ids": [],
  "scope_source": "user_selected|auto_visible",
  "requires_retrieval": true,
  "handoff": null,
  "fallback_intent": "plain_chat",
  "reason": "企业资料知识问答，应检索流程与数字化部可见资料"
}
```

### Step 3：实现 deterministic rules

规则第一版要覆盖：

- 文件清单类：`相关文件有什么`、`有哪些文档`、`列出资料`、`知识库里有什么`。
- 知识问答类：`中车长客数字化转型`、`线上故障怎么处理`、`工艺流程怎么做`、`制度/流程/手册/方案`。
- 文件读取类：`打开某个文件`、`读取 xxx.pdf`、`总结 xxx 文档`。
- 数据库类：`查询表`、`字段`、`SQL`、`创建新表`、`把某字段改成...`。
- 权限申请类：`申请工艺部知识库权限`、`申请数据库 read`、`申请 tool use`。
- 高风险类：数据库写、DDL、授权、删除、生产操作，先 route 到 handoff / human_review，不直接执行。

规则要可单测，不能藏在 prompt 里。

### Step 4：接入前端 KB / 部门选择

左侧加号或知识库选择得到的 scope 进入后端请求上下文：

```text
selected_kb_ids
scope_source=user_selected
```

未选择时：

```text
selected_kb_ids = 当前用户可见 KB 自动候选
scope_source=auto_visible
```

验收重点：用户选择“流程与数字化部”后，`中车长客数字化转型` 只在该 scope 内检索；用户不选时，在权限允许范围内自动检索，不要求用户手动指定 KBID。

### Step 5：实现 KnowledgeRetrievalOrchestrator

Orchestrator 只做编排，不做权限判断的旁路：

```text
document_list  -> list_knowledge_documents(kb_id/scope)
knowledge_qa   -> retrieve_knowledge(query, knowledge_base_ids=selected_kb_ids)
document_read  -> read_knowledge_document(file_name/doc_id, knowledge_base_ids=selected_kb_ids)
plain_chat     -> 不调用知识工具，交给普通回答
database       -> handoff 到数据库能力，后续仍走 ToolGateway / SafeSqlKernel
permission_request -> handoff 到权限申请入口
human_review   -> handoff 到人工审批
```

所有知识工具仍必须经过 `DocumentAccessService` / `RagAdapter` / `RetrievalService`，不能直接读 metadata store 绕过权限。

### Step 6：AnswerGenerator 收口回答

把回答生成从工具选择中拆出来：

- `document_list`：展示可见文件清单和 KB 名称。
- `knowledge_qa`：基于 retrieval context 和 source_ref 回答。
- `document_read`：基于读取内容总结或展示。
- `plain_chat`：普通对话。
- `database/permission/human_review`：告诉用户已进入对应流程或需要确认。

如果 `knowledge_qa` 没有结果，必须携带 diagnostics，不要直接让模型自由发挥。

### Step 7：小 LLM 分类器作为 v2 可选第二层

是否需要小 LLM：后续需要，但 v1 不能把它作为硬依赖或唯一判断来源。

实现要求：

- 通过 LangChain / 现有 `ModelGateway` 调用。
- 使用 structured output，输出 `QueryIntentDecision` 兼容字段。
- 只在 rules 低置信度或规则冲突时触发。
- 超时、未配置、输出不合法时降级到 rules。
- 不直接执行数据库写、DDL、授权、生产操作。

禁止新引入脱离 LangChain / LangGraph 的独立 agent framework。

### Step 8：LangGraph 兼容路径作为 v2 迁移约束

如果后续把该能力放进 LangGraph，形状应是：

```text
router node
  -> conditional edge: document_list
  -> conditional edge: knowledge_qa
  -> conditional edge: document_read
  -> conditional edge: plain_chat
  -> conditional edge: database
  -> conditional edge: permission_request
  -> conditional edge: human_review
```

第一版可以先用普通 service 编排，但 Interface 必须能迁移成 LangGraph node。

### Step 9：diagnostics / audit

每次决策记录：

- 原始 query。
- selected_kb_ids。
- scope_source。
- intent。
- knowledge_action。
- provider。
- confidence。
- reason。
- actual_tool_called。
- fallback_reason。

这些字段要能进入第 1 章 `RagDiagnostics`，用于解释“为什么没有检索 / 为什么没有命中 / 为什么列了文件”。

### Step 10：路由评测集

新增一组 query intent evalset，至少覆盖：

```text
中车长客数字化转型 -> knowledge_qa / retrieve / process_digital_dept 或 auto_visible
线上故障怎么处理 -> knowledge_qa / retrieve
相关文件有什么 -> document_list / list
这个文件主要讲什么 -> document_read / read 或先 list 再 read
查询订单表有哪些字段 -> database / handoff
把订单金额改成 100 -> database 或 human_review，不直接知识库回答
申请工艺部知识库权限 -> permission_request
你好 -> plain_chat
```

维护规则：每新增一条 Router rule，必须先补或同步补一条 evalset case。新增用户问法先落 evalset，再补 rule，避免规则半年后只靠人工记忆维护。

## 4.4 失败点和处理

| 失败点 | 处理 |
|---|---|
| Router 把知识问答误判成 plain_chat | 用 evalset 锁定企业资料关键词和可见 KB 触发规则 |
| Router 把文件清单误判成 retrieve | 文件清单类规则优先级高于普通 knowledge_qa |
| 用户选了部门但 Router 搜了全部 KB | `scope_source=user_selected` 必须作为强约束进入 Orchestrator |
| 小 LLM 未配置或超时 | 降级 rules，记录 `fallback_reason=llm_unavailable` |
| 数据库写被误走知识库回答 | database / high-risk 规则优先，handoff 后仍经 ToolGateway / SafeSqlKernel / human_review |
| prompt 和 Router 冲突 | Router decision 是事实来源，prompt 只消费 decision，不重新定义路由规则 |

## 4.7 本章 v1 验收标准

- `中车长客数字化转型` 这类企业资料问题稳定进入 `knowledge_qa/retrieve`。

- 每条 Router rule 都有对应 evalset case；新增问法先补 evalset case 再补 rule。
- Router decision 进入 diagnostics / audit，能解释每次用了 list、retrieve、read、plain_chat 还是 handoff。

## 5.3 实现步骤

```text

document
```

### Step 2：前端拆入口

权限申请页拆成：

```text
知识库快捷申请
高级资源申请
```

两个入口最终都调用同一个 permission request API。

### Step 3：知识库快捷申请

字段：

- 知识库：下拉选择中文名。
- 访问级别：部门资料。
- 理由：textarea，默认空也允许。

公开资料不需要出现在授权申请里；公开资料应由系统自动允许 public read。

### Step 4：高级资源申请

字段：

- 资源类型：tool / database / document。

- action：从 resource metadata 中可选。
- 理由：textarea。

禁止用户手写不存在的 resource id。

## 10. 第 10 章：原始资料导入和 RAG 评分闭环

## 10.3 执行步骤

### Step 1：冻结当前小样本状态

记录：

- imported doc_id。
- kb_id。
- status。
- source_ref。
- PDF job_id。

不确认小样本前不全量导入。

### Step 2：做小样本人工 smoke

- 知识库列表。
- 文件管理。
- PDF 状态。
- 搜索调试。
- sample DB catalog。

### Step 3：跑 RAG diagnostics

针对：

### Step 4：跑 RAG 20 题评测

```bash
uv run python -m evals.knowledge_base.run_department_rag_eval \
  --evalset evals/knowledge_base/evalsets/department_rag_20q.jsonl
```

每题必须输出：

```text
status
no_result_reason
selected_kb_ids
source_ref
answer_score
failure_category
```

### Step 5：决定是否扩大导入

只有满足以下条件才扩大：

- `review_status=pending` 为 0。
- 小样本没有跨部门错误。
- PDF 有最终状态或明确失败态。
- RAG eval 不再整体 `not_ready`。
- source_ref 可回查。

Escape hatch：

- 如果 `not_ready` 的根因被 diagnostics 证明是 eval 框架自身问题，而不是数据未导入、worker 未完成、权限不可见或检索无召回，可以先做人工 smoke + 小批量导入。
- 这种情况报告必须标注 `eval_framework_blocked`，并写清楚 blocked 的 eval 模块、人工 smoke 证据、导入批次上限和回滚方式。
- escape hatch 只允许小批量，不允许直接全量导入。

### Step 6：扩大 reviewed import

先扩大到小批量：

```bash
uv run python scripts/knowledge_assets/import_original_files.py --apply --limit 10
```

确认后再考虑更大批次。

### Step 7：每次扩大后重跑评测

每次导入后立即跑：

- RAG 20 题。
- unscoped 4 题。
- scoped isolation smoke。

### Step 8：更新报告

生成报告到：

```text
evals/knowledge_base/reports/
```

报告必须区分：

- data_not_indexed。
- no_retrieval_hit。
- wrong_scope。
- citation_missing。
- answer_wrong。

## 10.4 失败点和处理

| 失败点 | 处理 |
|---|---|
| PDF 仍 pending | 不扩大导入，先回第 2 章处理 worker health |
| RAG eval 仍全 not_ready | 先查 indexed_doc_count 和 diagnostics，不调模型参数 |
| eval 框架自身 blocked | 标注 `eval_framework_blocked`，可在人工 smoke 通过后小批量导入，不允许全量 |
| 出现跨部门命中 | 停止扩大导入，回查 visibility 和 allowed_doc_ids |
| source_ref 缺失 | 回第 9 章补 ChunkEvidenceMapper |
