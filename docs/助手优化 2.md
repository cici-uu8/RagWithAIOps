# 助手优化 2

## 0. 结论

`助手优化 2` 只在 `助手优化 1` 完成后启动。

`助手优化 1` 解决普通用户侧问题：

- 我是谁。
- 我能用什么。
- 我能看哪些知识库。
- 为什么某些能力不可用。
- 聊天、上传、AIOps 请求如何带可信登录态。

`助手优化 2` 解决管理员侧问题：

- 用户由谁创建。
- 系统管理员和部门管理员如何管理用户。
- 如何给用户、角色、部门授权。
- 如何管理知识库、工具、模型、数据库表列等资源范围。
- 如何审批权限申请和高风险任务。
- 如何审计谁在什么时候改了什么权限。

因此，优化 2 不是把更多说明文字塞进聊天页，而是新增一个真正的管理后台。前端要实现管理界面，但权限判断不能放在前端；前端只负责展示入口和提交操作，后端必须继续用 `CurrentUser`、admin dependency、`PermissionService` 和 audit 做最终校验。

默认注册策略建议采用“管理员创建用户”，不开放注册即使用。后续如需用户自助注册，只能做成“申请加入”，申请通过前账号不能访问企业资源。

## 1. 为什么必须做完优化 1 再做优化 2

管理后台依赖优化 1 的基础身份和能力发现。如果优化 1 没完成，优化 2 会缺少稳定入口和可信上下文：

- 没有登录态，前端无法判断当前是不是管理员。
- 没有 `/api/me/profile`，前端无法决定是否显示管理后台入口。
- 没有统一 `Authorization: Bearer <token>`，管理 API 只能退回不可信 header 或临时身份。
- 没有 401 / 403 错误处理，管理员操作失败时用户无法区分登录过期、权限不足和系统错误。
- 没有可见知识库 / 可用工具 / database-demo 状态，授权页面无法解释授权后用户实际能看到什么。

优化 2 启动门槛：

- 优化 1 的登录、登出、token 过期处理已经完成。
- 左下角用户入口能显示当前用户。
- `/api/me/profile` 能返回当前用户、角色、部门、可见知识库、可用工具和 feature flags。
- 普通用户看不到管理后台入口。
- admin 用户能看到管理后台入口。
- 聊天、上传、AIOps 请求都能基于 Bearer token 生成可信 `RequestContext`。
- 401 / 403 / 500 有明确前端提示。

未满足以上门槛时，不做优化 2 的前端管理台。否则管理台会看起来可用，但实际身份、权限和错误解释仍然不可靠。

## 2. 当前后端事实

当前后端已经有一部分管理基础：

- `/api/admin/users`：用户列表、创建、更新、禁用。
- `/api/admin/roles`：角色列表、创建、更新、删除。
- `/api/admin/grants`：resource grant 列表、授权、撤权。
- `/api/admin/audit`：按 trace、user、event type、时间范围查询 audit。
- `/api/admin/reviews/pending`：高风险任务待审批列表。
- `/api/admin/reviews/{review_id}/approve`：审批通过。
- `/api/admin/reviews/{review_id}/reject`：审批拒绝。

这些 API 目前更接近 E8 的“最小管理 API”，还不是完整管理后台。

现有边界：

- 非 admin 访问管理 API 返回 403。
- admin role 只是管理 API 的入口保护，不代表 admin 可以绕过所有资源权限。
- 工具、文档、数据库资源仍应以 `PermissionService` 的 grant / deny 结果为准。
- 授权和撤权会触发权限缓存失效。
- 管理操作需要写 audit。

当前缺口：

- 没有管理后台前端。
- 没有部门管理员产品流。
- 没有部门资源范围模型。
- 没有权限申请 / 审批流。
- 没有资源目录页面，管理员不知道可授权的 document、kb、tool、model、database table / column 有哪些。
- 没有授权前预览，管理员不知道这条 grant 会让谁获得什么能力。
- 没有权限变更后的用户侧 profile 刷新闭环。

## 3. 用户注册和创建策略

### 3.1 默认策略：管理员创建

第一版建议只支持管理员创建用户。

原因：

- 企业系统不能只靠用户自填部门。
- 用户自填角色存在越权风险。
- 用户能看哪些知识库、工具和数据库表列，必须由管理员或部门管理员显式授权。
- 当前项目还没有企业 SSO / LDAP / CAS，不适合开放自助注册即激活。

管理员创建用户流程：

1. 系统管理员进入管理后台。
2. 打开“用户管理”。
3. 点击“创建用户”。
4. 填写 username、初始密码、部门、角色。
5. 保存后系统写 audit。
6. 管理员再按需要给该用户、所在部门或角色授予资源权限。
7. 用户登录后通过 `/api/me/profile` 看到自己的角色、部门、可见知识库和可用能力。

### 3.2 可选策略：用户申请加入

如果后续确实需要自助注册，不能做成“注册后直接可用”，而应做成“申请加入”：

1. 用户打开登录页，点击“申请账号”。
2. 填写 username、姓名、邮箱、申请部门、申请原因。
3. 后端创建 `pending_user_request`，不是正式用户。
4. 系统管理员或对应部门管理员审批。
5. 审批通过后才创建正式用户并分配部门、角色和初始权限。
6. 审批拒绝时记录原因，申请人不能登录系统。

申请账号的默认权限：

- 不能聊天。
- 不能上传。
- 不能看知识库。
- 不能使用工具。
- 不能进入管理后台。

### 3.3 不推荐策略：开放注册

第一版不做开放注册。

不推荐原因：

- 无法验证部门归属。
- 无法确认资源范围。
- 容易出现默认权限过大或默认权限解释不清。
- 会把“账号体系”和“权限体系”两个问题同时打开，增加风险。

## 4. 管理角色模型

### 4.1 系统管理员

系统管理员是全局治理角色。

能做：

- 创建、更新、禁用所有用户。
- 创建、更新、删除角色。
- 创建和管理部门。
- 指定部门管理员。
- 给 user / role / department 授权或显式 deny。
- 管理全局 tool allowlist。
- 管理模型 endpoint 可见性。
- 管理 database schema registry 和表列权限。
- 查看全局 audit / trace。
- 审批所有高风险任务。
- 审批所有权限申请。

不能做：

- 不能绕过后端权限服务直接访问资源。
- 不能在前端伪造用户身份。
- 不能通过聊天自然语言直接执行高风险管理动作。

### 4.2 部门管理员

部门管理员是 scoped admin，不是小号系统管理员。

能做：

- 查看本部门用户。
- 创建或邀请本部门普通用户。
- 禁用本部门普通用户。
- 修改本部门普通用户的部门内属性。
- 给本部门用户授予本部门可管理范围内的资源权限。
- 撤销本部门用户的资源权限。
- 查看本部门相关 audit。
- 审批本部门权限申请。

不能做：

- 不能查看其他部门用户。
- 不能给任何人授予 `admin` 角色。
- 不能创建系统级角色。
- 不能跨部门授权。
- 不能授予自己没有管理权的知识库、工具、模型或数据库资源。
- 不能查看全局 audit。
- 不能管理 database schema registry 的全局配置。

部门管理员需要后端明确 scope：

```json
{
  "admin_scope": {
    "scope_type": "department",
    "department_id": "dept_1",
    "manageable_resource_types": [
      "document",
      "tool",
      "database_table",
      "database_column"
    ],
    "manageable_resource_ids": [
      "kb:guide",
      "tool:retrieve_knowledge",
      "database_table:sandbox.incidents"
    ]
  }
}
```

### 4.3 普通用户

普通用户只管理自己的使用体验。

能做：

- 查看个人资料。
- 查看我的权限。
- 查看可见知识库。
- 查看可用工具和不可用原因。
- 提交权限申请。
- 使用已授权的聊天、上传、AIOps、database-demo 等能力。

不能做：

- 不能进入管理后台。
- 不能创建用户。
- 不能给自己或别人授权。
- 不能查看其他用户 audit。
- 不能通过前端参数修改自己的角色或部门。

## 5. 权限和资源范围模型

优化 2 继续沿用当前 `ResourceGrant` 的基本形态：

```text
principal_type: user / role / department / public
principal_id: user_id / role_id / department_id / *
resource_type: document / kb / tool / model_endpoint / database_table / database_column / admin_review
resource_id: 具体资源 id
action: read / use / manage / approve
effect: allow / deny
reason: 授权原因
```

核心规则：

- 默认 deny。
- 显式 allow 才可用。
- deny 优先于 allow。
- admin 不是资源访问的隐式 bypass。
- 前端只能用 feature flags 控制入口展示，不能代替权限判断。
- 所有管理操作必须写 audit。

建议补充 grant 元数据：

```json
{
  "grant_id": "grant_xxx",
  "created_by": "user_admin",
  "created_reason": "dept_1 needs guide KB access",
  "owner_department_id": "dept_1",
  "expires_at": null,
  "status": "active"
}
```

这样后续管理员能回答：

- 这条权限是谁给的。
- 为什么给。
- 给到什么时候。
- 属于哪个部门的管理范围。
- 撤权会影响哪些用户。

## 6. 管理后台前端设计

### 6.1 入口

优化 1 的左下角用户菜单中增加：

```text
管理后台
```

展示条件：

- `feature_flags.admin = true`
- 或 `feature_flags.department_admin = true`

普通用户不显示入口。即使普通用户手动访问管理后台 URL，后端 API 仍必须返回 403，前端显示“你没有权限访问管理后台”。

建议路径：

```text
/static/admin-console.html
```

旧聊天页和执行看板继续保留：

```text
/                          普通聊天入口
/static/enterprise-dashboard.html  执行看板
/static/admin-console.html         管理后台
```

### 6.2 管理后台导航

第一版管理后台包含以下页面：

```text
概览
用户管理
部门管理
角色管理
权限授权
资源目录
权限申请
高风险审批
审计查询
```

系统管理员能看到全部页面。

部门管理员只看到：

```text
概览
本部门用户
本部门权限
资源目录（只读，限本部门可管理资源）
权限申请
审计查询（本部门范围）
```

### 6.3 概览页

展示：

- 当前管理员身份。
- 当前管理范围。
- 用户数量。
- 待处理权限申请数量。
- 待审批高风险任务数量。
- 最近管理操作。
- 最近权限拒绝事件。

不要在概览页放复杂图表。第一版以表格和状态摘要为主。

### 6.4 用户管理页

系统管理员功能：

- 用户列表。
- 搜索 username / user_id / department。
- 筛选 active / disabled。
- 创建用户。
- 更新用户名、部门、角色。
- 重置密码。
- 禁用用户。

部门管理员功能：

- 只能看本部门用户。
- 只能创建本部门普通用户。
- 只能禁用本部门普通用户。
- 不能分配 `admin` 或其他系统级角色。
- 不能把用户移动到其他部门。

创建用户表单字段：

```text
user_id
username
password
department_id
department_name
roles
```

当前 MVP 的后端 `AdminUserCreateRequest` 和管理后台 UI 都要求 `user_id` 为必填；`is_active` 只在更新 / 禁用路径处理，`created_reason` 尚未接入创建用户 API。

保存后：

- 后端写 audit。
- 前端显示新用户。
- 如需要，提示管理员继续配置权限。

### 6.5 部门管理页

第一版部门管理只做必要能力：

- 部门列表。
- 创建部门。
- 编辑部门名称。
- 指定部门管理员。
- 查看部门下用户数量。
- 查看部门可管理资源范围。

需要新增后端部门模型，否则部门只存在于 `UserProfile.department_id` 字段里，无法表达部门 owner 和管理范围。

建议模型：

```json
{
  "department_id": "dept_1",
  "department_name": "Department 1",
  "admin_user_ids": ["user_dept1_admin"],
  "resource_scope_ids": ["kb:guide", "tool:retrieve_knowledge"],
  "is_active": true
}
```

### 6.6 角色管理页

第一版角色不要做复杂继承。

内置角色：

- `admin`
- `department_admin`
- `user`

系统管理员可以创建业务角色，例如：

- `ops_reader`
- `db_demo_reader`
- `kb_guide_reader`

角色页面功能：

- 角色列表。
- 创建角色。
- 修改角色名称和描述。
- 删除未被使用的自定义角色。
- 查看角色当前拥有的 grants。

部门管理员不能创建全局角色。后续如需要，可以允许部门管理员创建部门内 role alias，但第一版不做。

### 6.7 权限授权页

这是管理后台的核心。

授权表单字段：

```text
principal_type: user / role / department
principal_id
resource_type: document / kb / tool / model_endpoint / database_table / database_column
resource_id
action: read / use / manage
effect: allow / deny
reason
expires_at
```

列表筛选：

- principal_type
- principal_id
- resource_type
- resource_id
- action
- effect
- owner_department_id

操作：

- 新增 grant。
- 撤销 grant。
- 查看 grant 影响范围。
- 查看 grant 关联 audit。

授权前必须做预览：

```text
这次授权将影响：
- principal: department dept_1
- resource: kb guide
- action: read
- effect: allow
- 预计影响用户: 12
- 当前存在 deny: 1
- 生效后仍被 deny 阻断的用户: 1
```

预览结果来自后端，不由前端自己计算。

### 6.8 资源目录页

管理员授权前必须知道有哪些资源可以授权。

资源目录第一版至少包含：

- 知识库 / 文档。
- 工具。
- database-demo 表。
- database-demo 列。
- 模型 endpoint。

每类资源展示：

```text
resource_type
resource_id
name
owner_department_id
status
actions_supported
description
```

数据库资源展示要特别谨慎：

- 未授权用户不显示可执行 SQL 入口。
- 已授权用户只显示可见表和可见列。
- 所有数据库入口都标明只读。
- DML / DDL / 多语句仍由后端阻断。

### 6.9 权限申请页

普通用户提交申请：

```text
申请访问 guide 知识库
申请使用 database-demo
申请查看 sandbox.incidents 表
申请使用某个工具
```

管理员处理：

- 查看申请人。
- 查看申请理由。
- 查看申请资源。
- 查看申请人当前已有权限。
- approve。
- reject。

通过后：

- 后端创建 grant。
- 写 audit。
- 申请状态变为 approved。
- 申请人下次刷新 `/api/me/profile` 后看到新能力。

拒绝后：

- 写拒绝原因。
- 不创建 grant。

### 6.10 高风险审批页

接已有 F6 Human-in-the-loop API。

页面展示：

- review_id。
- task_id。
- trace_id。
- 申请用户。
- 风险原因。
- 请求摘要。
- 创建时间。
- 当前状态。

操作：

- approve。
- reject。
- 填写审批原因。
- 跳转 trace / audit。

审批通过后第一版不自动恢复原任务。继续按 F6 当前边界：用户或后台用 `review_id` / `task_id` 重新提交同一任务。

### 6.11 审计查询页

支持按以下条件筛选：

- trace_id。
- user_id。
- event_type。
- decision。
- resource_type。
- resource_id。
- 时间范围。

系统管理员看全局审计。

部门管理员只看本部门范围：

- 本部门用户产生的事件。
- 本部门资源相关事件。
- 本部门管理员自己的管理操作。

审计页不要提供删除功能。

## 7. 需要补的后端 API

### 7.1 系统管理员 MVP 可复用现有 API

第一版系统管理员后台可以先接现有接口：

```text
GET    /api/admin/users
POST   /api/admin/users
PATCH  /api/admin/users/{user_id}
POST   /api/admin/users/{user_id}/disable

GET    /api/admin/roles
POST   /api/admin/roles
PATCH  /api/admin/roles/{role_id}
DELETE /api/admin/roles/{role_id}

GET    /api/admin/grants
POST   /api/admin/grants
DELETE /api/admin/grants/{grant_id}

GET    /api/admin/audit

GET    /api/admin/reviews/pending
POST   /api/admin/reviews/{review_id}/approve
POST   /api/admin/reviews/{review_id}/reject
```

这能先完成“系统管理员可以通过 UI 管理本地用户、角色、授权和审计”的闭环。

### 7.2 部门管理员需要新增 API

部门管理员不能只靠前端筛选，需要后端强校验。

建议新增：

```text
GET    /api/admin/departments
POST   /api/admin/departments
PATCH  /api/admin/departments/{department_id}

GET    /api/admin/scope
GET    /api/admin/resources
POST   /api/admin/grant-preview

GET    /api/admin/permission-requests
POST   /api/permission-requests
POST   /api/admin/permission-requests/{request_id}/approve
POST   /api/admin/permission-requests/{request_id}/reject
```

`/api/admin/scope` 用于告诉前端当前管理员能管理什么。

示例：

```json
{
  "scope_type": "department",
  "department_id": "dept_1",
  "can_manage_users": true,
  "can_manage_roles": false,
  "can_manage_global_grants": false,
  "manageable_resource_types": ["document", "tool"],
  "manageable_resource_ids": ["doc-guide", "tool:retrieve_knowledge"]
}
```

### 7.3 授权预览 API

新增：

```text
POST /api/admin/grant-preview
```

作用：

- 预估授权影响用户。
- 检查是否超出管理员 scope。
- 检查是否已有 deny。
- 检查是否重复授权。
- 返回可解释结果，给前端展示。

前端必须先 preview，再允许提交正式 grant。

不要把阶段 3 preview 实现成唯一的 `POST /api/admin/grants/preview`。当前已有动态路由 `DELETE /api/admin/grants/{grant_id}`，`preview` 会被当成 `grant_id` 匹配并返回 405；阶段 3 应优先使用 `/api/admin/grant-preview`，或显式注册 `/api/admin/grants/preview` 并确认路由冲突测试。

## 9. UI 统一方案

### 9.1 技术栈选择

当前前端事实：

- 聊天页是 `static/index.html`、`static/app.js`、`static/styles.css`，原生 HTML / Vanilla JS。
- 聊天页已经承载优化 1 的登录、左下角用户入口、个人资料弹层和错误提示。
- E11 执行看板是独立 Vue3 CDN 页面：`static/enterprise-dashboard.html`。
- 当前仓库没有 `package.json`、Vite、pnpm lock 或前端组件工程。

因此优化 2 不做“全站 Vue3 重写”，也不为了统一视觉去修改现有聊天页或 E11 执行看板。推荐技术栈：

```text
/                                  聊天页：保留原生 HTML / JS
/static/enterprise-dashboard.html  执行看板：保留 Vue3 CDN
/static/admin-console.html         管理后台：新增 Vue3 CDN
```

这样做的理由：

- 管理后台有大量表格、筛选、表单、状态切换，Vue3 比原生 DOM 拼接更适合。
- 聊天页当前已经在原生 JS 中实现用户入口和登录态，优化 2 不应为了 UI 统一重写聊天主路径。
- E11 已证明 Vue3 CDN 可以在当前静态目录下低成本运行。
- 不引入构建链，能保持当前项目的静态前端部署方式。

### 9.2 不采用的方案

第一版不采用以下方案：

- 不重写聊天页为 Vue3。
- 不引入 Vite / npm / pnpm 前端工程。
- 不引入 Element Plus / Ant Design Vue 等完整 UI 框架。
- 不新增 Web Components 作为原生 JS 和 Vue3 的共享层。

原因：

- 重写聊天页会把优化 2 从管理后台扩成前端重构，范围过大。
- 当前仓库没有前端工程化基础，引入构建链会改变部署和验证方式。
- 完整 UI 框架会带来样式重置和交互差异，容易和现有聊天页冲突。
- Web Components 会形成原生 JS、Vue3、Web Components 三套前端写法，维护成本更高。

### 9.3 共享设计令牌

三类页面不共享组件库。第一版也不要求现有聊天页和 E11 看板改成新的 CSS 变量。

优化 2 的 UI 统一原则是：

- 以现有聊天页和 E11 看板作为视觉基准。
- 新增管理后台主动贴近现有视觉语言。
- 不反向要求现有 `static/index.html`、`static/app.js`、`static/styles.css`、`static/enterprise-dashboard.html`、`static/enterprise-dashboard.css` 修改。
- 如果未来要把现有页面也迁到统一 CSS 变量，必须作为独立前端重构任务另行评估和验收。

建议新增：

```text
static/enterprise-ui.css
```

用途：

- 定义统一颜色。
- 定义统一字体。
- 定义统一间距。
- 定义统一按钮、输入框、选择框、表格、弹窗、toast、状态 badge。
- 第一版只要求新增管理后台引用。
- 聊天页和执行看板只作为取色、间距和交互风格参考，不在优化 2 中改动。

这组颜色兼容现有聊天页的 Google-style 蓝色和 E11 看板的企业蓝，不切换到新的 Element Plus 默认蓝，避免又引入第三套视觉语言。

### 9.4 布局统一

三类页面保持同一个产品骨架：

```text
左侧导航 / 列表
右侧主工作区
左下角或右上角用户入口
统一 toast / modal / empty / error 状态
```

聊天页：

- 左侧是会话列表。
- 主工作区是对话。
- 左下角是用户入口。

执行看板：

- 左侧是 trace / route 列表。
- 主工作区是实时输出和阶段时间线。
- 优化 2 不要求改执行看板。

管理后台：

- 左侧是管理导航。
- 主工作区是表格、详情、表单和审批流。
- 用户入口放左侧底部或右上角均可，但样式复用优化 1 的账号入口规范。

### 9.5 系统管理员和部门管理员 UI 统一

系统管理员和部门管理员使用同一个管理后台，不拆成两个页面。

前端启动时调用：

```text
GET /api/admin/scope
```

根据后端返回结果控制导航：

- 系统管理员看到全部导航。
- 部门管理员只看到本部门用户、本部门权限、资源目录、权限申请、审计查询。
- 普通用户看不到管理后台入口，即使直达 URL 也只能看到无权限页。

导航隐藏只是体验优化，不能替代后端 scope 校验。

### 9.6 管理后台视觉原则

管理后台是操作型产品，不做营销页、装饰页或大 hero。

设计原则：

- 信息密度高于聊天页。
- 表格、筛选、详情抽屉、确认弹窗是主形态。
- 页面标题和按钮文案要短。
- 表单必须显示必填、错误和后端拒绝原因。
- 授权、撤权、审批、禁用用户必须有二次确认。
- 成功 toast 只说明结果，不替代 audit。

### 9.7 管理后台交付方式

外部建议中提到“Vue3 单文件应用”和 `Vue3 + Vite`。这里需要区分两个概念：

- 可以做 Vue3 单页管理后台。
- 第一版不做 `.vue` Single File Component 工程。
- 第一版不引入 Vite、npm、pnpm、Vue CLI 或新的前端构建产物目录。

原因是当前仓库前端仍是静态资源模式，E11 看板也是 Vue3 CDN 页面。优化 2 的目标是补管理后台，不是改变整个项目的前端交付方式。

第一版文件建议：

```text
static/admin-console.html      管理后台入口
static/admin-console.js        管理后台 Vue3 CDN 应用逻辑
static/admin-console.css       管理后台页面样式
static/enterprise-ui.css       新增管理后台优先使用的轻量设计令牌和基础控件样式
```

开发方式：

```text
启动现有 FastAPI 服务
访问 /static/admin-console.html
修改 static/admin-console.js / static/admin-console.css 后刷新浏览器
```

验证方式：

```text
node --check static/admin-console.js
curl -i http://localhost:9900/static/admin-console.html
curl -i http://localhost:9900/static/admin-console.js
curl -i http://localhost:9900/static/admin-console.css
```

如果未来确实需要 Vite，应作为“前端工程化迁移”单独立项，并重新评估：

- 是否迁移聊天页。
- 是否迁移 E11 执行看板。
- 构建产物如何挂载。
- 本地启动脚本和部署脚本如何变化。
- 如何避免影响现有 `/` 聊天入口。

### 9.8 管理后台路由方式

第一版使用 hash 路由，不使用后端多页面路由。

推荐 URL：

```text
/static/admin-console.html#/              概览
/static/admin-console.html#/users         用户管理
/static/admin-console.html#/users/:id     用户详情
/static/admin-console.html#/departments   部门管理
/static/admin-console.html#/roles         角色管理
/static/admin-console.html#/grants        权限授权
/static/admin-console.html#/resources     资源目录
/static/admin-console.html#/permission-requests      权限申请
/static/admin-console.html#/reviews       高风险审批
/static/admin-console.html#/audit         审计查询
```

这样刷新页面时，FastAPI 只需要返回同一个静态 HTML，不需要新增 `/admin/users`、`/admin/audit` 之类的 fallback 路由。

实现选择：

- 可以用一个轻量 `location.hash` router。
- 也可以后续用 Vue Router CDN 的 hash mode。
- 第一版不要求引入 Vue Router，只要路由状态、左侧导航 active 状态和刷新恢复稳定即可。

路由守卫必须做两层：

1. 前端启动时检查 token 和 `/api/me/profile`，非管理员显示无权限页。
2. 每个管理 API 仍由后端校验 admin role 或 department admin scope。

前端守卫只改善体验，不作为安全边界。

### 9.9 管理后台错误处理

管理后台需要统一 `adminFetch()`，不要在每个页面散写 fetch 逻辑。

`adminFetch()` 至少负责：

- 自动读取优化 1 已确定的 token storage key。
- 自动加入 `Authorization: Bearer <token>`。
- 解析后端 `detail`、`reason`、`trace_id`。
- 把 401 / 403 / 500 / 网络断开转成统一 UI 提示。

错误语义：

```text
401 未登录或 token 过期：
清除本地 token，提示重新登录，并提供返回聊天页登录入口。

403 权限不足：
显示“你没有权限执行该操作”，并尽量展示后端 reason，例如“超出当前部门管理员 scope”。

409 / 422 业务校验失败：
显示后端 detail，例如“用户名已存在”“grant 已存在”。`resource_id` 是否存在需要依赖阶段 3 的资源目录和后端校验；当前 MVP 的 Grant 表单只负责提交，不验证资源目录。

500 后端处理失败：
显示“后端处理失败”，如果响应里有 trace_id，必须展示 trace_id 方便查 audit / logs。

网络断开：
显示“无法连接后端服务，请检查服务是否启动或稍后重试”。
```

典型操作提示：

- 创建用户失败：显示后端返回的用户名冲突、字段缺失或密码策略原因。
- 授权失败：显示是否超出管理员 scope、资源不存在、重复授权或 deny 阻断。
- 撤权失败：显示 grant 不存在、无权撤销或该权限来自角色 / 部门继承。
- 审批失败：显示 review 已处理、无审批权限或任务状态已变化。

这些提示要和优化 1 的 401 / 403 / 500 语义一致，但不要求改动现有聊天页 UI。

## 10. 管理操作效率优化

### 10.1 用户详情页直接管理权限

只做独立“权限授权”页面会让常见路径过长。

管理后台应支持：

```text
用户管理 -> 点击用户 -> 用户详情
```

用户详情页包含：

- 基本信息。
- 当前角色。
- 当前部门。
- 当前直接授予的 grants。
- 通过角色继承的 grants。
- 通过部门继承的 grants。
- 被 deny 阻断的 grants。
- 快速授权。
- 快速撤权。
- 最近权限相关 audit。

快速授权仍然必须走后端 preview：

```text
选择资源 -> 选择 action -> 填 reason -> preview -> confirm -> create grant
```

### 10.2 创建用户后的下一步动作

管理员创建用户后，前端不要只返回列表。

创建成功后给出三个动作：

```text
继续创建
进入用户详情
为该用户授权
```

这样符合真实管理流程：创建用户通常只是第一步，后面马上要分配部门、角色或资源。

### 10.3 批量授权

批量授权是有价值的，但不放在系统管理员 MVP 的第一步。

建议阶段：

- 阶段 2 系统管理员 MVP：只做单用户、单角色、单部门授权。
- 阶段 4 部门管理员 scope 稳定后：再做批量授权。

批量授权入口：

```text
用户管理 -> 勾选多个用户 -> 批量授权
部门管理 -> 选择部门 -> 给部门授权
角色管理 -> 选择角色 -> 给角色授权
```

批量授权必须先 preview：

- 影响多少用户。
- 多少用户已拥有该权限。
- 多少用户会被 deny 继续阻断。
- 是否超出当前管理员 scope。
- 是否会创建重复 grant。

### 10.4 权限模板

第一版不新增独立“权限模板”模型。

当前 `ResourceGrant` 已支持 `principal_type=role`，可以先用角色 grant 表达模板效果：

```text
role: ops_reader
grant: kb guide read
grant: tool retrieve_knowledge use
grant: database_table sandbox.incidents read
```

用户获得 `ops_reader` 角色后，通过角色继承这些 grants。

后续只有在以下情况出现时，再考虑独立权限模板：

- 角色数量过多且难以管理。
- 同一批权限需要跨多个角色复制。
- 需要模板版本、发布、回滚。
- 需要模拟“套用模板前后差异”。

### 10.5 授权撤销路径

撤权不能要求管理员先知道 grant_id。

每个权限展示位置都应支持撤销：

- 用户详情页撤销该用户直接 grant。
- 角色详情页撤销 role grant。
- 部门详情页撤销 department grant。
- 权限授权页按筛选结果撤销 grant。

如果权限来自角色或部门，用户详情页不能直接删除继承来源，只能提示：

```text
该权限来自 role=ops_reader，请到角色详情撤销；或为该用户新增 deny。
```

## 12. 风险和边界

### 12.1 不要做前端权限假象

前端可以隐藏入口，但不能决定权限。任何管理动作必须由后端重新校验。

错误做法：

```text
if user.roles includes department_admin, 前端自己过滤 dept_1 用户，然后直接调用全局授权 API
```

正确做法：

```text
前端展示 dept_1 管理页面
后端根据 token 计算 admin scope
后端判断这次操作是否在 scope 内
后端写 audit
```

### 12.2 不要把自注册当成企业账号体系

自注册只能降低申请门槛，不能代替管理员授权。第一版不做开放注册。

### 12.3 不要让聊天执行管理动作

管理动作应通过管理后台表单完成，不通过自然语言直接执行。

原因：

- 管理动作需要预览影响范围。
- 管理动作需要明确 reason。
- 管理动作需要二次确认。
- 管理动作必须写结构化 audit。

聊天可以解释“如何申请权限”，但不能替管理员直接创建 grant。

### 12.4 不要一次接完整 IAM / SSO

第一版先把本地 admin console 和本地权限模型跑通。SSO / LDAP / CAS 属于后续集成，不阻塞优化 2。

### 12.5 不要删除审计和授权历史

用户可以被禁用，grant 可以被撤销，但审计记录不能被前端删除。

### 12.6 不要为了统一 UI 重写聊天页

优化 2 的目标是管理后台，不是前端全站重构。

当前聊天页已经承载优化 1 的核心体验，重写聊天页会带来额外风险：

- 旧对话体验可能回归。
- 上传、AI Ops、流式对话和历史会话可能受影响。
- 优化 2 的验收焦点会从管理能力偏移到前端迁移。

第一版只做轻量统一：新增管理后台复用现有视觉语言和基础控件规范，不反向改现有 UI。

## 14.1 优化 1 回归修复：对话历史账号隔离

当前发现对话历史存在账号隔离漏洞，应在继续阶段 4 部门管理员前插队修复。这个问题不是优化 2 管理后台的新能力，而是优化 1“聊天请求带可信登录态”和“用户只能看到自己的使用侧数据”的回归。

已确认风险：

- 前端 `localStorage` 使用全局 `chatHistories` key，不按 `user_id` 分桶；同一浏览器上不同账号会共享侧边栏历史。
- 退出登录只清 `enterpriseAuthToken`，不切换或隔离历史桶；用户 A 退出后，用户 B 登录仍可能看到 A 的历史标题和内容。
- `/api/chat/session/{session_id}` 和 `/api/chat/clear` 当前没有强制绑定 `CurrentUser`；拿到 `session_id` 的用户可能读取或清空不属于自己的 session。
- `/api/chat` / `/api/chat_stream` / `/api/aiops` 如果允许续接他人 `session_id`，还会形成会话污染风险。
- `/api/aiops` 当前对未传 `session_id` 的请求 fallback 成 `session_id="default"`，等于把所有未带 id 的诊断请求合并到一个共享桶，跨用户读写。

修复原则：

- 前端必须做真实数据隔离，不做“渲染时过滤”的假隔离。
- 后端 session 必须有 owner 校验；只修前端或只修后端都不完整。
- 登出不应清空所有用户历史；推荐保留当前用户自己的桶，切换账号时只加载当前用户桶。
- 未登录不能进入聊天主路径，因此前端不引入 anonymous 桶，避免和优化 1 §0“聊天请求带可信登录态”相互矛盾。

建议实施范围：

1. 前端历史 key 从 `chatHistories` 改为 `chatHistories:${user_id}`。
2. 升级时一次性删除旧的 `chatHistories` 全局 key；旧数据无法可靠归属，统一清除。
3. 登录成功、退出登录、token 过期、跨标签 storage 事件时重新加载当前身份对应的历史桶；当前 tab 只响应自己 user 桶的变更，忽略其他桶的写入。
4. 保存历史时只写当前身份桶；不要把不同用户历史合并到一个数组。token 过期立即跳转登录，不允许在无 token 状态写 `chatHistories`。
5. 后端为 session 增加 owner 记录，最小实现可以先使用内存 owner map，后续 Runtime 持久化时再落库。session ownership 采用 first-write-wins 语义：第一次见到某个 `session_id` 时写入当前用户为 owner，后续他人发同一 `session_id` 返回 403；客户端必须用 UUID v4 生成 `session_id`，碰撞概率忽略不计。
6. `/api/chat` / `/api/chat_stream` / `/api/aiops` 在创建 session 时写入 owner；续接已有 session 时校验 owner。`/api/aiops` 必须停止 `session_id="default"` 共享桶 fallback，未传 session_id 时改为后端按 `user_id` 派生默认桶或要求客户端必传。
7. `/api/chat/session/{session_id}` 和 `/api/chat/clear` 增加 `CurrentUser` 依赖；session 不存在返回 404，owner 不匹配返回 403。
8. session owner 只能来自已验证的登录态，不接受前端可伪造的 `X-User-Id` / `X-Username` 头作为 owner 来源；必须基于 `CurrentUser` 或等价的已验证 JWT 身份。
9. 所有拒绝访问写 audit：复用现有 `permission_checked` event_type，`decision="denied"`，`metadata.denial_reason="session_owner_mismatch"`，并补齐 `resource_type="chat_session"` / `action="read|clear|write"`，便于和现有权限审计共线检索，不新增 event_type。

验收标准：

- admin 登录后创建一条对话，退出后 demo_user 登录，看不到 admin 的历史。
- demo_user 创建对话后切回 admin，admin 看不到 demo_user 的历史。
- 同一用户退出再登录，仍能看到自己的历史。
- 无 token 调用 `/api/chat/session/{session_id}` 返回 401。
- 其他用户 token 调用不属于自己的 `/api/chat/session/{session_id}` 返回 403。
- 其他用户 token 调用不属于自己的 `/api/chat/clear` 返回 403。
- 其他用户用不属于自己的 `session_id` 发 `/api/chat` 或 `/api/chat_stream` 返回 403，不能污染原会话。
- 其他用户用不属于自己的 `session_id` 发 `/api/aiops` 返回 403，不会落入共享 `default` 桶。
- 测试覆盖前端 localStorage 分桶、退出/登录切桶、后端 session owner 校验。

这项是优化 1 的契约回归：违反 §0“聊天请求带可信登录态”和 §4.3“普通用户不能查看其他用户使用侧数据”两条已声明完成的承诺。按“在功能扩展前先修复已声明完成的回归债务”的工程实践，应优先于阶段 4 部门管理员、阶段 5 权限申请、full grant preview 推进，避免新功能持续叠加在已知漏洞上。紧急度：高，建议本周内热修。
