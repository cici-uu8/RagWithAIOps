### 0.4 隐式 stage 6.5：数据持久化触发条件

阶段 4-6 的第一版可以继续沿用 in-memory service，但这只能是过渡方案，不是长期默认。

一旦出现下面任一条件，就必须单独开 `stage 6.5` 数据持久化计划，不能继续把 in-memory 当长期方案：

- `permission_requests > 50`
- `departments > 5`
- `users > 500`
- catalog resources > 1000
- audit events > 100000
- 服务重启次数已经超过月度容忍上限，或用户开始因为重启丢失申请而重复提交
- grant / audit 的体量开始让后端只读过滤明显退化

后续的持久化计划必须明确数据落库、清理、恢复和重启一致性，不允许只把临时方案默认延长。

## 2. 阶段 4：部门管理员 scoped admin

### 2.1 目标

让 `department_admin` 成为真正的 scoped admin，而不是前端隐藏按钮：

- 系统管理员仍有全局管理能力。
- 部门管理员只能看本部门用户。
- 部门管理员只能创建 / 禁用本部门普通用户。
- 部门管理员不能授予 `admin` 或 `department_admin`。
- 部门管理员只能授权自己 scope 内资源。
- 部门管理员只能看本部门相关 audit。

### 2.2 锁定决策

- `admin` 是全局系统管理员。
- `department_admin` 是 scoped admin。
- 第一版不做部门层级树，不做跨部门继承。
- 第一版部门模型使用 in-memory service，和当前 Auth / Permission MVP 风格一致。
- 部门管理员 scope 的权威来源是后端 `DepartmentService` / `AdminScopeService`，不是前端根据 roles 自己判断；scope 只在 routes dependency 里解析一次，后续 service / validator 只消费 `scope_context`。
- 部门管理员不能创建角色，不能删除角色，不能改系统角色。
- 部门管理员的资源 scope 第一版来自 `DepartmentRecord.manageable_resources`，不是从 grant 反推；校验时使用 `(resource_type, resource_id, action)` 三元组，不能只比较裸 `resource_id`。
- 部门资源 scope 第一版只允许 global admin 通过后端 API 配置，department admin 不能修改自己的 scope。
- `system` 部门是全局系统管理员的虚拟部门，用于 seed 和展示，不参与 department admin scope，不代表一个可被部门管理员管理的业务部门。
- 部门管理员默认不能管理 model endpoint，因为 model endpoint 尚未进入 resource catalog 第一版。
- 本阶段不做部门删除、重命名或迁移；`department_id` 视为不可变。如果后续要支持这些动作，必须单独定义级联 / 迁移策略。
- `department_admin` 种子必须在 `AdminService._roles` 中存在，阶段 4 的第一条 scope 测试才能真正跑起来。
- 角色、部门或禁用状态变化后的 JWT 失效使用 per-user `token_invalid_after` 方案：`AuthService.invalidate_tokens_for_user(user_id)` 记录时间戳，`validate_access_token()` 先读 `payload.iat_ms`，没有时回退到 `payload.iat * 1000`，并拒绝 `issued_at <= token_invalid_after[user_id]` 的旧 token；不尝试枚举并逐个 blacklist 该用户所有历史 token。

## 3. 阶段 5：权限申请

### 3.1 目标

普通用户不再通过聊天问“能不能给我开权限”，而是走系统内权限申请：

- 普通用户提交权限申请。
- 管理员或部门管理员查看 pending 申请。
- approve 后自动创建 allow grant。
- reject 后记录拒绝原因。
- 用户可查看自己的申请状态。
- 所有申请和审批写 audit。

当前实现状态（2026-06-01）：

- Task 5.1 / 5.2 / 5.3 已按 C 方案完成代码、验证和独立提交：Stage 5 主提交 `99d3d4c`，审计字段补丁 `d825034`。
- 后端新增 `app/enterprise/permission_requests/*`，用户提交、我的申请、管理员列表、approve、reject 已挂载到 `/api/permission-requests*` 和 `/api/admin/permission-requests*`。
- 前端复用现有聊天页用户菜单和管理后台静态 Vue3/hash route，不重写聊天主界面；管理后台 route key 固定为 `permission-requests`。
- approve/reject audit 已补齐审批链路：decision event metadata 包含 `approver_user_id`，approved event metadata 包含 `grant_id`，`AuditEvent.reason` 记录审批人填写的 reason 而不是申请人原始 reason。

### 3.2 锁定决策

- 第一版只支持“用户为自己申请权限”，不支持代他人申请。
- 第一版申请的 principal 固定为 `principal_type="user"`、`principal_id=current_user.user_id`。
- 第一版不做申请撤回。
- 第一版不做审批流多级流转。
- 部门管理员只能审批本部门用户的申请，且资源必须在自己的 scope 内。
- 跨部门申请采用 C 方案：申请先归属 requester 所在部门队列，同时用 `requires_global_review=true` 让 global admin 也可见。这样 dept_2 员工的申请不会进 dept_1 队列；dept_2 admin 能看到本部门员工申请，但 scope 外资源不能 approve，只能 reject 或保持上抛给 global admin。
- `review_queue` 第一版只允许两类取值：`department:<department_id>` 或 `global`。
- 跨部门判定算法：先找出包含 `(resource_type, resource_id, action)` 的所有 `candidate_department_ids`。如果 requester 的 `department_id` 是业务部门且该部门存在 department admin，则 `review_queue="department:<requester_department_id>"`；当 requester 部门不在 `candidate_department_ids` 时设置 `requires_global_review=true`，global admin pending 列表也必须看到。只有 requester 没有可用业务部门或没有任何部门管理员时，才退化为 `review_queue="global"` 且 `requires_global_review=true`。例如 dept_2 用户申请 dept_1 scope 内资源时，记录进入 `department:dept_2`，同时 `requires_global_review=true`。
- approve 必须走 `GrantValidator` 和 scoped admin check，不能绕过 preview-lite / scope。
- 权限申请不是 F6 高风险任务审批，单独建模块，不复用 `app/enterprise/reviews`。
- 审计 event_type 使用 `permission_request_*`，不复用 `human_review_*`；后续可以在管理后台做统一“审批视图”，但底层审计命名保持两条业务线分开。
- 管理后台“权限申请”入口必须显示当前 actor 可审批 pending 数的 badge；badge 不是全局 pending 总数。
