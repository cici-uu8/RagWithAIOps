# 项目最后优化2执行清单

## 背景

对照 LangGraph、Langfuse、Supabase、Dify、Semantic Kernel 等成熟项目，当前项目的主要缺口不是底层能力，而是**产品化的可见性、审计、评测和治理层**。本清单聚焦“看得见、管得住”的可见性层，不做全开放写操作，不做无结构扩张。

这份清单已经按 `docs/项目完整架构.md` 的架构铁律修订：新 HTTP 用户请求不能绕过 `RequestGateway`；数据库能力不能绕过 `ToolGateway` / `SafeSqlKernel`；后台聚合逻辑不能散落在 FastAPI route 里。

## 总体原则

1. **只做可见性**：先补 viewer / explorer / dashboard，不先开放全量写能力。
2. **只读优先**：database catalog 只读，memory 只做 operator review，audit 只做查询聚合。
3. **架构门禁优先于页面实现**：P0/P1/P2 的后端入口先满足 gateway / adapter / service 边界，再做前端。
4. **复用既有代码**：优先复用 P7 memory、E9 audit、admin-console 资源页和既有 database/tool gateway 边界。
5. **明确不做边界**：
   - 不做全开放 SQL 编辑器，只做只读 catalog + guarded sample preview。
   - 不做 Memory 自动 promotion，保持 operator review。
   - 不做散装 prompt 目录或无结构 skill 文件夹。
   - 不把成本控制单独立项，等明确花费压力后条件触发。
   - 不把 Skill 工程独立产品化，等明确扩展生态需求后条件触发。

## 架构合规门禁

以下门禁是开发前置条件，不满足就不能按本清单开工。

### 1. 新 HTTP 入口必须走 RequestGateway

允许路径：

```text
FastAPI route
  -> CurrentUser / GatewayRequest
  -> Adapter
  -> RequestGateway.execute(...)
  -> Domain Service
```

禁止路径：

```text
FastAPI route
  -> 直接调用 MemoryStore / SQLiteAuditSink / DB connection
  -> 手写 trace / audit / permission
```

说明：`RequestGateway` 负责 request_started / request_completed / request_failed、trace_id、request_id、guardrail 和 request 级审计。领域 service 仍然可以写领域审计，例如 `memory_review`、`database_query`、`tool_call`，但不能替代 gateway 入口。

### 2. 新数据库能力必须走 ToolGateway / SafeSqlKernel

`sample rows`、`table stats`、未来真实 DB catalog 都属于数据库能力。无论是 HTTP 展示还是 Agent tool 调用，都不得绕过：

- `ToolGateway.execute(context, tool_id, arguments)`
- `tool/use` 权限
- `database/read`、`database/write`、`database/admin` 权限
- registry allowlist
- `SafeSqlKernel` / SQL classifier / operation permission checker
- audit

第一版 sample 只能用已授权表和已授权列构造 `SELECT <authorized_columns> FROM <canonical_table> LIMIT <n>`，再通过 safe-select tool 执行。不能使用 `SELECT *`，不能直接查 `information_schema` / `sqlite_master`，不能绕过 allowlist 拼 SQL。

### 3. Ops 聚合逻辑必须进 service / adapter

Ops dashboard 的 route 只做 auth、参数解析和 gateway 调用。audit 查询与指标聚合放到 `OpsMetricsService`，HTTP 入口通过 `OpsMetricsAdapter` 暴露。route 里不能直接调用 `SQLiteAuditSink.query(...)`。

### 4. 不扩展历史绕行入口

项目里已有一些历史 route 可能直接调用 service。它们可以作为兼容存量存在，但本清单新增 P0/P1/P2 能力时不能继续扩大直接 route -> service 的模式。

## 优先级

| 优先级 | 任务 | 状态 | 边界 |
|---|---|---|---|
| **P0a** | Memory Operator 后端控制面 | 已完成，后端 API 稳定 | 只做 review queue / validation status / deprecation preview / approve / reject / owner deprecate |
| **P0b** | Memory Operator UI | 已完成，集成到 admin-console | UI 明确标注 Memory 仍默认 off，仅供 operator review |
| **P1** | Sandbox / Demo DB Catalog Browser | 可执行，限定范围 | 只展示 sandbox / database-demo / 已授权 MySQL allowlist，sample 必须走 ToolGateway |
| **P2** | Audit / Trace Ops Dashboard | P0/P1 后或并行小切片执行 | 只做 trace / audit / tool / route / latency / failure，不做成本 |
| **P3** | 成本统计 | 条件触发 | 等明确成本压力或稳定 usage baseline 后再做 |
| **P4** | Skill Registry | 条件触发 | 等明确扩展生态需求后再做 |

# P0a: Memory Operator 后端控制面

## 目标

把现有 memory operator CLI 能力暴露为**架构合规的最小 HTTP 控制面**，用于 operator 审批和治理。它不是 Memory 产品化完成，也不是把 durable memory 默认接入主 prompt。

## 现状

- 已有 `app/services/memory_store.py`：持久化 `MemoryRecord`，提供 `list_memories`、`get`、`upsert`、`get_validation_policy_status`、`record_aiops_diagnosis` 等能力。
- 已有 `app/services/memory_review_service.py`：提供 `list_review_queue`、`approve_candidate`、`reject_candidate`、`build_owner_deprecation_plan`、`deprecate_owner_memories` 等 operator review 能力。
- 已有 `app/services/memory_evidence_store.py`：L0 evidence 存储与 evidence TTL 清理；它和 durable memory review 不是同一层。
- 已有 `app/cli/memory_operator.py`：operator CLI。
- 已补齐：经过 `RequestGateway` 的 admin HTTP API。
- 已补齐：最小 UI 已集成到 admin-console，见 P0b。

## 不做

- 不做全 L0/L1/L2 Explorer。
- 不做 Memory 自动 promotion。
- 不把 memory 默认塞进主 prompt。
- 不做 durable memory 物理删除。durable memory 的治理先做 owner-scoped deprecation preview / deprecate；L0 evidence TTL 清理只能标注为 evidence cleanup，不等同于 durable memory cleanup。

## 后端文件清单

- 新增：`app/enterprise/admin/memory_operator_adapter.py`
- 新增：`app/enterprise/admin/memory_operator_routes.py`
- 修改：`app/main.py` 或既有 router 注册点，挂载 `/api/admin/memory-operator/*`
- 新增：`tests/test_memory_operator_adapter.py`
- 新增：`tests/test_memory_operator_routes.py`
- 新增或更新：`docs/memory_operator_api_design.md`

## API 设计

```text
GET  /api/admin/memory-operator/review-queue?owner_id=default&limit=20
POST /api/admin/memory-operator/atoms/{memory_id}/approve
POST /api/admin/memory-operator/atoms/{memory_id}/reject
GET  /api/admin/memory-operator/validation-status?owner_id=default
POST /api/admin/memory-operator/deprecation-preview
POST /api/admin/memory-operator/deprecate-owner
```

请求体示例：

```json
{
  "decision_note": "validated by operator"
}
```

注意：`reviewer_id` 不允许由前端传入，必须从 `RequestContext.user_id` 派生。

## 合规实现要求

1. route 只做 `CurrentUser` / admin 角色检查、请求参数解析、`GatewayRequest` 构造。
2. route 调用 `RequestGateway.execute(gateway_request, handler)`；handler 内调用 `MemoryOperatorAdapter`。
3. `MemoryOperatorAdapter` 接受 `RequestContext`，包装 `MemoryReviewService` / `MemoryStore`。
4. `list_review_queue` 调用真实方法 `MemoryReviewService.list_review_queue(owner_id=...)`。
5. approve/reject 调用 `approve_candidate` / `reject_candidate`，`reviewer_id=context.user_id`。
6. deprecation preview 调用 `build_owner_deprecation_plan(owner_id=...)`，不删除数据。
7. owner deprecate 调用 `deprecate_owner_memories(owner_id=..., reviewer_id=context.user_id, decision_note=...)`，必须要求二次确认 owner_id。
8. 领域审计可以在 adapter/service 内写 `memory_review`，但 request 级审计必须由 `RequestGateway` 统一写。

## 验收标准

1. admin 可以查询 review queue。
2. 非 admin 返回 403。
3. approve/reject 使用 `RequestContext.user_id` 作为 reviewer，不接受 body 伪造 reviewer。
4. deprecation preview 不修改数据。
5. deprecate-owner 需要 confirm_owner_id，且只 mark deprecated，不做 destructive delete。
6. audit 中能看到 request_started / request_completed 或 request_failed，以及领域 `memory_review` 事件。
7. 文档明确标注 Memory 仍默认 off，P0a 只是 operator 控制面。

# P1: Sandbox / Demo DB Catalog Browser

## 目标

创建数据库 catalog browser，让用户查看自己有权限的 sandbox / database-demo / allowlisted MySQL 数据库、表、列和 sample rows。它是授权范围内的只读 viewer，不是真实企业 DB 管理台。

## 现状

- 已有 `DatabaseCapabilityCatalogService`。
- 已有 `SafeSqlKernel`。
- 已有 `ToolGateway.execute(context, tool_id, arguments)`。
- 已有 `/api/database/safe-select` 存量端点。
- 已有 admin-console 资源页，按 table / column 展示资源。
- 缺失：独立 browser UI 与经过新合规入口的 sample rows preview。

## 不做

- 不做任意 SQL 编辑器。
- 不展示未授权列。
- 不用 `SELECT *`。
- 不直接访问业务 DB connection。
- 不直接查询 `information_schema` / `sqlite_master` 作为第一版 stats。

## 后端文件清单

- 新增：`app/enterprise/database/catalog_adapter.py` 或在既有 database adapter 边界中新增 catalog 方法
- 修改：`app/enterprise/database/routes.py`，新增 route 时必须走 `RequestGateway`
- 修改：`app/enterprise/database/catalog.py`，如需补 `get_authorized_columns` / canonical table lookup
- 新增：`tests/test_database_catalog_sample_api.py`
- 新增或更新：`docs/database_catalog_browser_design.md`

## API 设计

```text
GET /api/database/catalog
GET /api/database/{database_id}/tables/{table_name}/sample?limit=10
GET /api/database/{database_id}/tables/{table_name}/stats
```

说明：`/api/database/catalog` 如果沿用存量端点，不能在其上继续增加绕过 gateway 的新逻辑。新增 sample / stats 必须走 `RequestGateway`。

## 合规实现要求

1. route 构造 `GatewayRequest` 并调用 `RequestGateway.execute(...)`。
2. adapter/service 先从 registry/catalog 获取 canonical database/table/column 描述。
3. adapter/service 做权限过滤，只保留当前用户已授权列。
4. sample SQL 只能形如：`SELECT <authorized_columns> FROM <canonical_table> LIMIT <n>`。
5. `limit` 需要限制范围，例如 1-50；默认 10。
6. SQL 执行必须调用 `ToolGateway.execute(context, tool_id, {"sql": sql})`。
7. tool_id 使用已注册 safe-select tool，例如 `database_demo.safe_select` 或 allowlisted MySQL safe-select tool。
8. `SafeSqlKernel` 继续负责 SQL 安全校验、masking、result size、timeout 和 `database_query` audit。
9. stats 第一版可以返回 `row_count_estimate: null`、`size_bytes: null`；若要做 count，也必须经 safe-select tool 执行 guarded `COUNT(*)`。不能 route 直接查系统表。

## 验收标准

1. 有权限用户可以看到授权 database/table/column。
2. 无 table 权限用户 sample 返回 403。
3. 有 table 权限但只有部分 column 权限时，sample 只返回授权列。
4. 未授权列名不出现在 `columns`，也不出现在 `rows`。
5. sample 结果 JSON-safe。
6. audit 中有 `tool_call` 和/或 `database_query`，且 request 级 audit 由 `RequestGateway` 记录。
7. 页面或文档明确标注：只展示 sandbox / database-demo / allowlisted DB，不是真实 DB 管理台。

1. **P0a 先行**：先落 `MemoryOperatorAdapter + RequestGateway route`，用测试锁住 reviewer_id、audit、deprecation preview 边界。
2. **P1 可并行小切片**：先做 sample rows 后端，确保 `ToolGateway + SafeSqlKernel + authorized columns` 闭环，再做 UI。
3. **P0b 跟随 P0a**：P0a API 稳定后再补 UI。
4. **P2 在 audit query seam 明确后执行**：先补 `OpsMetricsService` 和 adapter，再做 dashboard。
5. **P3/P4 等触发**：不提前实现。

# 总体验收口径

每个任务完成后，必须满足：

1. 后端 API 单元测试通过。
2. 前端集成测试通过。
3. 浏览器手工验收通过。
4. `PROJECT_STATE.md` 与对应设计文档更新。
5. 开发记录更新：非平凡实现步骤写入 `docs/rag_fusion_development_record.md`；Memory 专项写入 `docs/memory_fusion_development_record.md`。
6. 与 `docs/项目完整架构.md` 不冲突：新入口走 `RequestGateway`，数据库能力走 `ToolGateway` / `SafeSqlKernel`，ops 聚合进 service/adapter。

# 长期风险与控制

| 风险 | 如果不控制会怎样 | 控制方式 |
|---|---|---|
| route 直接调 service | 新功能绕过 trace/audit/guardrail，架构铁律失效 | P0/P1/P2 route 测试断言 request audit 存在 |
| DB sample 变成隐形 SQL 编辑器 | 泄漏未授权列或绕过 SQL guard | 禁止 `SELECT *`，只允许 authorized columns + safe-select tool |
| Memory UI 被误解为产品化完成 | 评审时被追问主链路为何仍 default-off | UI 和 PROJECT_STATE 明确“operator review only” |
| Ops dashboard 伪造成本能力 | 没有 baseline 却显示成本，后续难以验收 | P2 response 不含 cost/token cost 字段 |
| P3/P4 提前做 | 投入大且偏离当前项目主线 | 保持条件触发，触发前只保留计划 |
