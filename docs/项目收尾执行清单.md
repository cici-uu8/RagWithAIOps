# 项目收尾执行清单

更新时间：2026-06-13

## 1. 收口判断

当前结论：底层能力不是主要缺口，主要缺口是产品化入口、闭环验证、统一观测和真实生产前置条件。

本清单用于把后续工作收敛为可交付迭代：

| 优先级 | 方向 | 当前判断 | 是否立即做 |
|---|---|---|---|
| P0a | 文件管理台基础版 | Beta 正在使用，用户首先需要看到文档状态 | 已实现基础版 |
| P0b | 上传后健康检查 | indexed 后补检索、source_ref、PDF 诊断，但不作为 ingestion gate | 已实现基础版 |
| P1.1 | Trace 基础版 | 已按 trace_id 聚合 routing + retrieval，解决 Beta 查询基础归因 | 已实现基础版 |
| P1.2 | Trace 完整版 | 补 tool/database/memory/SSE、request_id、对比和过滤 | 已实现基础版 |
| P2 | 数据库查看 UI | 需要真实只读数据库源，否则只能看 smoke 数据 | 有前置 |
| P3 | Memory 可见性 | Memory 当前默认 off/shadow，active 前用户不可见价值有限 | 有前置 |
| 延后 | 成本控制、路由 promote、AIOps 生产级、Skill 工程 | 需要真实指标、样本、投诉或 owner 要求 | 否 |

关键优先级调整：统一 Trace 时间线浏览器排在数据库 UI 前面。数据库 UI 依赖真实只读库前置条件；Trace 浏览器可以立即服务 Beta Week 2-3 的观察、归因和优化决策。

## 2. 已知事实边界

- RAG/PDF/Memory 三方案开发已经收口：Memory/Offload/PDF tools 已实现，默认 off/false，生产启用需要独立审批。
- RAG 当前处于 Beta Observation 阶段，默认保持 `dense_only / off / false / top_k=3`。
- 文件上传、文档状态、worker-health 的后端 API 已存在；P0a 文件管理前端和 P0b 上传后健康检查基础版已产品化，删除/重试仍未实现。
- 企业链路已有 audit、dashboard、routing shadow、SSE contract 等基础；P1.1 已支持按 `trace_id` 聚合 routing + retrieval，P1.2 已扩展为 `trace_id/request_id` 查询、tool/database/memory/SSE/permission/audit 聚合、source_ref 状态、过滤、复制和轻量 Trace 对比。
- 数据库能力已有 sandbox、非生产 MySQL smoke、safe-select、confirmation/direct execute 代码路径；生产数据库策略和完整 UI 仍未收口。
- Memory 当前不能当 RAG citation 使用；Memory guidance 是辅助上下文，不是文档证据。

## 3. P0a/P0b：前端文件管理 + 上传后测试闭环

目标：Beta 用户上传文档后，能在 UI 看到处理进度、失败原因和文档健康检查结果。

### P0a 文件管理台基础版

当前状态：已实现基础版。`GET /api/documents` 已支持默认 20 条分页、可见文档全生命周期状态列表、`trace_id/error_message` 等文件管理字段；前端已增加“文件管理”入口、列表、分页、10 秒处理中轮询和失败原因展示。P0a 不包含 P0b 健康检查、删除、重试或 Trace 时间线。

范围：

- 文档列表：文件名、类型、知识库、状态、上传时间、更新时间、操作。
- 状态展示：`uploaded / parse_pending / parsing / index_pending / indexing / indexed / failed` 等后端已有状态应以用户可读形式展示。
- 状态刷新：上传后自动轮询；页面手动刷新；终态停止高频轮询。
- 失败原因：展示 parse/index/enqueue 失败原因、trace_id 或 request_id。
- 操作：第一版以查看详情为主；重试、删除如后端缺 API，应显示 disabled 操作和缺口，不伪造能力。
- API contract 先行：先锁定列表和详情响应字段，再做 UI；缺字段要回到 contract，不在前端硬猜。

验收：

- 上传响应返回 `doc_id` 后，`/api/documents/{doc_id}` 能在 5 秒内返回该文档状态或明确错误。
- 活跃处理中文档的前端轮询间隔不超过 10 秒；终态后退避到手动刷新或低频刷新。
- 文档列表默认分页，第一页默认不超过 20 条，避免一次性拉全量。
- 文档状态能从处理中更新到 `indexed` 或失败态。
- 失败文档能看到明确错误原因或 trace_id。

验证建议：

```text
uv run pytest tests/test_document_processing_workflow.py tests/test_document_ingestion_service.py -q --no-cov
uv run pytest tests/test_assistant_frontend_optimization.py -q --no-cov
node --check static/app.js static/enterprise-api-client.js
git diff --check
```

### P0b 上传后健康检查

当前状态：已实现基础版。`VectorIndexService` 在文档进入 `indexed` 后以非阻塞方式投递健康检查；`DocumentHealthCheckService` 只做确定性诊断，覆盖检索命中、`source_ref` 一致性和 PDF artifact 可读性；结果保存在 JSON-backed `DocumentHealthCheckStore`。`GET /api/documents` 已返回 `health_check` 摘要，`GET /api/documents/{doc_id}/health` 返回详情，`POST /api/documents/{doc_id}/health/mark-false-positive` 记录误报；前端文件管理台新增健康度列、详情和误报入口。P0b 不改变文档 `indexed` 状态，不调用 LLM，不启用 query rewrite / hybrid / rerank 默认值。

范围：

- 文档 `indexed` 后自动触发健康检查。
- 健康检查第一版只做确定性检查，不调用 LLM 作为 gate。
- 检索测试：基于文档标题、文件名、显式关键词或 artifact chunk 抽样生成 query，验证能命中目标 doc。
- `source_ref` 测试：验证命中结果的 `kb_id/doc_id/chunk_id` 可解析，且不越权。
- PDF 测试：若文档有 PDF artifact，验证可读页；若存在 table artifact，再验证 table id 可解析。
- 健康度列：显示 `pending / passed / warning / failed / skipped`，并展示失败原因。
- 健康检查异步执行，进入独立队列或后台任务，不阻塞 indexing 和用户查询。
- 并发和重试要有限制；第一版允许跳过小文档或异常 artifact，并把结果标记为 `skipped`。
- 提供误报/忽略入口或状态，为后续 review 误报率留证据。

验收：

- 文档 `indexed` 后 30 秒内，UI 能显示健康检查 `pending / passed / warning / failed / skipped` 中的一种。
- 至少能区分：检索未命中、source_ref 不可解析、PDF 页/表 artifact 不可用、权限过滤。
- 健康检查失败不应把文档状态改成 indexed failed；它是质量诊断，不是 ingestion 状态。
- 健康检查队列长度超过 100 时必须降级：暂停自动检查或只保留手动触发。

验证建议：

```text
uv run pytest tests/test_document_health_check_service.py tests/test_assistant_frontend_optimization.py -q --no-cov
uv run pytest tests/test_knowledge_search_diagnostics.py tests/test_knowledge_query_orchestration_integration.py -q --no-cov
uv run pytest tests/test_pdf_document_tools.py tests/test_pdf_agent_tool_smoke.py -q --no-cov
node --check static/app.js
git diff --check
```

不做项：

- 不因为单个上传文档健康检查失败就修改全局 retrieval mode。
- 不启用 query rewrite、hybrid、rerank 默认值。
- 不把 LLM-as-judge 作为第一版上传健康 gate。
- 不把健康检查失败作为上传失败或 indexed 失败。

## 4. P1.1/P1.2：统一 Trace 时间线浏览器

目标：输入 `trace_id` 或 `request_id`，能看到一次请求的完整后端活动时间线，支持 Beta 问题归因。

### P1.1 Trace 基础版

当前状态：已实现基础版。`GET /api/admin/traces/{trace_id}` 已复用现有 audit 数据，按管理员 scope 返回 routing + retrieval 时间线；缺失 routing/retrieval 时显示 `not_recorded`；返回 30 天保留和 2 秒查询目标元数据；SQLite audit sink 已加 trace/timestamp 查询索引；admin console 已增加 Trace tab 和 raw JSON 展开。

范围：

- 新增或复用 admin API，第一版只按 `trace_id` 聚合 routing + retrieval。
- 输出统一 timeline item：`timestamp/source/stage/event_type/status/message/data`。
- 保留 raw JSON 展开能力，默认展示摘要。
- 缺失来源要显示 `not_recorded`，不能静默省略。
- 不要求第一版聚合 tool/database/memory/SSE；这些来源属于 P1.2 后续项。

验收：

- 输入 `trace_id` 能看到 routing decision 和 retrieval hits 的时间线。
- Trace 查询 P95 目标 < 2 秒；查询失败时返回结构化错误，不要求用户查终端。
- 能回答一次 query 未命中的基础原因属于：routing/retrieval 缺失、retrieval no-hit 或权限过滤；top_k/ranking、source_ref 解析、tool/database/memory/SSE 深度归因放入 P1.2。

### P1.2 Trace 完整版

当前状态：已实现基础版。`GET /api/admin/traces/{trace_id}` 现在同时支持 `trace_id` 和 `request_id` 识别，返回 `lookup.matched_by`；timeline 聚合 routing、retrieval、permission、tool、database、memory、sse 和 audit，缺失核心来源继续显示 `not_recorded`；retrieval item 返回 hits、source_refs 和 `source_ref_status`；summary 返回 route、top hit、source_ref、latency 和 terminal status。新增 `GET /api/admin/traces/compare?left=...&right=...`，用于同屏比较 routing、top hit、source_ref、latency 和 terminal status。Admin console 已增加 source 过滤、复制 trace_id、复制脱敏 JSON、trace 对比输入和对比表。

范围：

- 在 admin console 或 enterprise dashboard 增加 Trace 查询页。
- 支持 `trace_id/request_id` 查询，展示折叠时间线。
- 节点类型至少包括：routing decision、retrieval hits、source_ref、tool call、permission/audit、SSE event、memory/offload summary。
- 支持复制 JSON、复制 trace_id、按 event_type 过滤。
- 轻量 Trace 对比：同屏展示两个 trace 的 routing、retrieval hit、source_ref、latency、terminal status。
- 用于 dense vs hybrid shadow、同一问题不同 wording、修复前后对比。
- 普通用户和管理员看到的 trace 深度不同；敏感字段默认脱敏。

验收：

- 不打开终端、不查 SQLite、不翻 JSONL，也能完成一次 Beta 查询归因。
- 对 retrieval failure，页面能直接显示 hits、score/rank、target doc、source_ref 是否可解析。
- 能比较两个 trace 的实际 route、top hits、source_ref 和失败分类差异。

验证建议：

```text
uv run pytest tests/test_enterprise_observability_e9.py tests/test_enterprise_dashboard_e11.py -q --no-cov
uv run pytest tests/test_enterprise_trace_eval.py -q --no-cov
node --check static/admin-console.js static/enterprise-dashboard.js static/enterprise-api-client.js
git diff --check
```

不做项：

- 不让 Trace 浏览器修改业务状态。
- 不把 shadow routing 直接 promote 到默认路径。
- 不在 Trace UI 中泄露无权限文档内容、offload 原文或敏感数据库结果。
- 不把缺失来源当作成功聚合；必须显示 `not_recorded`。

## 5. P2：数据库查看 UI

前置条件：至少接入一个真实只读数据库源，并具备 read-only account、data owner、permission owner、allowlist、masking、audit 路径。

目标：用户能在 UI 浏览真实只读 catalog，生成安全查询，并查看历史查询/确认流程。

### P2.1 数据库 catalog 浏览器

范围：

- database -> table -> column 层级浏览。
- 显示 column 类型、敏感标记、可见性和授权状态。
- 点击 table 显示 schema。
- 提供“生成示例查询”按钮，生成 safe-select 草案。

验收：

- 用户能浏览真实只读库 catalog。
- 未授权表/列不可见或明确显示无权限，不泄露字段细节。

### P2.2 查询历史面板

范围：

- safe-select 历史：时间、trace_id、SQL hash/脱敏 SQL、结果行数、状态。
- confirmation 流程：pending、cancelled、expired、executed、failed。
- 支持按状态、database_id、trace_id 过滤。

验收：

- 能从一次查询跳转到对应 audit/trace。
- 用户能看到自己发起的 confirmation 状态。

### P2.3 Safety 边界可视化

范围：

- 展示当前 allowlist/denylist。
- 展示最大影响行数阈值。
- 展示 DDL allowlist 和删除类确认规则。
- 展示当前数据源是否只读、是否允许 direct execute。

验收：

- 用户能在执行前理解为什么某条 SQL 被允许、拒绝或要求确认。

验证建议：


不做项：

- 没有真实只读数据库源时，不启动完整 P2。
- 不把非生产 writable MySQL smoke 外推为生产可写上线。
- 不开放 confirm function calling；确认仍应走用户 HTTP/UI。

## 6. P3：Memory 可见性

前置条件：Memory 从 off/shadow 进入 active，且已有审批、rollback 和真实长会话 evidence。

目标：用户知道本轮是否使用了记忆、用了哪些、哪些被跳过，以及它不是文档引用。

范围：

- 回答旁显示本轮 Memory 状态：off/shadow/active。
- active 时显示使用了几条历史记忆。
- 展开后显示记忆摘要、时间、来源、owner、evidence id。
- 显示跳过原因：stale、truncated、permission denied、not selected。
- 明确标识 Memory 为 guidance，不作为 RAG citation。

验收：

- 用户能解释“为什么系统记得上次话题”。
- shadow 模式下只显示观测信息，不暗示已影响回答。
- active 模式下每条注入记忆都有 evidence 可追溯。

- 不跳过 Gate A.1/rollback/审批直接 active。

## 10. 长期运行预案

这些设计不是远期优化，而是 P0/P1 第一版实现时必须预留的运行边界。

### 10.1 存储增长

- Trace 聚合缓存或派生视图默认只保留最近 30 天；底层 audit retention 仍按合规文档单独治理。
- 每月评估 trace/audit/health-check 存储增长。
- 本地 SQLite/JSONL 超过 100MB 时启动压缩、分片或归档方案。
- 重要 trace 可以人工标记长期保留；默认普通成功 trace 不长期保存。

### 10.2 性能监控

- 文档列表查询目标 P95 < 1 秒，默认分页 20 条。
- Trace 查询目标 P95 < 2 秒。
- 健康检查队列长度目标 < 100；超过阈值自动降级或暂停自动检查。
- 活跃文档轮询采用退避策略，避免大量 indexed 文档持续轮询。

### 10.3 权限审计

- Trace 查询需要 admin 或受控 scoped-admin 权限。
- 普通用户只能查看自己的请求摘要，不能查看无权限文档内容、offload 原文、敏感 tool/database 参数。
- 敏感字段自动脱敏，至少覆盖 password、token、secret、email、phone、database credentials。
- Trace 查询本身写 audit，每月 review 权限日志。

### 10.4 健康检查运行边界

- 健康检查是诊断，不是 gate；失败不阻塞用户继续使用 indexed 文档。
- 健康检查异步、限流、可重试；失败原因要可见。
- 误报反馈要记录，后续按误报率调整检查策略。

### 10.5 延后项触发 review

- 每月 review 成本、路由 shadow、AIOps lab、Skill 工程的触发条件。
- 记录“接近触发”的项目和缺口，例如样本数不足、owner 未确认、指标缺失。
- 触发条件可以根据真实 Beta 数据修订，但必须记录理由。

## 11. 收尾验收总标准

- Beta 用户上传文档后能看到处理进度、失败原因和健康检查结果。
- 技术 reviewer 能通过 Trace 浏览器回答一次 Beta query 的路径和失败原因。
- 数据库 UI 和 Memory UI 不在前置条件不足时抢跑。
- 延后项都有明确触发条件，不因“看起来企业化”直接开工。
