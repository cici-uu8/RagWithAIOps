## 2026-05-31 Enterprise 2.0 F4 structured verifiers

- `PlanVerifier` 只做确定性规则：plan 不能为空、步骤数不能超过上限、不能出现合同禁止动作、不能使用合同外工具/数据源。它输出 `VerificationResult` / `VerificationFinding` / `VerificationStatus`，不调用 LLM，也不做自我反思循环。
- `CitationVerifier` 只信结构化 `source_ref`，不信 `citation_text`。这保证 citation 结果能跟 `trace_id` 一起审计，而不是把 display text 当成证据来源。
- `SqlResultVerifier` 只认 `safe_sql_verified=True` 和授权列列表，直接把 SQL 结果和 SafeSqlKernel / 权限过滤边界对齐。
- `VerificationService` 把 verifier 结果写入 `verification_result` audit 事件，并把 original error 的 class/message 保留下来，避免自检层吞掉原始失败信息。
- adapter 层接入点是最小的：AIOps 的 plan 事件、RAG retrieval 结果、DB `safe_select` 结果三处各写一笔 verifier audit；旧 planner / retrieval / SQL core 没有被重写。

## 2026-05-31 Enterprise 2.0 F5 structured failure recovery

- F5 的关键边界是“统一分类，但不抹掉来源”：audit 顶层 `error_class` 使用稳定枚举（如 `guardrail_blocked`、`model_unavailable`、`tool_failed`、`sql_blocked`），原始异常类保留在 `metadata.source_error_class` / `source_error_classes`，这样前端和 eval 不依赖 Python 异常名，排障仍能回看根因。
- 安全阻断不能复用模型/工具的恢复逻辑。`auth_failed`、`permission_denied`、`guardrail_blocked`、`sql_blocked` 全部走 `abort`，并显式标记 `retryable=false` / `fallback_allowed=false`；这是防止“自动恢复”变成绕过治理的核心测试点。
- fallback 成功不是普通 allowed，而是 degraded completion。ModelGateway 在备用模型成功时保留业务成功结果，同时 audit 写 `decision=degraded` 和 `recovery_decision=fallback`，后续 F8 才能用这些数据判断成本/延迟/质量策略是否需要调整。
